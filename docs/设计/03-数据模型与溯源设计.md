# 03 · 数据模型与溯源设计

> 本文是系统的**核心契约**。前端、后端、算法三方都依赖此处的锚点规范与坐标契约。

## 1. 实体关系

```
company（本期恒为固定值，多租户预留）
   └── project ── 可变容器 ──▶ project_file（软删除 / 替代关系）
          │                          │
          │                          ▼
          │                   document ──1:N── document_version
          │                                       │
          │                                       ├──1:N── page ──1:N── element ──0:N── table_cell
          │                                       │
          │                                       ├──1:N── parse_run（解析链，可多次）
          │                                       │
          │                                       └──1:N── field_instance ──1:N── extraction ──1:N── evidence
          │                                                                     │        │
          │                                                                     │        └──0:1── review_task（复核队列）
          │                                                                     └──1:N── review_action（事实标准）──▶ gold_item
          │
          └── lot（标段）：抽取结果的"适用范围"维度
```

设计要点：

- **`document_version` 是溯源的根**：所有 bbox、锚点、证据都挂在 version 上。文件更新即产生新 version，历史证据继续指向旧 version，永不错位。
- **`evidence` 独立成表且与 `extraction` 一对多**：同一字段在招标公告、须知前附表、合同条款多处出现是常态，必须支持多证据。
- **`extraction` 是"一次尝试"而不是"最终结果"**：同一字段的重跑与人工修正各占一行，`is_current` 标出当前值（见 4.6 节）。
- **`review_action` 是事实标准的生产记录**，与队列表 `review_task` 职责不同：前者记"人做了什么判断"，后者记"还有什么待办"。二者不能合并成一张表，否则"这一条待办最后是怎么处理的"将无法回答。
- **`element` 承载解析出的块**，是锚点的物理落点。
- **`project` 是可变容器**（见第 4 节）：文件可随时增删改，且不允许批量创建项目。
- **`company` 本期恒为固定值**，只做数据层预留（见 4.7 节）。

## 2. 锚点规范（Anchor）

### 2.1 格式

```
p{page_no}b{block_no}
```

- `page_no`：**1-based 物理页号**（与 MinerU locator 的 page 对齐）
- `block_no`：**1-based 块序号**（与该页内 MinerU 的 block 序号对齐）
- 示例：`p12b5` = 第 12 页第 5 个块

在喂给 LLM 的正文中，锚点以可识别的包裹形式出现：

```
<<p12b5>> 3.2 投标保证金金额为人民币伍万元整（¥50,000.00）。
```

### 2.2 为什么用自有锚点而不是 MinerU locator

| 方案 | 问题 |
| --- | --- |
| 直接用 `doc:{short_id}/tier:.../page:12/block:5` | token 成本高；且把 MinerU 的进程内 `short_id` 暴露成业务主键，服务重启/升级即失效 |
| 用原文片段本身做锚点 | 同一句话多处出现，无法消歧 |
| 用自增 ID | 重解析后 ID 变化，历史证据失效 |

**自有锚点 = 稳定 + 短 + 可重算**：`p12b5` 只依赖「页号 + 页内块序」，只要解析配置不变就可复现。它的**唯一范围是一次 `parse_run`**：重解析后 block 划分会变，同一个 `p12b5` 可能指向另一段文字，所以旧锚点不能拿到新 run 里用。`element` 表对 `(run_id, page_no, order_no)` 建**唯一索引**，锚点只是它的可读表示。

### 2.3 锚点分配规则

| 块类型 | 是否分配锚点 | 理由 |
| --- | --- | --- |
| 标题 / 段落 / 列表 | 是 | 主要证据来源 |
| 表格（整表） | 是 | 评分办法表、技术参数表是核心证据 |
| 图片 / 图表 | 是 | 可能作为佐证 |
| 页眉 / 页脚 / 页码 | **否** | 噪声，且会造成锚点空洞；但**仍落库**为 element，只是不参与编号 |
| `bbox` 为 `null` 的块 | 是（降级） | 允许存在，证据降级为页级定位 |

> **编号连续性是契约**：`block_no` 只在"参与编号的块"内连续递增。这样锚点不会因为页眉页脚的存在而出现跳号，降低 LLM 复述时的出错概率。

### 2.4 锚点的唯一性保障

- 数据库唯一索引：`UNIQUE (run_id, page_no, order_no)`——**锚点只在所属 `parse_run` 内唯一**，接口查锚点必须带上 `parse_run_id`
- 应用层：锚点生成后写入前做一次全集去重校验（防止 MinerU 返回的 block 序号有重复/缺失）

## 3. 坐标契约

### 3.1 规范

```
bbox = [x0, y0, x1, y1]
```

| 属性 | 约定 |
| --- | --- |
| 取值范围 | **0–1 归一化**（相对页面宽高） |
| 原点 | **左上角**（`y0` 是上边缘，`y1` 是下边缘） |
| 方向 | 基于**渲染后的视觉方向**（已处理 `/Rotate`） |
| 精度 | 存储 `numeric(7,6)`，约 0.1 微米级精度，远超需求 |
| 空值 | 允许 `NULL`，表示无几何信息，证据降级为页级定位 |

**前端只需做乘法**：

```ts
const rect = {
  left:   bbox[0] * viewport.width,
  top:    bbox[1] * viewport.height,
  width:  (bbox[2] - bbox[0]) * viewport.width,
  height: (bbox[3] - bbox[1]) * viewport.height,
};
```

这一条约定消灭了 PDF 坐标系（左下原点、pt 单位、MediaBox/CropBox 差异、旋转）带来的全部复杂度。**任何试图在前端做 PDF 原生坐标转换的实现都应被评审拒绝。**

### 3.2 归一化的责任方

| 数据来源 | 现状 | 我们的动作 |
| --- | --- | --- |
| MinerU MiddleJson | 已是 0–1 归一化，**但未声明原点** | **P0 实测确认原点方向**，若为左下原点则在适配器内统一翻转为左上 |
| 页面几何（我方自持） | pt 尺寸，不做归一化 | 由 pypdfium2 读页面尺寸与 `/Rotate`，落 `width_pt`/`height_pt`/`rotation`，不做归一化存储 |

### 3.3 页面尺寸为何必须自持

MinerU 的 `PageInfo` **不包含 `page_size`**。因此：

- 绝对坐标（pt）无法从 MiddleJson 还原；
- 页面几何必须由**我们自己的 PDF 引擎**读出并落库（`page.width_pt`、`page.height_pt`、`page.rotation`）。

`page` 以 `version_id` 为键、不带 `run_id`——页面几何是**版本的属性**，不随重新解析变化，因此按 `(version_id, page_no)` 幂等 upsert，重跑不重写。

这既是诊断依据（对比 PDF.js 读到的尺寸可发现渲染异常），也是**缩放重绘时 overlay 的唯一尺寸来源**。

**尺寸口径必须钉死**：`width_pt` / `height_pt` 记的是**未应用 `/Rotate` 的页面框（MediaBox）**，
视觉尺寸由 `rotation` 换算得到（`viewport_size()`）。把视觉尺寸直接写进来再加 `rotation=90`，
等于旋转算了两遍：PDF 渲染出来是横版、契约算出来是竖版。这时候共享向量的单测会**全绿**
（两边各自自洽），只有前端那条「渲染基座 = 解析基座」断言能抓住它。

> **落地提醒（阶段 0 必验）**：pypdfium2 的 `page.get_size()` 是否已经把 `/Rotate` 算进去，必须实测确认
> （pdfium 的 `FPDF_GetPageWidth` 语义历来是「旋转后的宽度」）；若已算进去，几何适配器要先换回来再落库。
> 同类坑的现成例子：reportlab 在 `/Rotate` 为 90/270 时会**再交换一次** MediaBox 宽高（`pdfbase/pdfdoc.py`），
> 所以 `scripts/make_sample_pdf.py` 里那行 `setPageSize` 看着是反着写的；
> 样本侧已由 `apps/web/scripts/verify-sample-coords.mjs` 兜住（拿渲染器读数与契约对账）。

### 3.4 旋转页处理

扫描件常见 90°/270° 旋转。规则：

1. 解析阶段读取 PDF 的 `/Rotate` 值，若为 90/270，**在适配器内对 bbox 做坐标变换**，输出始终是"视觉方向"的 bbox。
2. 前端渲染时用 `page.getViewport({ scale, rotation: page.rotate })`，得到的视口尺寸即"视觉方向"，与后端契约一致。
3. 两者必须同为视觉方向，否则高亮框会横过来——**这是最容易出现且最难排查的 bug，必须在联调第一轮就验证**。

## 4. 项目、文件与字段模型

### 4.1 项目是可变容器

业务约束：**一个项目下允许批量上传文件；不允许批量创建项目；上传后仍可修改、新增、删除文件。**

因此 `project` 不是冻结快照，而是活容器。三种操作必须区分语义，因为它们的技术处理完全不同：

| 操作 | 语义 | 处理 |
| --- | --- | --- |
| **改元数据**（重命名、改角色、调顺序） | 就地更新 | 不影响任何解析结果 |
| **换内容**（上传同一份文件的修订版） | 生成**新的 `document_version`** | `project_file.replaces_id` 指向被替代项；旧版本与其结果**保留**，标记为"已被替代" |
| **删除文件** | 软删除（`deleted_at`） | 该文件产生的抽取结果与证据**一并标记为"来源已移除"，不物理删除** |

> **为什么删除也要保留结果**：物理删除会让历史结果变成无源之水——用户看到一条保证金金额，点进去却没有原文。保留 + 标记，才能解释"当时为什么得出这个值"。审计要求也指向保留。

**UI 必须把"重命名"和"上传新版本"做成两个不同操作**，否则用户会误以为改的是同一件事，导致溯源指向错误版本。

### 4.2 文件角色与可解析性

招标包里的文件不是等价的，需要按角色区分：

| role | 说明 | 是否解析 |
| --- | --- | --- |
| `main` | 招标文件正文 | ✅ |
| `clarification` | 答疑纪要 | ✅ |
| `addendum` | 补充通知 / 变更公告 | ✅ |
| `boq` | 工程量清单（Excel） | 一期只存不解析 |
| `drawing` | 图纸（DWG/PDF） | 只存不解析 |
| `format` | 投标文件格式附件 | ✅（但与正文不冲突） |
| `other` | 其他 | 按扩展名决定 |

保留 `is_parseable` 字段，让"只存不解析"的附件在界面上依然可见、可下载——**它们必须"在"，因为业务方要能拿到原件**。

### 4.3 字段类型与多值

字段清单里混了三种形态，必须分开建模：

| 类型 | 字段举例 | 存储 | UI |
| --- | --- | --- | --- |
| **单值** | 项目名称、招标编号、保证金金额、开标时间 | 标量 | 值 + 证据 |
| **多值列表** | 资格要求、废标条款、星号技术条款 | 数组，**每项独立带锚点** | 可勾选清单（接上"逐条核对"形态） |
| **表结构** | 评分办法、技术参数表 | 整表锚点 + 结构化行数组 | 表格 + 整表高亮 |

> **多值列表的每一项必须独立带锚点**：一条资格要求可能在投标人须知第 8 页，另一条在技术规范第 45 页。共用一个整段锚点会让定位失去意义。

### 4.4 标段适用范围

一个招标文件常分多个标段（包），不同标段的保证金、工期、资格要求**可能完全不同**。整份文档只抽一组值会直接导致投标错误。

- `extraction.lot_id` 为 `NULL` 表示**全文适用**；否则表示仅适用于该标段。
- 一期实现：识别标段结构 → 给字段打适用范围标签；**识别不确定时降级为全文适用**（宁可标注保守，不可标错）。
- 标段识别失败的表现是"实际按标段区分的要求被当成全文要求"，因此识别置信度低时应在 UI 上提示人工确认。

### 4.5 跨文件冲突

主文件抽出的值**可能被后续文件推翻**——最典型的是答疑纪要/补充通知改开标时间、改保证金、改最高限价。

**策略：只标注冲突，不自动覆盖。**

- 同一字段在同一项目内出现多个不同值时，建立 `extraction_conflict` 记录，把候选值并列展示。
- 后出文件（按 `role` + 上传时间判断）的值标记为"可能覆盖"，但**不自动采信**。
- 强制进入人工复核，由业务方裁定，裁定结果写入 `resolved_id`。

> **为什么不自动覆盖**：自动判定依赖"文件类型 + 时间先后"的正确识别，一旦误判就会自动给出错误答案——在投标场景下，这比让用户自己看一眼严重得多。

### 4.6 结果的尝试与确认

**结果不是一行记录，而是一条尝试链。**

同一个字段在同一份文档上会被反复处理：首次自动抽取 → 用户重跑 → 管理员换提示词重跑 → 人工修正。每次处理都是一次**尝试**：

- 每次尝试**单独落一行**（`extraction` 表），append-only，**永不 UPDATE 覆盖**；`is_current` 标出当前生效的那条。`attempt_no` 是时间线序号（含人工修正），`machine_attempt_no` 只给机器结果编号——统计模型成功率时二者**绝不能混用**。
- 每个（文档版本 + 字段 + 标段）对应一个稳定的 `field_instance`，尝试链挂在它下面。
- 人工复核产生 `review_action` 记录，这是"事实标准"的唯一来源（见 [09-评测与质量门禁.md](../质量/09-评测与质量门禁.md)）。

| 操作 | `trigger` | 锚点/坐标 | 之前的确认结果 |
| --- | --- | --- | --- |
| 首次自动抽取 | `first` | — | — |
| 带提示重跑 | `hinted_rerun` | 不变 | 保留，被新尝试取代 |
| 无提示重跑 | `user_rerun` | 不变 | 同上 |
| 换参数重跑抽取 | `param_rerun` | 不变 | 同上 |
| 重新解析文档 | `reparse` | **全部重建** | **全部打回重新复核** |
| 人工修正 | `manual_edit` | 用户重新框选 | 同上 |

> **"重新抽取"与"重新解析"必须严格分开**：前者只重跑抽取层，MinerU 产物复用，锚点仍指向同一段文字，历史确认只是被取代；后者重跑 MinerU，block 划分与 bbox 全部重建，**旧证据作废、所有已确认结果强制打回重新复核**。两者的代价差一个量级，绝不能放在同一个按钮上。详见 [09](../质量/09-评测与质量门禁.md) 第 2.1 节。

**为什么坚持 append-only**：需要回答"这个值被改过几次、每次是什么、谁改的"。覆盖式更新会让"首次通过率"和"第 k 次救回率"这两个指标根本算不出来，也会让用户失去对修正历史的可追溯性。

### 4.7 多租户预留（本期不实现）

公司隔离、跨公司共享、平台管理员均列为**后续扩展**。本期为单租户部署，但保留两件事：

1. 顶层实体（`project` / `document` / `document_version` / `config_release` 等）**带 `company_id`，`NOT NULL`，本期恒为配置中的固定值**。
2. 数据访问层统一通过「当前租户上下文」注入过滤条件，**业务代码不得直接写死 `company_id`**。

> **为什么这一项值得现在做**：给已上线、有几万行数据的表补一个 `NOT NULL` 的租户列，需要迁移 + 回填 + 改遍所有查询；而现在做只是每张表多一列 + 一个取值函数。这是多租户问题上唯一强烈建议保留的预留。

## 5. 表结构

本节是 DDL 的**唯一权威**，`apps/api/alembic/versions/0001_initial_schema.py` 是它的可执行副本（由本节抽取生成，逐字保留列名与索引）。**改表结构只改本节**，再同步迁移；`apps/api/tests/contract/test_ddl_matches_docs.py` 从两侧各解析一次结构（表名 / 列名 / 索引名）再比对，任何一侧漏改都会立刻变红。

迁移相比本节有三处必要补充（直接按章节顺序执行本节会失败）：补 `CREATE EXTENSION pg_trgm`；把 `field_instance.current_extraction_id`、`config_release.regression_run_id` 这两处互相引用的外键延后成 `ALTER TABLE ... ADD CONSTRAINT`；执行顺序按外键依赖排而非章节顺序。原因写在迁移文件的 docstring 里。

为什么权威在文档而不在迁移：本节同时讲清了字段语义与溯源规则，是评审对象；以迁移为准，这些解释必然退化成注释。

```sql
-- 文档（逻辑实体，代表"一份标书"）
CREATE TABLE document (
    id            BIGSERIAL PRIMARY KEY,
    title         TEXT         NOT NULL,          -- 初始取文件名，可人工修改
    project_no    TEXT,                            -- 招标编号，抽取后回填
    status        TEXT         NOT NULL DEFAULT 'active',
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    deleted_at    TIMESTAMPTZ
);

-- 文档版本（溯源的根，由内容哈希唯一定位）
CREATE TABLE document_version (
    id                 BIGSERIAL PRIMARY KEY,
    document_id        BIGINT      NOT NULL REFERENCES document(id),
    version_no         INT         NOT NULL,
    sha256             CHAR(64)    NOT NULL,       -- 原始文件内容哈希
    mime               TEXT        NOT NULL,
    size_bytes         BIGINT      NOT NULL,
    original_key       TEXT        NOT NULL,       -- 原件对象存储 key
    -- 转换产物（PDF 直通时等于原件）
    pdf_key            TEXT        NOT NULL,       -- 坐标基座
    pdf_sha256         CHAR(64)    NOT NULL,
    is_converted       BOOLEAN     NOT NULL,       -- 是否经过格式转换
    converter          TEXT,                       -- 'gotenberg'
    converter_version  TEXT,                       -- GET /version 的结果
    page_count         INT,
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (document_id, version_no)
);
CREATE UNIQUE INDEX ux_version_sha ON document_version (sha256, converter_version);
CREATE INDEX ix_version_doc ON document_version (document_id, created_at DESC);

-- 解析运行（一次 MinerU 调用，记录全部环境信息以支持重放）
CREATE TABLE parse_run (
    id                 BIGSERIAL PRIMARY KEY,
    version_id         BIGINT      NOT NULL REFERENCES document_version(id),
    provider           TEXT        NOT NULL DEFAULT 'mineru',
    provider_version   TEXT        NOT NULL,       -- MinerU 版本
    tier               TEXT        NOT NULL,       -- flash|basic|standard|advanced
    backend            TEXT,                       -- pipeline|vlm|hybrid，来自产物
    schema_version     TEXT        NOT NULL,       -- MiddleJson schema_version
    status             TEXT        NOT NULL,       -- pending|running|completed|partial|failed|canceled
    request_id         TEXT,                       -- Gotenberg-Trace 风格的自有 job id
    raw_middle_key     TEXT,                       -- MiddleJson 原始产物存档
    raw_content_key    TEXT,                       -- Content List 存档
    page_count         INT,
    elapsed_ms         INT,
    error_code         TEXT,
    error_message      TEXT,
    started_at         TIMESTAMPTZ,
    finished_at        TIMESTAMPTZ,
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

### 5.3 结果尝试与事实标准

```sql
-- 字段实例：跨尝试不变的稳定身份
CREATE TABLE field_instance (
    id            BIGSERIAL PRIMARY KEY,
    version_id    BIGINT      NOT NULL REFERENCES document_version(id),
    field_key     TEXT        NOT NULL,
    lot_id        BIGINT      REFERENCES lot(id),          -- NULL = 全文适用
    -- 当前展示哪一次结果；由应用在新尝试落库后更新（唯一 current 约束在 extraction 上）
    current_extraction_id BIGINT REFERENCES extraction(id),
    first_seen_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (version_id, field_key, lot_id)
);

-- 复核动作：事实标准的生产记录（每次确认/修正/补充各一行，只增不改）
CREATE TABLE review_action (
    id          BIGSERIAL PRIMARY KEY,
    instance_id BIGINT      NOT NULL REFERENCES field_instance(id),
    attempt_id  BIGINT      NOT NULL REFERENCES extraction(id),  -- 被核对的机器尝试
    -- correct/supplement 产生的人工结果快照；confirm/reject 时为空
    result_attempt_id BIGINT REFERENCES extraction(id),
    action      TEXT        NOT NULL,       -- confirm|correct|supplement|reject
    review_mode TEXT        NOT NULL,       -- item（逐条）|batch（批量勾选）|spot_check（抽检）
    old_value   JSONB,                      -- correct 时保留原值，供统计与回归
    new_value   JSONB,
    evidence    JSONB,                      -- 用户框选的锚点，correct/supplement 必填
    actor       TEXT        NOT NULL,
    comment     TEXT,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_review_action_instance ON review_action (instance_id, created_at DESC);
CREATE INDEX ix_review_action_mode ON review_action (review_mode, created_at DESC);

-- 回归集条目：由 correct / supplement 快照而来，与生产数据物理隔离
CREATE TABLE gold_item (
    id                 BIGSERIAL PRIMARY KEY,
    source_instance_id BIGINT,                -- 只留血缘，不设外键（理由见下）
    version_id         BIGINT      NOT NULL,
    field_key          TEXT        NOT NULL,
    expected           JSONB       NOT NULL,
    expected_anchors   TEXT[]      NOT NULL,  -- 必须非空：gold 一定带锚点
    origin             TEXT        NOT NULL,  -- correct|supplement
    param_snapshot     JSONB       NOT NULL,  -- 产出这条 gold 时的参数，回放时用于分层
    created_at         TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ix_gold_field ON gold_item (field_key);
```

**为什么 `field_instance` 要独立成表，而不是靠 `(version_id, field_key, lot_id)` 三元组现算**：尝试链、复核状态、统计口径都要挂在同一个东西上。三元组现算的话，任何一处写错（例如漏掉 `lot_id` 为 NULL 的语义）都会让统计悄悄错位，而且无法建外键约束。给它一个主键，是所有下游统计可靠的前提。

**`review_mode` 为什么必须记**：用户对高置信项"批量勾选通过"时并没有真看。把批量通过和逐条细看混进同一个分母，首次通过率会被系统性抬高。分档之后，抽检数字只能用于校准 `batch` 档，不能拿去修正 `item` 档。

**为什么要分 `attempt_no` 与 `machine_attempt_no` 两个序号**：时间线要能完整回放（谁在什么时候改过什么），但统计模型成功率时必须只看机器产生的结果。若人工修正也占用机器序号，第 k 次救回率就会把"人改对了"算成"模型跑对了"，指标立刻失真。人工修正通过 `review_action.result_attempt_id` 关联到它产生的结果快照。

**为什么机器序号在同一 `parse_run` 内唯一、换 run 后从 1 重新计数**：锚点 `p12b5` 只在所属 `parse_run` 内有意义(见 2.1 节)。重新解析后，新 run 的第一次抽取就是它的第 1 次机器尝试，这样「重解析后的首次通过率」才能与「重解析前」分开对比，而不是被历史序号污染。
**为什么 `gold_item.source_instance_id` 不设外键**：生产数据会随项目删除而清理，而回归集必须能独立存活——它是历史资产的沉淀，不能跟着业务数据一起消失。

**为什么 gold 必须带锚点**：只有值没有出处的样本无法验证定位质量。而"值对了但高亮标错位置"同样会让用户失去信任，且仅比对值发现不了这类错误。

## 6. 对象存储布局

```
s3://ai-tender/{company_id}/
  originals/{sha256}/source{ext}                     # 原始上传件（法律原件，永久）
  attachments/{project_id}/{project_file_id}/{name}  # 只存不解析的附件（图纸/清单）
  converted/{src_sha256}/{pdf_sha256}.pdf            # 转换产物（坐标基座）
  render/{version_id}/crops/{crop_key}.webp         # 多模态裁剪图（按需生成，crop_key = hash(page_no + bbox + dpi)）
  mineru/{version_id}/{run_id}/middle.json           # 原始产档存档（审计/重放）
  mineru/{version_id}/{run_id}/content_list_v2.json
  mineru/{version_id}/{run_id}/images/...
  exports/{version_id}/{export_id}.{ext}
```

原则：

- **按内容哈希寻址的层**（originals / converted）天然去重，可永久保留。
- **按版本寻址的层**（render / mineru）随版本走，删除文档时按版本清理。
- **`mineru/` 下的原始产物必须存档**：MinerU schema 跨大版本不兼容（见 [01](../调研/01-接口调研-MinerU.md)），没有原始产物就无法回溯历史结果是如何产生的。
- **本期不生成整页图**：在线预览由前端 `pdfjs-dist` 直接渲染 PDF 基座（见 [06](06-前端展示与定位.md) 第 3 节），定位靠归一化 bbox 现场换算——两者都不需要服务端位图。`render/` 下只有多模态裁剪图，按 `(version_id, page_no, bbox, dpi)` 寻址，同一区域重复裁剪时天然复用。

## 7. 幂等、重跑与版本

| 场景 | 行为 |
| --- | --- |
| 相同文件重复上传 | `sha256` 命中已有 version → 直接复用，不重复转换与解析 |
| **重新抽取**（换提示词 / 换模型 / 用户重跑） | 复用现有 `parse_run` 与 `element`，只新增一条 `extraction` 尝试（同一 run 内 `machine_attempt_no + 1`）。**锚点与坐标不变**，历史确认仅被新尝试取代 |
| **重新解析**（换 tier / ocr_mode / MinerU 版本） | 新建 `parse_run` → 重建 `element`，机器解析序号在新 run 内**从 1 重新计数**。**旧锚点在新 run 中失效**：当前结果强制打回待复核；旧 `review_action` 与旧指标保留在旧 run 的历史里继续可查，但**不能替新 run 的结果背书** |
| 同文件用不同档位解析（对比用途） | 新建 `parse_run`，`element` 按 run 隔离存储；切换"当前 run"时才替换 `is_current`，切换前可与旧 run 做差异比对 |
| MinerU 服务重启导致 job 丢失 | 按 `sha256` 重新提交（MinerU 侧文件命中复用，代价很低）。**upload/file/job ID 全为进程内状态，不可假设可续跑** |
| 文件内容变化 | 新 `sha256` → 新 version → 历史证据不受影响 |
| MinerU 升级 | 按"重新解析"处理，与旧 run 做差异比对后再切换当前版本 |

> **两条链必须分开记**：`parse_run` 记的是"文档被怎么解析的"，`extraction` 链记的是"字段被怎么抽取的"。把两者混成一条链，就会出现"改一句提示词导致所有已确认结果被打回"这种代价失控的情况。

## 8. 已知缺口（明确不接受范围外承诺）

| 缺口 | 影响 | 缓解 |
| --- | --- | --- |
| **无单元格级 bbox** | 评标办法表只能高亮整张表，不能精确到某个评分项所在单元格 | 二期：解析表格 HTML + 按块内字符区间近似定位；或视觉方案检测表格线 |
| 无印刷页码（`page_label`） | 用户口中的"第 X 页"可能指印刷页码，与物理页号不一致 | 在页面上叠加显示物理页号；抽取印刷页码后建立映射表（后续） |
| 扫描件无原生文本层 | 无法做字符级高亮 | 证据降级为 bbox 矩形高亮 + 侧栏展示 OCR 文本，并标注来源为 OCR |
| 手写签名/印章覆盖文字 | OCR 可能出错 | 证据标 `quote_source=ocr`，UI 提示人工核对 |
| **重解析作废全部确认** | 换 MinerU 版本 / 档位后所有已复核结果需重新复核，人工成本集中爆发 | 仅管理员可触发 + 二次确认（确认框内显式列出将失效的已确认数量）+ 强制填写理由并进审计；旧记录保留为审计不物理删除 |
