## 3. 渲染方案

**用 `pdfjs-dist` 直接控制，不用 `react-pdf`**——因为需要自绘高亮层并精确控制坐标，封装库会挡住关键 API。

```ts
// 渲染一页：位图 + 文本层
async function renderPage(pdf: PDFDocumentProxy, pageNo: number, scale: number) {
  const page = await pdf.getPage(pageNo);
  // rotation 必须显式传入：扫描件常带 90/270 度旋转，
  // 传入 page.rotate 后 viewport 即为"视觉方向"，
  // 与后端归一化 bbox 的方向约定保持一致（见 03 文档 3.4）。
  const viewport = page.getViewport({ scale, rotation: page.rotate });

  const canvas = document.createElement('canvas');
  canvas.width = viewport.width;
  canvas.height = viewport.height;
  await page.render({ canvasContext: canvas.getContext('2d')!, viewport }).promise;

  return { page, viewport };
}
```

**首屏与预览**：原文渲染的唯一数据源是 PDF 基座（`GET /versions/{vid}/file`，见 [05](05-后端API设计.md) 第 1 节），`pdfjs-dist` 按 Range 边下边渲染；第一页呈现前用**骨架屏**占位——**不预渲染、不存储任何服务端位图**。

**为什么不做页图占位**：页图要在服务端全量渲染并长期存储（扫描件单份几十 MB），而它只在首屏生效几秒。骨架屏 + 结果面板先出已经能消除长时间空白感，收益远大于成本。

**字体必须内嵌（阶段 0 实测结论）**：pdf.js 没有「未内嵌中文字体」的替换表——遇到只引用不内嵌的 CID 字体
（例如 reportlab 默认的 STSong-Light）会**整页渲染成豆腐块**；cMaps 只解决「CID → Unicode」，解决不了「谁来画字形」。
因此 DOCX → PDF 转换（LibreOffice）必须在容器里装好中文字体并启用字体内嵌，上线前拿一份真实标书验证正文可读。
本仓库的样本 PDF 已改为内嵌字体子集（见 `scripts/make_sample_pdf.py`），并留了 `pnpm verify:sample` 做几何对账。

**为什么不做缩略图导航**：前端生成缩略图必须先拿到整份 PDF（扫描件动辄数百 MB），服务端生成又要引入全量渲染。页码范围导航改由两部分承担：

- **页码跳转**：Toolbar 输入页码 → 滚动到该页占位元素（高度来自 `width_pt/height_pt`，不需要先渲染）；
- **章节树**：用 `element.level` / `parent_id`（MinerU `title_leveling` 产出，见 [03](03-数据模型与溯源设计.md) 第 5 节）生成目录，点击跳到对应页并高亮该标题块。

## 4. 高亮分层策略

**两层叠加，各司其职**：

| 层 | 何时使用 | 精度 | 视觉 |
| --- | --- | --- | --- |
| **bbox 矩形层** | **始终绘制** | 块级 | 半透明黄底 + 描边 |
| **文本 span 层** | 存在原生文本层且能定位到字符区间时绘制 | 字符级 | 加深底色 + 下划线 |

**为什么两层都要画**：

- bbox 矩形是**兜底且永不失败**的——它只依赖归一化坐标，与文本层质量无关，对扫描件同样有效。
- 文本 span 提供**可复制、可读**的精确高亮，是数字 PDF 的体验上限。
- 扫描件没有原生文本层，此时只画矩形，并在侧栏展示 OCR 文本——**不要为扫描件硬造伪文本层**，收益低而复杂度高。

```tsx
// 高亮绘制：坐标换算只有乘法，这是归一化契约换来的最大红利
function EvidenceOverlay({ bbox, viewport, pulse }: Props) {
  const [x0, y0, x1, y1] = bbox;
  const style: CSSProperties = {
    left:   x0 * viewport.width,
    top:    y0 * viewport.height,
    width:  (x1 - x0) * viewport.width,
    height: (y1 - y0) * viewport.height,
  };
  // pointer-events:none 必须设置，否则覆盖层会吞掉用户的文本选择与点击
  return <div className={cx('evidence-rect', pulse && 'pulse')} style={style} />;
}
```

```css
/* 闪烁三次后停在常亮状态：常亮是为了让用户随时知道当前定位在哪，
   闪烁只是引导视线，不能闪完就消失 */
.evidence-rect.pulse { animation: pulse 0.6s ease-in-out 3; }
@keyframes pulse {
  0%, 100% { background: rgba(255, 214, 0, 0.28); }
  50%      { background: rgba(255, 145, 0, 0.55); }
}
```

## 5. 点击定位时序（核心逻辑）

这是整个前端最关键的 40 行代码。**顺序不能变**，每一步都对应一个真实的失败模式。

```ts
/**
 * 点击结果卡片 → 定位并高亮原文
 *
 * 三个关键点（顺序不可调换）：
 *  1. 必须先确保目标页已渲染完成，否则会出现"跳过去了但没高亮"
 *  2. 必须先滚动页面挂载，再画 overlay，否则 overlay 被创建在未挂载的 DOM 上
 *  3. 缩放后必须能重绘，所以当前高亮要存进状态而不是画完即忘
 */
async function locateEvidence(ev: Evidence) {
  const { page_no, bbox } = ev;

  // ① 确保页面已渲染（虚拟滚动场景下，目标页通常是未挂载的）
  const pageView = await ensurePageRendered(page_no);

  // ② 页面级滚动：把目标页移到视口内
  pageView.root.scrollIntoView({ block: 'center', behavior: 'auto' });

  // ③ 等待一帧，确保浏览器完成布局，否则拿到的尺寸是旧的
  await nextFrame();

  // ④ 写入"当前高亮"状态（驱动 EvidenceLayer 重绘）。
  //    用状态而非直接操作 DOM，是为了缩放/resize 时能自动重算矩形。
  setActiveEvidence(ev);

  // ⑤ 页内精确滚动：把高亮块移到视口中央
  //    用 'smooth' 提升可感知性——用户需要看到"从哪滚到哪"
  pageView.evidenceRoot.scrollIntoView({ block: 'center', behavior: 'smooth' });

  // ⑥ 触发闪烁
  setPulseKey(k => k + 1);
}

/** 确保某页已渲染，返回其视图对象；重复调用复用同一 Promise，避免并发重复渲染 */
const renderPromises = new Map<number, Promise<PageView>>();

function ensurePageRendered(pageNo: number): Promise<PageView> {
  const cached = renderPromises.get(pageNo);
  if (cached) return cached;

  // 先滚动到占位元素，IntersectionObserver 才会触发真实渲染
  scrollToPlaceholder(pageNo);

  const task = waitForRender(pageNo).then(buildPageView);
  renderPromises.set(pageNo, task);
  return task;
}
```

**必须处理的边界场景**：

| 场景 | 处理 |
| --- | --- |
| 目标页渲染失败 | 捕获异常 → 降级为"仅滚动到页 + toast 提示"，不阻断用户 |
| 同一结果被连续点击 | `pulseKey` 自增触发重新动画；否则用户以为没响应 |
| 快速连续点击不同结果 | 用 `AbortController` 或请求序号丢弃过期响应，避免"停在中间某页"的错乱 |
| `bbox` 为空（降级证据） | 不做矩形高亮，改为**整页边框闪一下** + 提示"该结果仅有页级定位" |
| 多证据 | EvidenceList 切换时复用 `locateEvidence`，并记录当前 `seq` |

## 6. 缩放与重绘

```tsx
// 缩放/窗口变化后必须重算 overlay。
// 把 activeEvidence 作为 useEffect 依赖，是保证"缩放后高亮不漂移"的关键。
useEffect(() => {
  if (!activeEvidence) return;
  // 重新计算该页所有 overlay 矩形（bbox 不变，只变乘数）
  recomputeOverlays(activeEvidence.page_no, scale);
}, [scale, activeEvidence]);

// 缩放比例变化时，PDF.js 必须整页重渲染（canvas 尺寸变了），
// 因此 renderPromises 缓存必须失效，否则会拿到旧尺寸的视图对象。
useEffect(() => {
  renderPromises.clear();
  setActiveEvidence(ev => ev); // 触发重绘保持高亮
}, [scale]);
```

## 7. 虚拟滚动

- **只渲染可视页 ± 2 页**，其余用等高占位元素（高度 = `width_pt/height_pt` × 当前宽度）。
- 用 `IntersectionObserver` 触发挂载/卸载；滚动时用 `rootMargin: '200% 0px'` 预渲染上下两屏，减少滚动空白。
- **销毁页面前必须 `page.cleanup()` 并取消未完成的 `renderTask`**，否则缩放时会出现"幽灵渲染"覆盖新内容。
- **已知限制**：改 canvas 尺寸会立刻清空位图，新的一帧画完前该页会有极短空白（缩放时可见）。彻底消除要双缓冲
  （旧位图留到新位图画好再换），代价是多一份 canvas；当前先不做，缩放重绘的目标时间（< 200ms）已由「只重绘可视页」保证。
- 页高用 `width_pt/height_pt` 计算，保证占位高度与真实渲染高度一致，**否则滚动位置会在渲染完成瞬间跳动**。

## 8. 反向标注（= 生产事实标准）

在 `AnchorLayer` 上开启框选模式：

```
用户框选 → 命中所在 element（锚点反查或本地 elements 缓存）
        → 显示候选块 bbox 边框，用户确认选对了块
        → 弹出修正面板（当前值 / 框选文本 / 提交）
        → POST /instances/{iid}/reviews
          { action: 'correct' | 'supplement', review_mode: 'item',
            new_value, evidence: [{ anchor, match_type: 'manual' }] }
        → 本地更新结果面板，并刷新尝试链
```

要点：

- **锚点是必填项，不是可选项**：`correct` / `supplement` 若不带锚点，后端直接返回 422 `missing_evidence`。前端要在提交按钮上做同样的禁用态，**别让用户点了才知道**。
- 框选结束后立即**显示候选块的 bbox 边框**，让用户确认选对了块再提交——避免误选后又要重来。
- 支持**多锚点**：允许用户依次框选多处作为同一条结果的证据（标书中"资格要求"常分散在两三处）。
- **必须提供"文档中确实没有"的出口**：面板上给一个与"提交"并列的按钮——「文档中未提及」。它提交的是 `action: confirm`（针对 `status=not_found` 的那次尝试），而**不是编一个空值**。
- 反向标注产生的 `match_type='manual'` 证据是**最高质量样本**，经 `review_action` 落库后自动进入回归集（见 [09-评测与质量门禁.md](../质量/09-评测与质量门禁.md) 第 4 节）。

> **为什么把"没有"做成独立按钮，而不是让用户留空提交**：留空会被后端当成"值未变"，用户以为标记过了、系统其实什么都没记；而且留空无法区分"文档里确实没有"和"忘了填"。

## 9. 结果面板的六种特殊形态

这六种形态在招标场景里天天出现，且都直接影响"能不能信任结果"，不能按普通字段渲染。前三节是"结果长什么样"，后三节是"结果被改过之后长什么样"。

### 9.1 多值字段 → 可勾选清单

资格要求、废标条款、星号技术条款这类多值字段**不能渲染成一个长文本块**——业务方的动作是"逐条核对能不能满足"。

```
投标人资格要求（12 条）                    [批量确认]
  ☐ 第 1 条  具备建筑工程施工总承包一级及以上资质      [定位] ✓
  ☐ 第 2 条  近三年完成过单项合同额 ≥5000 万的业绩     [定位] ✓
  ☐ 第 3 条  拟派项目经理须具备一级建造师资格          [定位] ✓
  ...
```

- 每条右侧带证据角标，点击**单独定位到该条的锚点**——每条有独立锚点，可能分布在完全不同的页。
- 支持标注"满足 / 不满足 / 待确认"，该标注可随导出一起出去，直接变成应标核对底稿。

### 9.2 未找到字段 → 显式显示，绝不隐藏

```
投标保证金金额
  未在本文档中找到            [确认没有] [人工补充]
```

- **不允许隐藏该字段**。隐藏会让用户以为系统漏了，反而破坏信任。
- 提供"人工补充"入口：用户在原文框选后手动填入，走反向标注链路，产生 `match_type=manual` 的证据。
- 这类字段在评测报告里单独统计（见 [09-评测与质量门禁.md](../质量/09-评测与质量门禁.md)）。
- **「确认没有」必须和「人工补充」并列**：前者提交 `action=confirm`（确认系统判断正确），后者提交 `action=supplement`。两个动作都会让实例收敛、都会进统计——**「确认没有」不是「没操作」**。

### 9.3 跨文件冲突 → 并列展示 + 强制裁定

补充通知改了保证金或开标时间时的呈现：

```
投标保证金金额                                     ⚠ 存在冲突
  ¥50,000.00    《招标文件》   p12b5     [定位]
  ¥80,000.00    《补充通知2》  p3b2   ← 可能覆盖   [定位]

  [采信第一条]  [采信第二条]  [都不对，手动填入]
```

- **两个值都展示，系统不自动选一个**。
- 后出文件的值打"可能覆盖"标记，但**不自动采信**（见 [03](03-数据模型与溯源设计.md) 第 4.5 节的取舍理由）。
- 裁定动作进审计日志。

### 9.4 标段筛选器

- 项目含多标段时，结果面板顶部出现切换器：`全部 / 一包 / 二包 / …`
- 每张结果卡显示**适用范围徽标**（"全文"或具体标段）
- 标段识别置信度低的结果带"待确认适用范围"提示，引导人工复核
- 切换标段时同时过滤原文高亮层，避免不同标段的要求互相干扰

### 9.5 尝试链与版本切换

一个字段可能被重跑过多次。面板必须让用户**随时知道自己在看哪一次**：

```
投标保证金金额                              [重跑] [定位]
  ¥80,000.00          第 2 次尝试（带提示重跑）   ✓ 已确认
  ────────────────────────────────────────────────
  历史 ▸  第 1 次  ¥50,000.00                    × 已修正
```

- 默认只展示 `is_current = true` 的尝试，历史收在折叠区，点击展开。
- 展开的每次尝试显示：`machine_attempt_no`（机器解析序号，人工修正显示为「人工」）/ trigger 中文名 / 值 / 证据 / 当时是否被确认。
- **被取代的确认必须显式标注**：用户可能记得"我明明确认过 5 万"，页面要能解释清楚「你确认的是第 1 次，第 2 次重跑后已被取代」。
- trigger 的中文名必须全局统一，不允许各处自造：

| trigger | 中文名 |
| --- | --- |
| `first` | 首次抽取 |
| `hinted_rerun` | 带提示重跑 |
| `user_rerun` | 重跑 |
| `param_rerun` | 换参数重跑 |
| `reparse` | 重新解析 |
| `manual_edit` | 人工修正 |

**重新解析后的状态**：受影响实例的卡片顶部显示横幅——「本文档已重新解析，此前 318 条确认结果已失效，需重新复核」。**不能静默清空**，否则用户会以为系统丢了数据，进而不再信任任何一条结果。

### 9.6 重跑入口与"值不值"提示

重跑按钮的形态由服务端下发的 `rerun_button` 决定（见 [05-后端API设计.md](05-后端API设计.md) 第 3.12 节）：

| `rerun_button` | 渲染 |
| --- | --- |
| `show` | 普通「重跑」按钮 |
| `show_hint` | 「重跑」按钮 + 前缀提示「重跑一次通常能修好」 |
| `hide` | 主操作位只留「人工修正」，「重跑」收进"更多"菜单 |

- **带提示重跑**：点击后在面板内展开一行输入框，引导语示例——`该值可能在"投标人须知前附表"或"评标办法"章节`。允许留空（留空即普通重跑）。
- 重跑进行中按钮置灰并显示进度；重复点击由后端 409 `rerun_in_flight` 兜底。
- **重跑时不要锁住面板**：用户可以继续核对其他字段，结果回来后就地刷新该卡片。

> **为什么重跑按钮的显隐要由数据决定**：某些字段重跑是纯粹浪费用户时间（模型每次都给出同一个错值）。把它藏起来，比给一个总是失败的按钮更有诚意。

## 10. 性能预算

| 指标 | 目标 | 手段 |
| --- | --- | --- |
| 工作台首屏 | < 1.5 s | 结果面板先出；原文区骨架屏 + PDF 基座 Range 渐进渲染 |
| 点击结果 → 高亮可见 | **< 300 ms**（已渲染页） | `evidence-map` 内存索引，零网络请求 |
| 点击结果 → 高亮可见（跨 50 页） | < 800 ms | 占位高度精确 + 预渲染上下两屏 |
| 缩放重绘 | < 200 ms | 只重绘可视页；overlay 只做乘法 |
| 结果面板 500 条 | 无卡顿 | 虚拟列表 |

## 11. UI 形态建议

- **双栏联动**：左原文、右结果，点击右侧卡片左侧定位。基础形态，必做。
- **证据指示器**：在结果卡片上显示证据数（如"证据 1/3"），点击可循环定位。
- **页面内标注气泡**：在原文页面上直接渲染该页所有结果的角标（数字），点击角标反向高亮对应卡片——这是评审人员最喜欢的形态，因为它把"结果"和"原文"在视觉上合一了。
- **复核模式**：把 `conflict` / `need_review` 的项按优先级排在最前，并**自动带出冲突的两个值**供对比裁决。
- **复核统计条**：项目顶部显示「已复核 212 / 共 276，已修正 18 条」。数字要**包含修正数**——只报复核进度、不报改了多少条，用户会怀疑系统在藏问题。
- **水印与权限**：原件属敏感资产，展示层加水印（含用户名与时间），并禁止未授权的下载与复制。
