# 04 · 解析流水线与抽取 Agent

## 1. 流水线总览

```
上传
 └─ ① 入库与哈希        sha256 去重 → document_version
 └─ ② 格式归一化        非 PDF → Gotenberg → PDF 基座
 └─ ③ 页面几何探测      记录页面尺寸 / rotation / 有无文本层，不渲染位图
 └─ ④ MinerU 解析       standard 档，整文档 → MiddleJson + ContentList
 └─ ⑤ 产物归一化落库     element（锚点生成、bbox 归一化）
 └─ ⑥ 章节树构建        title_leveling 产出 → element.level / parent_id
 └─ ⑦ 锚点文档构造      每块前缀 <<p{n}b{m}>>
 └─ ⑧ 抽取 Agent        定向字段 + 开放式条款扫描
 └─ ⑨ 三道校验         锚点存在性 / quote 一致性 / 规则冲突
 └─ ⑩ 落库与复核排队    extraction + evidence + review_task
```

## 2. 状态机

任务（`parse_run.status`）状态流转：

```
pending ──▶ converting ──▶ geometry ──▶ parsing ──▶ normalizing ──▶ extracting ──▶ validating
   │            │              │             │              │              │              │
   └────────────┴──────────────┴─────────────┴──────────────┴──────────────┴──────────────┘
                                         任意阶段失败 → failed
                                         部分产物成功 → partial
                                         用户取消     → canceled
```

**状态设计要点**

- **`converting` 与 `parsing` 分离**：转换失败（400/500）和解析失败（模型/OOM）的处置策略完全不同，混在一个状态里无法定位。
- **`partial` 必须落库**：MinerU 的 `partial` 表示部分文件成功，已完成部分的产物要保存并逐文件记录 error，不能整体丢弃。
- **每个阶段可单独重跑**：产物分层存储（[03](03-数据模型与溯源设计.md) 第 5 节），重跑 `normalizing` 不需要重新解析，重跑 `extracting` 不需要重新归一化。这是控制成本的关键。

## 3. 阶段详解

### ① 入库与哈希

- 流式计算 `sha256`，边写对象存储边算，避免大文件二次读取。
- `sha256` 命中已有 version → 直接复用，跳到最后一步。
- 记录原始文件名、MIME、大小。

### ② 格式归一化

- 已是 PDF → 直通，`is_converted = false`。
- 其他 → Gotenberg（详见 [02](../调研/02-接口调研-LibreOffice.md)）。
- 记录 `converter_version`，用于未来排查版面漂移。

### ③ 页面几何探测

用 pypdfium2 打开 PDF 基座逐页读取。**这一步不渲染任何位图**：在线预览由前端 `pdf.js` 直接渲染 PDF 基座，服务端的位图能力只用于多模态裁剪图（见 4.8 节）。

**为什么放在 MinerU 解析之前**：`page` 以 `version_id` 为键、不带 `run_id`——页面几何是版本的属性，不随重新解析变化。提前写入并按 `(version_id, page_no)` 幂等 upsert，重新解析不会重复写；解析中途失败也能先看到页数与尺寸。逐页记录：

| 字段 | 用途 |
| --- | --- |
| `width_pt` / `height_pt` | 绝对坐标诊断、页面尺寸自持（MiddleJson 无此信息） |
| `rotation` | 前端视口一致性校验 |
| `text_layer` | 判断是否扫描件，决定证据可用的高亮方式 |

### ④ MinerU 解析

- 固定 `tier=standard`；疑难件允许人工触发 `advanced`。
- **必须整文档解析**：`title_leveling` 只在 `is_full_document` 为真时生效（[01](../调研/01-接口调研-MinerU.md) 第 9 节）。
- 请求 `output_formats=["middle_json","zip"]`；MiddleJson 立即下载并原样存档。ZIP 默认不下载，仅在抽取确实需要文档内嵌图片时按需获取。
- 记录 `provider_version`、`schema_version`、`backend`。

### ⑤ 产物归一化落库

这是**最容易出错、最需要测试覆盖**的一段，规则：

1. 遍历 `pages[].blocks[]`，按顺序处理。
2. `bbox` 为 `null` → 允许，落 `NULL`，证据降级为页级定位。
3. `bbox` 原点和旋转语义未实测前不写坐标；确认后按配置转换为视觉方向（见 [03](03-数据模型与溯源设计.md) 3.2）。
4. 页眉/页脚/页码类块保留在原始 MiddleJson 存档中，不写入 `element`，也不参与锚点编号。
5. 参与编号的块 → 按页内顺序生成 `order_no`（从 1 连续递增）与 `anchor`。
6. 生成后做**锚点全集唯一性校验**，发现重复/跳号立即失败（宁可失败也不要脏数据）。

当前 Worker 已实现结构归一化和锚点写入；`MINERU_BBOX_ORIGIN` 默认 `unknown`，因此未校准坐标按 `NULL` 落库。旋转页还需将 `MINERU_BBOX_ROTATION` 实测配置为 `visual` 或 `unrotated`。

### ⑥ 章节树构建

- 优先使用 MinerU 的 `title_leveling` 结果（LLM 归并 2–6 级标题）。
- 兜底策略：按 `type=title` + 字号/加粗等启发式重建。
- 结果写入 `element.level` 与 `element.parent_id`，同时生成供前端使用的目录树。

### ⑦ 锚点文档构造

把结构化块还原成"带锚点的纯文本/Markdown"，作为 Agent 的输入：

```
<<p7b1>> ## 第二章 投标人须知
<<p7b2>> ### 2.1 投标人资格要求
<<p7b3>> 投标人须具备建筑工程施工总承包一级及以上资质，且近三年...
<<p7b4>> 2.1.1 投标人应提供有效的安全生产许可证复印件并加盖公章。
<<p7b5>> [表格] 资格审查表 | 序号 | 审查因素 | 审查标准 | ...
```

**构造规则**

- 只输出参与编号的块（页眉页脚天然不进入 Agent 视野，减少噪声与 token）。
- 表格以紧凑形式呈现（表头 + 行），或直接给 HTML 片段；**表格内不插入锚点**，整表共用一个锚点。
- 单个块过长（超过阈值）时**不切分锚点**，只在该块内部做截断并标注 `[截断]`，避免产生"半个块的锚点"导致定位歧义。

## 4. 抽取 Agent 设计

### 4.1 为什么不做事后文本匹配

| 方案 | 致命缺陷 |
| --- | --- |
| Agent 输出纯文本 → 回原文模糊匹配定位 | 同一句话在招标公告、须知前附表、合同条款多处出现，**无法消歧**；OCR 错字、全半角差异导致匹配失败；**错配比匹配失败更致命**——用户点过去发现高亮的是另一条，信任直接归零 |
| **Agent 直接输出锚点（采用）** | 定位退化为**主键查找**，命中率 100%，且无歧义 |

### 4.2 输出 Schema（强约束）

用 JSON Schema 把锚点格式锁死，`evidence` 必填且至少一项：

```json
{
  "type": "object",
  "properties": {
    "field_key": { "type": "string" },
    "value":     { "type": ["string", "number", "object", "array", "null"] },
    "value_text":{ "type": "string" },
    "quote":     { "type": "string", "description": "必须逐字复制原文，不得改写" },
    "evidence":  {
      "type": "array",
      "minItems": 1,
      "items": { "type": "string", "pattern": "^p\\d+b\\d+$" }
    },
    "confidence":{ "type": "number", "minimum": 0, "maximum": 1 },
    "not_found": { "type": "boolean" }
  },
  "required": ["field_key", "quote", "evidence", "confidence"]
}
```

三个机制性保障：

- `pattern` 校验 → **模型无法返回格式错误的锚点**。
- `minItems: 1` → **取不到证据就不许出值**，从机制上消灭幻觉字段。
- `not_found` → 给模型一个"确实没有"的合法出口，避免它为了满足必填字段而编造。

### 4.3 分块与调度

**绝不做固定 token 切分**——会把表格拦腰截断，导致跨页表格彻底失效。分块规则：

| 层级 | 规则 |
| --- | --- |
| 一级 | 按**章节**（`element.level` 的第一个层级）切分，一个章节一个 chunk |
| 二级 | 章节超长时，按**二级标题**再切，**不切断表格块** |
| 上下文 | 每个 chunk 头部注入**父章节标题路径**（`第二章 > 2.1 投标人资格要求`），否则模型无法判断当前处于哪类条款 |
| 跨页 | 带 `continues_prev = true` 的块必须与其前驱同 chunk |
| 重叠 | 相邻 chunk 重叠 1 个块，防止跨边界的条款被遗漏 |

**两遍式抽取**：

```
第一遍：章节识别 → 只处理与目标字段相关的章节（资格要求只查须知前附表与技术规范）
第二遍：字段抽取 → 在候选章节内做 schema 约束抽取（并行，按 chunk 并发）
```

**为什么两遍**：招标文件 100+ 页，全量塞给模型会同时触发上下文超限与 lost-in-the-middle；两遍式把 token 成本降一个量级，同时提高准确率。

### 4.4 两类抽取任务

| 类型 | 目标 | 策略 |
| --- | --- | --- |
| **定向字段** | 项目名称、招标编号、预算、保证金、开标时间地点、工期、付款方式、资格要求等 | 字段级 schema + 定向检索，规则优先（金额/日期/编号用正则交叉验证） |
| **开放式条款** | 废标条款、星号条款、异常风险条款 | 逐章节扫描 + 分类打标，输出同样带锚点 |

### 4.5 提示词骨架

```
你是招标文件结构化抽取助手。严格执行：

1. 只根据 <正文> 中的内容作答，禁止使用任何外部知识或推测。
2. 每个字段的 quote 必须【逐字复制】原文，禁止改写、断句、补全标点。
3. evidence 必须填写 quote 所在块的行首锚点（形如 p12b5）。
4. 如果正文中没有该字段，返回 not_found: true，不要编造，不要给证据。
5. 同一字段若在多处出现，evidence 填全部锚点，按相关性排序。

<章节路径>第二章 投标人须知 > 2.3 投标保证金</章节路径>
<正文>
<<p12b5>> 3.2 投标保证金金额为人民币伍万元整（¥50,000.00）。
<<p12b6>> 投标保证金应在投标截止时间前到账，逾期视为无效投标。
</正文>
```

**注**：`quote` 要求逐字复制不是形式主义——它是第 ⑨ 步一致性校验的输入。模型若改写，校验会失败并降置信度。

### 4.6 标段识别与适用范围

在归一化落库（第 ⑤ 步）之后插入一个轻量识别步骤：

1. 用章节树 + 关键词（"标段"、"分包"、"包"、"A标段"、"第X包"）识别标段结构，写入 `lot` 表。
2. 抽取时把标段清单作为上下文注入，要求 Agent 对每条结果标注适用范围（`lot_code` 或全文）。
3. **识别置信度低时一律降级为"全文适用"**，并在结果上打标记提示人工确认。

> 宁可保守地标成"全文适用"，也不要标错标段——标错会让业务方按错误标段的要求去应标，属于实质性错误。

### 4.7 双路投票与二次抽取

**双路投票（必开）**

| 路径 | 覆盖范围 | 说明 |
| --- | --- | --- |
| 规则路 | 金额、日期、编号、百分比 | 正则 + 单位换算；同时作为校验 ③ 的独立来源 |
| LLM 路 | 全部字段 | schema 约束抽取 |

- 两路一致 → 提升置信度，进入"批量确认"通道
- 两路不一致 → `status=conflict`，强制逐条复核，**两个值都保留**供人工裁决

**低置信二次抽取（必开）**：对置信度低于阈值的字段，换一个 chunk 边界或换一版提示词重抽一次。两次结果一致则提升置信度，仍分歧则进复核。成本约 +10~20% token，是性价比最高的一档质量提升。
> **二次抽取不算一次"尝试"**：它发生在同一次抽取任务内部，共用同一个 `machine_attempt_no`（见 [03-数据模型与溯源设计.md](03-数据模型与溯源设计.md) 第 4.6 节）。只有**用户在结果页主动触发的重跑**才递增机器解析序号。把内部重试也记成一次尝试，"首次通过率"就失去了意义——它会把"系统自己纠错成功"误算成"重跑救回来的"。

### 4.8 多模态直读（可选开关，默认关闭）

多模态抽取按需生成局部图像：用 MinerU block 的归一化 bbox 映射到对应 PDF 页，由系统从 PDF 页面自行裁剪，不依赖 MinerU ZIP 提供整页截图。

- 先用锚点筛选相关文本块与表格块，再按块 bbox 裁剪局部图；多个相关块可合并为一个区域，避免将整页送入模型。
- 裁剪图由 `render.crop_dpi` 控制清晰度，直接从 PDF 原页按 bbox 渲染——**在线预览不使用任何服务端位图**（前端 `pdf.js` 直接渲染 PDF 基座），所以这个参数只影响送进 VLM 的图像质量，不影响用户看到的原文。
- 裁剪保留少量上下文边缘，输入仍携带原有 block anchor；VLM 输出必须回指输入锚点，沿用现有证据校验。
- 只有字段类型和文档画像触发多模态时才生成裁剪图；普通文字字段不额外渲染。

| 场景 | 是否启用 | 理由 |
| --- | --- | --- |
| 表格类字段（评分办法、技术参数表） | ✅ | 表格二维关系在纯文本里会丢失 |
| 扫描件 | ✅ | 可直接核对 OCR 对应的版面区域 |
| 普通文字条款 | ❌ | 收益有限，图像 token 成本较高 |

由 `extract.strategy.multimodal` 控制（默认 `false`），按「文档画像 + 字段类型」启用，见 [08-动态配置中心.md](../质量/08-动态配置中心.md)。

### 4.9 OCR 模式与档位取值

- `ocr_mode` 三态（`auto` / `txt` / `ocr`）由配置下发到 MinerU 请求。默认 `auto` 让服务逐页判断——一本标书里数字正文页与盖章页、手签页混排时无需拆文件。
- 若评测发现扫描件召回率不足，可评估把含扫描页的文档改为强制 `ocr`。
- 档位固定 `standard`；`advanced` 仅由人工对单份文档触发（见 [01-接口调研-MinerU.md](../调研/01-接口调研-MinerU.md) 第 3 节）。

## 5. 校验与冲突（落库前的闸门）

| # | 校验 | 规则 | 失败处置 |
| --- | --- | --- | --- |
| 1 | **锚点存在性** | 每个 evidence 锚点必须能在 `element` 表中查到，且属于当前 version | 丢弃该证据；若全部丢弃 → `not_found`，不落库 |
| 2 | **quote 一致性** | 把 quote 与 `element.text` 做归一化比对（去空白、全半角统一、去除 OCR 常见混淆字符），要求匹配 | 匹配失败 → 尝试**块内子串定位**得到 `char_start/char_end`；仍失败 → `status=need_review`，`match_type=manual` |
| 3 | **规则冲突** | 金额、日期、编号类字段用正则独立提取一次，与 LLM 结果比对 | 不一致 → `status=conflict` + 创建 `review_task`，**两个值都保留供人工裁决** |

**校验 1 为什么必须做**：模型仍有可能复述出"格式合法但不存在"的锚点（比如把 `p12b5` 误写成 `p12b6`）——格式校验拦不住这种情况，只有查库能拦。

**校验 2 的双重收益**：既验证了模型没有编造，又顺带拿到了 `char_start/char_end`，供前端做**块内字符级精确高亮**（[06](06-前端展示与定位.md)）。

### 5.1 第 ④ 道：跨文件冲突检测

三道校验通过后，在**项目**维度再做一次检测（单文档流程不涉及此步）：

- 同一 `field_key` 在同一项目内的多个文件（正文 / 答疑 / 补充通知）中出现**不同值**时，建立 `extraction_conflict`。
- 按 `project_file.role` + 上传时间判定"后出文件"，把其值标记为**"可能覆盖"**。
- **不自动采信**：两个候选值并列展示，强制人工裁定，裁定结果写入 `resolved_id`。

> 为什么不自动覆盖：自动判定依赖"文件类型 + 时间先后"的正确识别，一旦误判就会**自动给出错误答案**——在投标场景下，这比让用户自己看一眼严重得多。详见 [03-数据模型与溯源设计.md](03-数据模型与溯源设计.md) 第 4.5 节。

## 6. 置信度与复核

- 置信度 = 模型自评 × 校验结果折扣：
  - 校验全通过：保留模型自评
  - 校验 2 靠子串定位成功：× 0.9
  - 存在规则冲突：强制 ≤ 0.5 且置 `conflict`
  - 证据降级为页级（bbox 为空）：× 0.8
- **复核队列排序**：`conflict` > `need_review` > 低置信度，同级别按字段重要性排序。
- **反向标注回流**：用户在原文框选修正后，产生一条 `match_type=manual` 的高质量证据。经 `review_action` 落库后，这是**回归集（`gold_item`）的唯一来源**（见 [09-评测与质量门禁.md](../质量/09-评测与质量门禁.md) 第 4 节）。

### 6.1 复核动作（事实标准的生产过程）

复核不是"看一眼点通过"，而是四选一，每次产生一条 `review_action`：

| 动作 | 含义 | 落库要求 |
| --- | --- | --- |
| `confirm` | 当前值正确 | 记录复核强度（逐条 / 批量勾选 / 抽检） |
| `correct` | 当前值错误，用户改成新值 | **必须绑定锚点**（用户在原文重新框选） |
| `supplement` | 原文有但系统没抽出来 | 人工补值 + **必须框选锚点** |
| `reject` | 该值无效（常见于锚点已失效） | 记录原因 |

**必须提供"文档中确实没有"的出口**：文件里确实没写这个字段时，用户应能标"未提及"并结束，而不是被迫编一个值——强迫填值会污染回归集。

> **为什么"人工修正必须绑锚点"是硬规则**：如果只让人改值、不让他指位置，拿到的就是"值对但出处丢了"的样本，恰好废掉这套系统唯一的核心能力。绑定锚点后有两个收益：每次修正都在生产可回归的 gold 样本；同时能独立暴露"值对了但高亮标错位置"这类仅比对值发现不了的错误。
>
> **`correct` / `supplement` 是全系统最值钱的资产**——它们是业务方在真实工作中顺手产出的、带锚点的标准答案，零额外成本（见 [09](../质量/09-评测与质量门禁.md) 第 4 节）。

### 6.2 复核强度为什么要分档

用户对高置信项"批量勾选通过"时并没有真看。若把批量通过与逐条细看混进一个分母，首次通过率会被系统性抬高。

- 复核动作必须带 `review_mode`：`item`（逐条）/ `batch`（批量勾选）/ `spot_check`（抽检）；
- 统计时分档列出，**不合并**；
- 校准靠随机抽检，且抽检数字只能用来修正 `batch` 档（见 [09](../质量/09-评测与质量门禁.md) 第 6.1 节）。

## 7. 成本与性能控制

| 手段 | 效果 |
| --- | --- |
| 复用 `sha256` 跳过重复文件 | 消除重复解析 |
| 阶段可重跑，产物分层存档 | 改抽取提示词不需要重跑 OCR |
| **单字段重跑**：只对出错字段重新调用模型，其余结果不动 | 用户修正单个字段的代价从"整份重跑"降到"一次调用" |
| **重新抽取不复用旧结果**：新尝试全量重算该字段，不做局部增量 | 避免"改了一半、留下不一致的半成品"，代价可控且结果可复现 |
| 两遍式抽取 + 章节过滤 | 相比全量投喂降低一个量级的 token |
| 定向字段并行、开放式扫描串行 | 平衡吞吐与速率限制 |
| 只对低置信度字段二次抽取（换 chunk 或换提示词） | 把预算花在真正需要的地方 |
| 多模态裁剪图按需生成 + 按区域缓存 | 图像成本只发生在多模态字段上 |
> **两条链必须分开记**：`parse_run` 记的是「文档被怎么解析的」，`extraction` 链记的是「字段被怎么抽取的」（见 [03](03-数据模型与溯源设计.md) 第 7 节）。混成一条链，就会出现「改一句提示词导致所有已确认结果被打回」的代价失控。

## 8. 失败、重试与重跑

| 失败点 | 重试策略 |
| --- | --- |
| Gotenberg 400 | **不重试**，落 `failed` 并提示业务方（文件损坏/需密码） |
| Gotenberg 500 / 503 | 指数退避重试 3 次；连续失败则扩容告警 |
| MinerU 服务重启导致 job 丢失 | 按 `sha256` 重新提交（命中文件复用，成本低） |
| MinerU `partial` | 保存已完成产物，标记缺失项，`status=partial` |
| LLM 超时/限流 | 队列内退避重试；单字段失败不影响其他字段 |
| 校验 1 全部失败 | 该字段判定为 `not_found`，不落库，不产生复核任务（属于正常的"文档中不存在"） |

### 8.1 "重试"与"重跑"不是一回事

| | 重试（retry） | 重跑（rerun） |
| --- | --- | --- |
| 触发 | 系统自动，同一动作失败后重放 | 用户或管理员主动 |
| 结果 | **不产生新结果**，成功后与首次等效 | **产生一条新尝试**（`machine_attempt_no + 1`） |
| 统计含义 | 不计入机器解析序号 | 计入机器解析序号，参与「第 k 次救回率」 |
| 幂等要求 | 必须幂等 | 不需要幂等，但要可追溯 |

> 混淆两者会直接污染指标：如果把自动重试也算成一次尝试，"首次通过率"会被上游抖动拉低，而用户看到的是"重跑救回来"——归因完全错了。

### 8.2 各类失败的处置

| 失败点 | 重试策略 |
| --- | --- |
| 用户触发**单字段重跑** | 复用解析产物，只新增一次抽取尝试；不触发上游任何阶段 |
| 用户触发**带提示重跑** | 同上，提示原文写入 `extraction.hint`，作为后续提示词优化的语料 |
| 管理员触发**重新解析** | 走完整链路（重新上传 → 解析 → 重抽），完成后把受影响实例**全部打回待复核队列顶部**，并统计失效数量写入审计 |
**死信处理**：连续失败超阈值的任务进入死信队列并告警，附带完整上下文（hash、阶段、原始错误、可复现命令），便于人工介入。
