# 09 · 评测与质量门禁

> 需求来源：准确率要求 95% 以上。
> 本文定义**指标口径、尝试模型、事实标准的来源、重跑策略、回归门禁与线上监控**。
> 本文的规则由 [08-动态配置中心.md](08-动态配置中心.md) 的变更流程强制执行。

## 0. 前置共识

招标文件**没有通用标准答案**——同一个字段，在不同文件里是否存在、值是什么、在什么位置，全都不一样。因此：

- 本设计**不假设存在预先标注的标准答案集**，也不按"先建测试集再开发"的常规软件工程套路推进。
- 事实标准从**业务方每一次真实的复核动作**中自然积累，随使用增长。
- 因此本文件的核心不是"如何一次性证明准确率达标"，而是"**如何把复核动作变成可信的数字，并让它驱动系统变好**"。

## 1. 口径钉死

| 问题 | 结论 |
| --- | --- |
| 度量单位 | **字段实例**（一个文档版本 + 一个字段 + 一个标段 = 一个实例），不是文档 |
| 度量阶段 | **尝试层**（每次尝试单独算），不是"最终值" |
| 分母 | **已复核的实例**（存在 `review_action`），不是全部实例 |
| 复核强度 | 必须分档记录（逐条 / 批量 / 抽检），**不同档不合并成一个数** |
| not_found | 不计为错误，单独统计（见 3.3） |

**为什么分母必须是"已复核实例"**：未复核的实例既没有对错，也没有事实标准。把它算进去，得到的是一个既非准确率也非召回率的混合数——只能用来骗自己。

**为什么复核强度必须分档**：用户对高置信项"批量勾选通过"时并没有真看。把批量通过和逐条细看合并进同一个分母，首次通过率会被系统性抬高。两档分开列，读者自己知道该信哪个。校准手段见第 6 节。

> **附带结论**：一个 20 字段的文档，字段级 95% 对应的**文档级全对率只有 0.95^20 ≈ 36%**。任何对外表述都必须写清单位是字段实例，否则 95% 会被理解成"每份文档都对"。

## 2. 尝试模型：机器结果逐次留档

每次机器生成结果都建立一条新尝试记录。结果值、证据和参数快照只增不改；当前指针切换到新尝试时，旧尝试与复核记录仍保留。

| trigger | 含义 | 机器解析序号 | 坐标关系 |
| --- | --- | --- | --- |
| `first` | 对当前文档版本的首次自动抽取 | 1 | 使用首次 `parse_run` |
| `hinted_rerun` | 用户提供提示后重跑抽取 | 递增 | 复用当前 `parse_run`，锚点不变 |
| `user_rerun` | 用户无提示重跑抽取 | 递增 | 复用当前 `parse_run`，锚点不变 |
| `param_rerun` | 管理员更换模型或抽取参数后重跑 | 递增 | 复用当前 `parse_run`，锚点不变 |
| `reparse` | 管理员重跑 MinerU 并重新抽取 | 递增 | 新建 `parse_run`，锚点按新结果生成 |
| `manual_edit` | 用户人工修改或补充值 | 不占机器解析序号 | 必须绑定用户选择的证据锚点；无原文时可确认 `not_found` |

尝试记录包含两个序号：`attempt_no` 表示结果时间线顺序（包括人工修正），`machine_attempt_no` 只给机器生成的结果编号。首次自动抽取为 1，之后每次自动重跑或 `reparse` 递增；`manual_edit` 的 `machine_attempt_no` 为空。因此「第 k 次解析正确率」不会把人工修正误算成模型成功。

### 2.1 抽取重跑与 MinerU 重解析

- **抽取重跑**只重新运行 Agent，复用当前 `parse_run` 与 `element`；所有输入证据锚点仍属于同一套坐标。
- **MinerU 重解析**新建 `parse_run` 和该 run 的 `element`。PDF 基座与页面几何仍属于同一 `document_version`，历史元素及证据保留，历史复核仍然有效；新 run 的结果必须重新复核。
- 锚点 `p12b5` 的唯一范围是 `parse_run`。查看历史尝试或定位证据时，接口必须带对应 `parse_run_id`，不能拿旧锚点去查当前 run。
- `field_instance.current_extraction_id` 指向当前展示结果。新 run 成功后更新该指针，旧尝试、旧确认和旧坐标不删除、不改写。

> **为何重解析后仍要重新复核**：旧确认只证明旧 run 的结果与旧证据相符。它继续作为旧尝试的历史事实，但不能替新 run 的值和锚点背书。

### 2.2 用户修正与尝试链

`correct` / `supplement` 复核动作会保留被核对的机器尝试，并新建 `trigger=manual_edit` 的结果快照。`review_action.attempt_id` 指向被核对的尝试，`result_attempt_id` 指向人工修正后的快照。人工修正作为独立结果展示和统计，不计入机器解析成功率。

## 3. 指标定义

以下通过率按**有明确复核结论的尝试**计算，待复核尝试单列，不进入分子或分母。所有指标按字段类型、项目、`trigger`、`review_mode` 与参数快照下钻。

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| **首次通过率 FPY** | `machine_attempt_no=1` 且复核动作为 `confirm` 的尝试数 ÷ 已有复核结论的 `machine_attempt_no=1` 尝试数 | 衡量首次自动抽取的复核通过情况 |
| **第 k 次救回率** | `machine_attempt_no=k` 且复核动作为 `confirm` 的尝试数 ÷ 第 k 次机器结果中已有复核结论的尝试数；按 `trigger` 分开 | 判断各次抽取重跑或 MinerU 重解析的效果 |
| **累计通过率（≤N）** | 在前 N 次机器结果中至少有一次被 `confirm` 的实例数 ÷ 前 N 次里至少有一个机器结果已复核的实例数 | 比较继续机器重跑的收益 |
| **人工兜底率** | 产生 `manual_edit` 结果的实例数 ÷ 至少有一个机器结果已复核的实例数 | 衡量需要人工改值或补充的比例 |
| **收敛机器解析次数** | 结束于机器结果被确认或人工修正的机器尝试数 | 观察耗时和调用成本 |

FPY 与第 k 次救回率都是**复核通过情况**。主动复核与主动重跑存在用户选择偏差，因此不能单独当作真实准确率。95% 是质量目标，需结合第 6 节随机抽检，并同时报告样本范围和样本量。

### 3.1 复核结论如何计数

- `confirm` 表示当前尝试正确；机器结果为 `not_found` 时，确认表示用户确认文档确实未提及，也计为通过。
- `correct`、`supplement`、`reject` 表示该机器尝试未通过。`correct` / `supplement` 会另建 `manual_edit` 结果，并带用户选定的锚点。
- 对历史机器尝试可单独做 `spot_check`；其复核结论计入被抽中的那一次尝试，不覆盖其他尝试。
- 重解析前的确认继续计入旧 `parse_run` 的历史指标；新 `parse_run` 的通过情况单独计数。

### 3.2 幻觉与溯源

| 指标 | 定义 | 门槛 |
| --- | --- | --- |
| **幻觉率** | 原文不存在该信息、机器却给出值的已复核或抽检结果比例 | 观察到的错误数为 0 |
| **证据反查 404 率** | evidence 的锚点在对应 `parse_run` 中查不到 | 0 |

幻觉与证据损坏单独报告，不让总体通过率把它们平均掉。一条无中生有的金额可能直接影响投标决策。

### 3.3 `not_found` 的处理

`not_found` 是机器给出的一个待核结果，不自动算对或算错，也不从准确率分母中排除：

- 用户确认「文档中确实没有」→ 该次机器结果通过；
- 用户用 `supplement` 补出值 → 该次机器结果未通过，产生漏抽记录和带锚点的人工结果；
- 统计时另列 `not_found` 比例及确认/补充结果，帮助判断字段定义或解析是否需要调整；
- UI 显式显示「未在本文档中找到」，提供「确认没有」与「人工补充」两个动作。

### 3.4 分组与项目展示

| 分组 | 说明 |
| --- | --- |
| 字段类型 × `machine_attempt_no` × `trigger` | 分开看首轮、Agent 重跑和 MinerU 重解析的结果 |
| 参数快照 | 比较模型、prompt、tier、`ocr_mode` 和 MinerU 版本 |
| `review_mode` | 区分逐条复核、批量确认与随机抽检 |
| 项目 | 展示本项目的首次通过率、每次重跑通过率、人工兜底率和待复核数；不做项目间考核 |

项目之间文档难度和复核深度不同，项目指标只用于了解本项目处理情况，不用于横向排名。

## 4. 事实标准从哪来

### 4.1 唯一来源：复核动作

每次复核产生一条 `review_action`，四种动作，各自产出不同性质的事实标准：

| 动作 | 含义 | 产出的事实标准 |
| --- | --- | --- |
| `confirm` | 当前值是对的 | 弱标准（批量确认时是空标准，见 6.1） |
| `correct` | 当前值是错的，用户改成新值 | **gold 值**（旧值 + 新值都保留） + **用户框选的锚点** |
| `supplement` | 原文有但系统没抽出来，人工补 | **gold 值 + 漏抽证据** |
| `reject` | 该值无效（如锚点已失效） | 无 |

**`correct` 与 `supplement` 是整套系统里最值钱的资产**：每一条都是"值 + 锚点"的完整标准答案，而且是业务方在真实工作中顺手产出的，零额外成本。

### 4.2 三条硬规则

**规则一：人工修正必须绑定锚点。**

如果只让人改值、不让他指位置，我们得到的是"值对但出处丢了"的样本——恰好毁掉这套系统唯一的核心能力。要求绑定锚点后有两个收益：一是每次改值都在生产可回归的 gold 样本；二是**独立暴露"值对了但锚点错了"这一错误类型**，这是只看值发现不了的。

**规则二：必须提供"文档中确实没有"的出口。**

文件里确实没写这个字段时，用户应能标"文档未提及"并结束，而不是被迫编一个值。强迫用户填值会污染 gold 集。

**规则三：不做盲标。**

常规评测要求标注者看不到系统结果，避免被带偏。**本设计刻意不这么做**，因为标准答案正是从"看到结果后的反应"里产生的：用户看到值才能判断对错、才能改。要防的不是"被带偏"，而是"批量确认的水分"——这由第 6 节的抽检解决。

### 4.3 回归集：自然积累的难题集

`gold_item` = 所有 `correct` / `supplement` 实例的快照（值 + 锚点 + 产出时的参数快照）。

用途：**任何 prompt / 模型 / 解析参数变更，都在回归集上回放一遍**，得到"新版本在已知难题上的通过率"。

- **不需要业务专家额外投入**——这是本设计回应"无法制定标准答案"的关键：标准不预先造，从使用里长出来。
- **回归集的通过率不代表整体准确率**：它只包含曾经错过、曾经漏过的实例，天然偏难。它的作用是**保证不退步**，不是宣称准确率。对外报准确率只能用第 6 节的抽检数字。
- 回归集与生产数据**物理隔离**，防止针对它调优。

### 4.4 冷启动

系统上线初期回归集为空。此时的策略：

1. 第一批项目的全部字段**默认进入逐条复核**——此时用户本来也会全看（新系统没人敢信），不额外增加负担；
2. 复核动作自动沉淀出第一批 `gold_item`；
3. 从第二批项目起，回归集开始对配置变更起门禁作用。

**不做预标注评测集**：它要求业务专家在系统还没产生任何价值时，先投入几十份文档的标注人力；而且标出来的分布与真实使用分布未必一致。用真实复核替代预标注，是这里唯一可持续的路径。

## 5. 三种恢复路径

发现结果不对时，按代价从低到高：

| 路径 | 何时用 | 代价 | 是否重建锚点 | 默认可见性 |
| --- | --- | --- | --- | --- |
| **① 人工修正**（主） | 绝大多数情况 | 秒级 | 否（用户重新框选） | 用户 |
| **② 带提示重跑** | 值不在预期位置、需要换 chunk 或补上下文 | 一次 LLM 调用 | 否 | 用户 |
| **③ 参数重跑** | 提示词模板整体升级、换模型 | 批量（仅回归集回放） | 否 | 管理员 |
| **④ 重新解析** | 换 MinerU 版本 / tier / ocr_mode、原文件更换 | 全量重跑 + 重新复核 | **是，全部重建** | **管理员，二次确认** |

### 5.1 为什么人工修正是主路径

**重跑不保证更准。**同参数重跑只是重新抽样，可能更差；真正有效的是带提示重跑，但用户脑子里"它应该在第三章那张表里"这种信息需要主动输入。与其让用户反复点重跑碰运气，不如让他直接改——**改一次一秒钟，而且顺带产出了 gold 样本**。

产品上要做的是把"改"做得足够顺手（见 [06](../设计/06-前端展示与定位.md) 第 8 节），而不是把"重跑"做得显眼。

### 5.2 带提示重跑必须允许填提示

不填提示的重跑等于原地重掷骰子。UI 上的提示输入框要有引导语（例：`该值可能在"投标人须知前附表"或"评标办法"章节`），并允许留空（留空即 `user_rerun`，仍作为对照数据保留）。

### 5.3 重新解析的额外约束

- 仅管理员可触发，且必须**二次确认**，确认框内列出"将失效的已确认结果数量"；
- 触发时必须填写理由，写入审计日志；
- 执行后所有受影响实例**回到待复核队列顶部**，不能被静默遗忘。

## 6. 采样偏差与准确率估计

| 数据来源 | 代表范围 | 解释方式 |
| --- | --- | --- |
| 用户主动确认、修正或重跑 | 被用户实际操作过的尝试 | 计算复核通过率和各次重跑效果；主动操作样本有选择偏差 |
| 回归集回放 | 曾经被修正或补充的难例 | 比较新旧配置在同一批已知难例上的变化；不代表整体准确率 |
| **随机抽检** | 抽样框中按规则随机选出的机器结果 | 估计该抽样框内的准确率；必须报告抽样范围、样本量和估计结果 |

### 6.1 随机抽检

- 首次准确率抽检从 `machine_attempt_no=1` 的自动结果中随机选；每次重跑或 `reparse` 的准确率抽检按对应序号和 `trigger` 单独抽样。
- 若要校准批量确认结果，可另外从 `review_mode=batch` 且动作为 `confirm` 的尝试中抽样。这个数字只代表批量确认人群，不能替代全体首次结果准确率。
- 抽检针对抽中的历史尝试及其所属 `parse_run`，用户核对其原始值和证据；抽检动作追加 `review_action`，保留原来的机器结果与历史复核。
- 初期每周抽查数十个字段实例。报表同时给出总体、字段类型、项目、机器尝试序号和触发方式的样本数；样本不足时标记「样本不足」，不宣称达到 95%。
- 抽检发现的 `correct` / `supplement` 样本进入回归集。抽检频率和样本量可按实际处理规模调整。

> 随机样本只能估计其定义的抽样框。若只抽批量确认结果，报告就应写「批量确认准确率」，不能概括为所有招标文件解析准确率。

### 6.2 参数变更回放

提示词或模型变更时，对回归集做**同文档、同字段、同条件的配对回放**，比较新旧结果在已知难例上的变化。回归集来自曾经出错的样本，因此适合发现退步，不用于宣称整体准确率。

MinerU 参数或版本变更还会改变解析块和锚点。回放时按原文 PDF 与字段 gold 值比较抽取结果，并检查新 run 证据是否能反查；旧锚点只属于旧 run。受影响的新结果需重新复核。

## 7. 门禁规则

配置发布（`config_release` 激活）必须通过：

| 类型 | 规则 | 不通过时 |
| --- | --- | --- |
| 硬门槛 | 幻觉率 = 0 | 阻止激活 |
| 硬门槛 | 证据反查 404 率 = 0 | 阻止激活 |
| 硬门槛 | **回归集通过率不得低于当前 active** | 阻止激活 |
| 硬门槛 | 回归回放未能完成（`replay_error`） | 阻止激活（没有报告就不能声称"不倒退"） |
| 硬门槛 | **变更影响清单必须逐条有人确认** | 阻止激活 |
| 软门槛 | 首次通过率较当前 active 下降 ≤ 2 个百分点 | 需 admin 二次确认 + 强制填写理由 |

### 7.1 变更影响清单

每次配置变更自动生成：

1. 本次变更涉及的字段类型；
2. 回归集中与这些字段相关的**失败项清单**（带锚点，可直接跳原文）；
3. 新增 / 删除的字段定义；
4. 预计受影响的线上实例数。

发布前必须由 `admin` **对每一条点"确认已知悉"**。每条确认单独落一行到 `config_ack`（表结构见 [08-动态配置中心.md](08-动态配置中心.md) 第 7 节），同时写 `config_audit` 的 `action=acknowledge`。

> **为什么不再用"数字过线"当唯一门禁**：回归集只包含历史难题，样本有限，数字上下浮动一两个百分点常常只是波动。真正能拦住事故的，是"有人看过这次改动会影响什么"，而不是一个阈值。数字仍然要看，但它不是最后一道闸门。

### 7.2 字段清单不做定稿

只给一份**初始字段集**，允许在复盘中随时增删：

- 新增字段走同一门禁（回归回放 + 影响清单），首次上线时回归集为空，只需人工确认影响；
- 删除字段不阻止激活，但必须提示"该字段在 N 个项目中已被复核，删除后这些结果将停止展示"；
- 字段定义的每次增删都进审计日志，与 `config_release` 关联。

## 8. 重跑按钮自动收起（数据驱动）

UI 上的"重跑"按钮不是每个字段类型都该有——有些字段重跑纯属白费用户时间。

规则（按字段类型，样本量为该类型已有复核结论的实例数；救回率取第 2 次机器结果的救回率，见 3.1）：

| 条件 | 行为 |
| --- | --- |
| 第 2 次机器结果的救回率 < 10%，且样本量 ≥ 30 | **收起「重跑」按钮**，主操作位只留「人工修正」 |
| 第 2 次机器结果的救回率 ≥ 30%，且样本量 ≥ 30 | 结果卡上提示「重跑一次通常能修好」 |
| 样本量 < 30 | 保留按钮，不做判断 |

- 阈值与样本量下限放在配置中心（L3），可改（见 [08](08-动态配置中心.md)）。
- **样本量下限的意义**：避免用 3 条样本的噪声把按钮藏掉，也避免用 3 条样本的运气把"提示重跑"喊出来。
- 按钮收起不是硬拦截：高级入口仍可重跑，只是不占主操作位。

## 9. 线上监控

| 指标 | 频率 | 说明 |
| --- | --- | --- |
| 首次通过率（分复核强度） | 每日 | 主指标 |
| 第 k 次救回率（按字段类型） | 每日 | 驱动第 8 节的按钮收起 |
| 复核修正率 | 每日 | 零额外成本的错误率代理指标 |
| 随机抽检修正率 | 每周 | **唯一的无偏准确率估计** |
| not_found 分布 | 每周 | 分布突变 = 提示词或解析出问题的早期信号 |
| 人工兜底率 | 每周 | 系统能力边界 |
| 平均收敛尝试次数 | 每周 | 成本侧 |
| 证据反查 404 率 | 实时 | **必须恒为 0** |
| bbox 为空占比 | 每日 | 解析质量退化（降级为页级定位的证据比例） |

**告警规则**

- 404 率非零 → 立即告警（溯源能力已破损，优先级高于任何准确率问题）；
- 首次通过率单周下跌超 10 个百分点 → 告警（可能是上游解析退化或模型网关异常）；
- 某字段类型 not_found 占比周环比翻倍 → 提示（先看提示词，再看解析产物）。

## 10. 数据模型

结果尝试链与事实标准的四张表（`field_instance` / `extraction` / `review_action` / `gold_item`）的**权威定义在 [03-数据模型与溯源设计.md](../设计/03-数据模型与溯源设计.md) 第 5.3 节**，此处不重复，避免两处 DDL 漂移。

本节只定义本文独有的表：

```sql
-- 回归回放（一次参数变更的回放报告）
CREATE TABLE regression_run (
    id                BIGSERIAL PRIMARY KEY,
    release_id        BIGINT      NOT NULL REFERENCES config_release(id),
    gold_total        INT         NOT NULL,
    pass_count        INT         NOT NULL,
    fail_count        INT         NOT NULL,
    baseline_rate     NUMERIC(5,4),                          -- 当前 active 的回归集通过率，用于比较
    anchor_hit        NUMERIC(5,4),
    by_field          JSONB,                                 -- 逐字段通过率
    failures          JSONB,                                 -- 失败明细（含 gold 锚点，便于跳原文）
    impact_items      JSONB,                                 -- 变更影响清单（逐条 confirmation 状态）
    started_at        TIMESTAMPTZ,
    finished_at       TIMESTAMPTZ
);
```

**为什么把 DDL 收敛到一处**：`extraction` 的列在本次设计中改动最大（双序号、`reparse`、人工快照）。同一份 DDL 抄在两个文档里，下一次改动必定漏掉其中一处，而漏掉的那处看起来仍然"权威"——这类漂移在评审时极难发现。

**`regression_run` 为什么存 `baseline_rate` 而不是每次现算**：门禁判定要能复现"当时为什么判定为退步"。当前 active 事后会被替换，届时再算基线已经变了。

**实现口径（2026-09-29）**：回放只重跑抽取（复用既有 `parse_run` 与 `element`，不重新转换/解析）；
`baseline_rate` 取当前 active 版本最近一次**已完成**回放的通过率，没有就为 `NULL`（门禁跳过不退步判定，冷启动口径）；
回放分条失败写进 `failures`（`value_mismatch` / `hallucination` / `anchor_404` / `extraction_failed`），
无法回放的 gold 记 `gold_unavailable` 且不计入通过率分母；整轮起不来记 `replay_error` 并由硬门槛 `regression_run_failed` 拦住激活。

## 11. 报告结构

### A. 回归回放报告（配置评审用）

1. 回归集规模、通过率，与当前 active 的差值
2. **逐字段回放矩阵**：哪些字段变好、哪些变差
3. 失败明细：gold 值 vs 新结果，**带锚点可直接跳原文**
4. **变更影响清单**（必须逐条确认，见 7.1）

### B. 运营统计报告（业务与管理用）

1. 首次通过率、累计通过率曲线，**分复核强度列出**
2. 第 k 次救回率（按字段类型）→ 同时输出"哪些字段该收起重跑按钮"
3. 人工兜底率与 not_found 分布
4. 抽检修正率（无偏，单独标注为"对外口径"）

### C. 项目视图（项目内展示，不做考核）

1. 该项目已复核 N 项，其中修正 M 项
2. 待复核队列（含 reparse 后被打回的项）
3. 重跑记录与收敛情况

> 第 3 项的价值容易被低估：它让业务方看到"系统在为一个项目尝试了几次"，而不是把失败藏起来。**能看见失败的系统才会被信任。**
