# 08 · 动态配置中心

> 需求来源：业务方要求「可以在页面上改配置，改完立即生效」；质量门禁要求零幻觉、回归集不退步、变更影响清单逐条确认。
> 本文定义配置的分层、生效语义、变更门禁与实现方式。

## 1. 为什么要把它当成一个独立模块

动态配置在这个系统里不是"一个设置页"，而是**质量与复现性的交汇点**：

- 配置会改变首次通过率、重跑救回率和溯源质量 → 任何变更都必须可归因、可回滚。
- 配置变更会影响结果 → 而历史结果必须可复现 → 两者冲突，只能用**快照**化解。

因此配置中心的核心不是"能改"，而是**"改了之后说得清"**。

## 2. 三层配置

| 层 | 内容 | 生效方式 | 修改权限 |
| --- | --- | --- | --- |
| **L1 运行参数** | 并发数、重试次数、各阶段超时、轮询间隔与上限、批量大小、队列优先级 | **立即生效** | `operator` |
| **L2 解析配置** | MinerU `tier`、`ocr_mode`、多模态裁剪 DPI、是否启用 `title_leveling` / `cross_page_table_cell_merge`、是否启用版面预处理（纠偏/去噪） | 新任务生效 | `admin` + 门禁 |
| **L3 抽取配置** | 字段定义、提示词、模型选择、置信度阈值、双路投票开关、多模态直读开关、复核阈值、导出列配置 | 新任务生效 | `admin` + 门禁 |

**分层依据是"生效代价"，不是"重要性"**：

- L1 改了不影响结果，可以随便改、立即生效。
- L2/L3 改了会改变结果，所以必须绑定快照与门禁。

### 2.1 L1 配置项

> **命名约定（重要）**：以下三项限的是**在途请求数**，不是 worker 进程数。命名刻意用 `max_inflight` 而非 `concurrency`，避免与 Celery 的池并发混淆——池子是固定的资源上限，配置是流量闸门。实现方式见 [10-技术选型与工程结构.md](../工程/10-技术选型与工程结构.md) 第 3.5 节。

| key | 默认 | 说明 |
| --- | --- | --- |
| `convert.max_inflight` | 4 | 同时在途的 Gotenberg 转换请求数 |
| `parse.max_inflight` | 2 | MinerU 侧同时处于 `queued` + `running` 的 job 数；建议不超过 GPU 数 × 2 |
| `extract.max_inflight` | 8 | 同时在途的 LLM 抽取请求数 |
| `dispatch.interval_seconds` | 5 | 调度器 tick 间隔；**这就是"改完多久生效"的上限** |
| `job.poll.initial_interval_ms` | 2000 | MinerU 轮询初始间隔（官方建议） |
| `job.poll.max_interval_ms` | 30000 | 轮询最大间隔（官方建议） |
| `job.poll.max_attempts` | 180 | 轮询上限，超出视为超时 |
| `job.timeout.convert_minutes` | 10 | 转换超时 |
| `job.timeout.parse_minutes` | 60 | 解析超时 |
| `job.retry.convert_500` | 3 | Gotenberg 500/503 重试次数（400 不重试） |
| `queue.priority.batch` | low | 回归回放/批量任务优先级，低于交互任务 |

### 2.2 L2 配置项

| key | 默认 | 说明 |
| --- | --- | --- |
| `mineru.tier` | `standard` | 生产固定档；`advanced` 建议仅由人工对单文档触发 |
| `mineru.ocr_mode` | `auto` | 逐页自适应；扫描件占比高时可评估改 `ocr` |
| `mineru.output_formats` | `["middle_json","zip"]` | 需要 MiddleJson 和内嵌图形 sidecar；ZIP 默认不下载，按需获取 |
| `mineru.page_range` | `all` | **必须为 all**，否则 `title_leveling` 失效 |
| `render.crop_dpi` | 300 | 多模态字段裁剪图 DPI；按 PDF 页与块 bbox 生成局部图，按需渲染并缓存（页面预览不使用服务端位图） |
| `llm_aided.title_leveling` | `true` | 章节树构建依赖它 |
| `llm_aided.cross_page_table_cell_merge` | `true` | 治跨页评分表 |
| `preprocess.deskew` | `true` | 扫描件纠偏 |
| `preprocess.denoise` | `true` | 扫描件去噪 |
| `preprocess.min_dpi` | 300 | 低于此值的扫描件先升采样 |

### 2.3 L3 配置项

| key | 默认 | 说明 |
| --- | --- | --- |
| `extract.fields` | 见字段清单 | **字段定义，变更需过门禁**（见 3 节） |
| `extract.prompt.version` | — | 提示词以版本化模板存储，不直接编辑字符串 |
| `extract.model` | 网关模型名 | 由自建网关提供 |
| `extract.confidence.auto_pass` | 由回归数据标定 | 高于此值进入「批量确认」通道 |
| `extract.confidence.review` | 由回归数据标定 | 低于此值强制逐条复核 |
| `extract.strategy.dual_route` | `true` | 规则 + LLM 双路投票 |
| `extract.strategy.second_pass` | `true` | 低置信字段二次抽取 |
| `extract.strategy.multimodal` | `false` | 多模态直读开关（仅表格类字段与扫描件生效） |
| `extract.scope.per_lot` | `true` | 按标段分组输出适用范围 |
| `extract.rerun.hide_threshold` | `0.10` | 第 2 次机器结果的救回率低于此值 → 收起「重跑」按钮（见 09 第 8 节） |
| `extract.rerun.min_sample` | `30` | 判定重跑按钮显隐的样本量下限，低于则不下结论 |

## 3. 字段定义变更的特殊规则

字段定义（`extract.fields`）**不能像其他配置一样直接保存生效**，因为它是统计与复核的基准：

- 字段清单变了 → 统计分母的构成变了 → 首次通过率这类跨版本数字失去可比性。
- 历史结果按旧字段定义产生 → 新定义下无法直接对比。

**规则**：

1. 字段定义变更保存为 **draft release**，不立即生效。
2. 必须在**回归集**（由历史 `correct` / `supplement` 动作沉淀而来）上回放，生成与当前 active release 的对比报告，同时生成**变更影响清单**。
3. 回放通过率不得低于当前 active；**影响清单必须由 `admin` 逐条确认**（见 [09-评测与质量门禁.md](09-评测与质量门禁.md) 第 7 节）。
4. 每条抽取结果记录产生它的**字段定义版本号**，跨版本的结果不做直接比较。
5. **字段清单不做定稿**：允许增删，走同一流程；删除时须提示「该字段在 N 个项目中已被复核」。

> 冷启动阶段回归集为空，此时只校验影响清单，不做数字对比——不是「不校验」，而是校验的对象换成了「人是否看过影响」。

## 4. 快照语义（复现性的唯一保障）

> 「改完立即生效」与「结果可复现」在字面上是冲突的。解法是：**立即生效的是下一个任务，不是正在跑的任务。**

```
任务创建
  └─▶ 解析当前 active release + 覆盖项
        └─▶ 写入 job_config_snapshot（完整解析后的配置，非引用）
              └─▶ parse_run.snapshot_id = snapshot.id
```

- 快照存**解析后的完整值**，不是"指向 release 的指针"——否则 release 被后续修改或回滚后，历史任务就无法解释。
- 排查质量问题时：取 snapshot + 原始 MiddleJson 存档，理论上可完全复现一次解析。
- UI 上每条结果可查看"产生它的配置版本"，这是回答"为什么这条抽错了"的起点。

## 5. 变更门禁流程

```
① 编辑（draft）
     │
② 触发回归回放  ── 低优先级队列 + 夜间窗口，与交互任务隔离
     │             回放对象 = 回归集（历史 correct / supplement 沉淀）
     │
③ 生成回归报告 + 变更影响清单
     │  报告：回归集通过率 / 逐字段差异 / 失败明细（带锚点）
     │  清单：受影响的字段类型、回归失败项、字段增删、预计影响实例数
     │
     ├─ 清单全部确认 且 回归通过率 ≥ 当前 active ──▶ ④ 激活，旧 release 归档
     │
     ├─ 首次通过率下降 > 2pp（软门槛）──▶ ④' 需 admin 二次确认 + 填写理由 ──▶ 激活并记录
     │
     └─ 清单有未确认项 / 回归通过率下降 ──▶ 阻止激活（无绕过入口）
```

**硬门槛**（任一不满足即阻止激活，**无强制绕过入口**）：

- 幻觉率 = 0
- 证据反查 404 率 = 0
- 回归集通过率 ≥ 当前 active
- 变更影响清单**逐条已确认**

**软门槛**：首次通过率相比当前 active 下降不超过 2 个百分点。

> **为什么门槛从「数字过线」改成「不退步 + 影响清单被确认」**：招标文件没有通用标准答案，回归集只包含历史难题，样本有限，数字上下浮动一两个百分点常常只是波动。真正能拦住事故的是「有人看过这次改动会影响什么」，而不是一个绝对阈值。指标的完整定义见 [09-评测与质量门禁.md](09-评测与质量门禁.md) 第 7 节。

## 6. 审计与回滚

| 能力 | 要求 |
| --- | --- |
| 变更审计 | 记录 谁 / 何时 / 改了哪个 key / 旧值 / 新值 / 理由 / 回归回放报告链接 / 影响清单确认记录 |
| 一键回滚 | 激活任一历史 release，回到当时的完整配置，**不重建配置**（避免遗漏） |
| 差异视图 | 任意两个 release 的逐项 diff |
| 影响评估 | 激活前展示变更影响清单，且必须**逐条确认**（见 [09](09-评测与质量门禁.md) 第 7.1 节） |
| 快照不可变 | `job_config_snapshot` 只写不改，禁止 UPDATE |

## 7. 数据模型

```sql
-- 配置项定义（元数据：类型、默认值、是否受门禁约束）
CREATE TABLE config_item (
    key            TEXT PRIMARY KEY,          -- 'mineru.tier'
    layer          TEXT NOT NULL,             -- L1|L2|L3
    value_type     TEXT NOT NULL,             -- int|number|bool|string|json|secret（number 是 2.3 节小数阈值的补充）
    default_value  JSONB NOT NULL,
    description    TEXT NOT NULL,
    requires_gate  BOOLEAN NOT NULL DEFAULT false,   -- 是否受回归门禁约束
    updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 配置版本（一次提交 = 一个 release）
CREATE TABLE config_release (
    id             BIGSERIAL PRIMARY KEY,
    company_id     BIGINT      NOT NULL DEFAULT 1,   -- 多租户预留；本期恒为 1
    version_no     INT         NOT NULL,
    values         JSONB       NOT NULL,             -- 全量值（非 diff），保证可独立回放
    status         TEXT        NOT NULL,             -- draft|active|archived|rolled_back
    based_on       BIGINT      REFERENCES config_release(id),
    regression_run_id BIGINT REFERENCES regression_run(id),   -- 见 09 第 10 节
    note           TEXT,
    created_by     TEXT        NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ux_release_active ON config_release (company_id) WHERE status = 'active';

-- 任务级配置快照（不可变）
CREATE TABLE job_config_snapshot (
    id           BIGSERIAL PRIMARY KEY,
    release_id   BIGINT      NOT NULL REFERENCES config_release(id),
    resolved     JSONB       NOT NULL,       -- 解析后的完整配置值
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 变更审计
CREATE TABLE config_audit (
    id          BIGSERIAL PRIMARY KEY,
    release_id  BIGINT      NOT NULL REFERENCES config_release(id),
    actor       TEXT        NOT NULL,
    action      TEXT        NOT NULL,        -- create|acknowledge|activate|rollback|force_activate
    diff        JSONB       NOT NULL,        -- {key: {old, new}}
    reason      TEXT,                        -- 强制激活时必填
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- 变更影响清单的逐条确认记录（门禁要能回答「谁在何时确认了哪一条影响」）
CREATE TABLE config_ack (
    id         BIGSERIAL PRIMARY KEY,
    release_id BIGINT      NOT NULL REFERENCES config_release(id),
    item_kind  TEXT        NOT NULL,     -- config_changed|field_def_changed|regression_failure|field_removed
    item_ref   TEXT        NOT NULL,     -- 如 'bid_bond_amount@p12b5'
    actor      TEXT        NOT NULL,
    comment    TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (release_id, item_kind, item_ref)
);
```

**`ux_release_active` 这个部分唯一索引是关键**：它从数据库层面保证同一租户**永远只有一个 active release**，杜绝并发发布导致的状态撕裂。

## 8. 即时生效的实现

```
配置写入 DB
   └─▶ 写入 Redis 缓存（key: config:active:{company_id}）
         └─▶ PUBLISH config:invalidate
               └─▶ 各 Worker 订阅失效消息，清本地缓存
```

- **Worker 取任务时读缓存**（不是启动时读），缓存 miss 回源 DB。
- 目标：配置改动后 **5 秒内**全局生效，**不需要重启任何服务**。
- 兜底：即使 pub/sub 消息丢失，缓存设 60 秒 TTL，最坏 60 秒后一致。
- **`job_config_snapshot` 在任务创建时写入**，运行中的任务不受任何配置变更影响。

**实现口径（与上面这张图的差异，写在代码里而不是留在脑子里）**：

| 事项 | 本文的写法 | 实现（`apps/api/src/tender/`） | 为什么 |
| --- | --- | --- | --- |
| 提交侧闸门 | convert/extract 用 Redis 信号量 | 统一用 `job` 表的"已派发且未结束"计数（`job.dispatched_at`，迁移 0004） | worker 崩溃或消息丢失时任务状态会自动收敛；信号量要额外一套 TTL 与回收逻辑才能达到同等可靠性 |
| 立即生效的时限 | 5 秒内全局生效 | beat 固定 5 秒唤醒 + tick 内按 `dispatch.interval_seconds` 节流；缓存写 + PUBLISH 失效，60 秒 TTL 兜底 | beat 不读配置，改成配置驱动等于让"改配置"依赖 beat 重启；ttl 仍然是最后一道兜底 |
| 回归报告缺失 | 只校验影响清单（冷启动口径） | 只认 `finished_at` 非空的报告；回放在跑或半途失败时按"报告未产出"处理 | 不能拿半份报告当"不倒退"的凭证，也不能因为回放在跑就把门禁卡死 |
| 回归回放的投递 | 低优先级队列 + 夜间窗口 | API 直接投递独立 `regression` 队列（`queue.priority.batch` 只作部署口径），不参与 beat 的差额派发 | 回放是管理员显式触发的一次性批处理，不该和交互任务抢 `extract.max_inflight` 的闸门；beat 只管四条流水线 |
| 回放失败 | 未写 | 写 `failures[].kind = replay_error`，门禁新增硬门槛 `regression_run_failed` | 模型网关不可用时"回归集不倒退"无法验证，必须拦住激活而不是静默放行 |
| 统计口径 | "必须分档记录（逐条 / 批量 / 抽检）" | `stats/fields` 顶层数字只代表逐条档，批量与抽检原样放 `by_mode` | 三档合并会把没人真看过的批量确认算进准确率 |

## 9. 权限

| 角色 | L1 | L2 | L3 |
| --- | --- | --- | --- |
| `viewer` / `reviewer` | 只读 | 只读 | 只读 |
| `operator` | **读写** | 只读 | 只读 |
| `admin` | 读写 | **读写 + 门禁** | **读写 + 门禁** |

- 所有写操作进 `config_audit`。
- 敏感值（API Key 等，`value_type = secret`）**只写不回显**，页面显示为掩码。

## 10. 多租户预留（本期不实现）

本期为单租户部署，`company_id` 恒为配置中的固定值。但：

- 只有 `config_release` 带 `company_id`（`ux_release_active` 也已按 `company_id` 分区）；`config_item` / `config_ack` / `config_audit` 通过 `release_id` 归属到公司，不重复存租户列——重复存迟早会出现「明细行与 release 归属不一致」这种无法自证的数据。
- 配置的读写**统一走"当前租户上下文"**，业务代码不得直接写死 `company_id`。

未来开启多公司时，只需让上下文能解析出不同的 `company_id`，并增加"平台默认 + 公司覆盖"的合并逻辑（覆盖项继承平台 release 的未覆盖 key），**不需要改动业务代码与表结构**。
