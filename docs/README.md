## 1. 背景与目标

### 1.1 业务背景

招标文件（标书）通常为 50–300 页的 PDF 或 Word，结构高度固定：招标公告、投标人须知前附表、评标办法、技术要求、合同条款、投标文件格式。业务方需要两类结果：

1. **结构化字段**：项目名称、招标编号、预算/最高限价、投标保证金、开标时间与地点、工期、付款方式、资格要求等。
2. **关键条款**：废标条款、星号（实质性）技术条款、评分办法明细。

### 1.2 核心诉求

只有"答案"没有"出处"的结果在招标场景下**不可用**——业务方必须能一键跳回原文核对。因此系统的第一性需求不是解析准确率，而是**溯源能力**：

> 任意一条解析结果，都必须能定位到源文档的确定位置，并在界面上高亮出来。

这条约束反过来决定了上游所有的技术选型。

### 1.3 设计目标与非目标

**目标**

- 支持 PDF（含扫描件）与 Office 系列（doc/docx/xls/xlsx/ppt/pptx）的统一入库与解析。
- 每条抽取结果携带**块级证据**：页码 + 归一化 bbox + 原文片段 + 字符区间。
- 前端支持"点击结果 → 自动翻页 → 滚动 → 高亮闪烁"的完整定位闭环。
- 支持人工修正与反向标注，形成准确率提升闭环。
- 全链路可重放：相同源文件可复现相同结果，解析产物可审计。

**非目标（本期不做）**

- 不做投标文件的生成/撰写。
- 不做多文档横向比对（后续能力，数据模型预留字段）。
- **不做单元格级高亮**——MinerU 只提供块级 bbox，见 [03](设计/03-数据模型与溯源设计.md) 的缺口说明。
- 不做在线协同编辑。

### 2.1 架构图

                             | REST + SSE
+----------------------------v-----------------------------------------+

|  |- 文档/版本管理  |- 任务编排  |- 结果与证据读写                      |
|  \- 反向标注       \- 权限与审计                                       |
+--+----------+-----------+--------------+----------------------------+
   |          |           |              |
   |          |           |              +-------------------+
   |          |           |                                  |
+--v-----+ +--v-----+ +---v------+                +----------v---------+
|Postgres| | Redis  | |  MinIO   |                |   解析 Worker      |
|业务元数据| |队列/进度| |原件/PDF/JSON|             |  (Celery/Arq)      |

### 2.2 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 前端 | Next.js + React + TypeScript | 与后端解耦，SSR 便于内网部署 |
| PDF 渲染 | `pdfjs-dist` 直接控制 | 需要自绘高亮层，`react-pdf` 封装过深不便干预坐标 |
| 服务端 PDF 引擎 | `pypdfium2` + Pillow（服务端） | 读页面几何与按 bbox 裁剪多模态局部图；**不渲染整页图**；PDFium 引擎，许可干净（见 [10](工程/10-技术选型与工程结构.md) 第 3.11 节） |
| 包管理 | **pnpm** | 项目约定 |
| 应用后端 | Python 3.12 + FastAPI | 解析生态集中在 Python；异步 IO 适合编排长任务 |
| 任务队列 | Redis + Celery（或 Arq） | 解析是分钟级长任务，必须异步 + 可重试 |
| 数据库 | PostgreSQL 16 | JSONB 存值对象与 bbox，便于审计与重放 |
| 对象存储 | MinIO（S3 兼容） | 存原件、PDF 基座、多模态裁剪图、MinerU 原始产物 |
| Office 转 PDF | **Gotenberg**（容器 + HTTP） | 见 [02](调研/02-接口调研-LibreOffice.md) |
| 文档解析 | **MinerU 4.x**（容器 + `/v1/*` HTTP） | 见 [01](调研/01-接口调研-MinerU.md) |
| 抽取模型 | OpenAI 兼容协议的自建网关 | 招标文件涉密，禁止走公网模型 |

### 2.3 服务边界

三个外部依赖全部以**黑盒 HTTP 服务**方式接入，不侵入其内部实现：

| 服务 | 协议 | 我们的封装 |
| --- | --- | --- |
| Gotenberg | `POST /forms/libreoffice/convert` | `OfficeConverter` 适配器 |
| MinerU | `POST /v1/uploads` → 上传 → 建解析任务 → 轮询 → `GET /v1/files/{id}/content` | `MineruClient` 适配器 |
| LLM 网关 | `POST /v1/chat/completions`（OpenAI 兼容） | `LlmClient` 适配器 |

**为什么坚持适配器隔离**：三者都处于快速迭代期（MinerU 4.0 相对 2.x 已是不兼容变更，官方专门维护 Migration 文档）。把版本差异锁死在适配器内部，业务代码只依赖自有领域模型，替换或升级时影响面可控。

## 4. 关键决策总览

以下为当前已确认的关键决策，开发中若需推翻任一条需重新评审。

### 4.1 产品定位与范围

| # | 决策 |
| --- | --- |
| 1 | 用户角色 = **投标方**（应标核对），非招标方视角 |
| 2 | 明确排除：评审流转/协作、SSO/OA 集成、多文档比对、加密文档、移动端、批量创建项目 |
| 3 | 溯源基准 = **系统内 PDF**；原件保留可下载，界面标注"页码以系统内 PDF 为准" |

### 4.2 质量与评测

| # | 决策 |
| --- | --- |
| 4 | 质量目标为字段实例级 **≥95%**；依据复核与随机抽检评估，报告样本量和口径，不以预制答案集作发布硬门槛 |
| 5 | `not_found` 是合法结果；用户可确认文档确实未提及，UI 必须显式显示 |
| 6 | 不预建盲标答案集；`correct` / `supplement` 复核动作沉淀带锚点的回归样本 |
| 7 | 分开统计首次通过率与每次重跑救回率；项目内展示，不做项目间排名 |
| 8 | 幻觉率与证据反查 404 率分别监控，目标均为 **0** |

### 4.3 解析链路

| # | 决策 |
| --- | --- |
| 9 | 非 PDF 一律先经 Gotenberg 转 PDF，Office 不走 MinerU 原生通道 |
| 10 | MinerU `standard` 档、**整文档解析**（`page_range: all`）、`ocr_mode` 逐页自适应；`advanced` 仅人工触发 |
| 11 | `output_formats = ["middle_json","zip"]`；不请求 markdown |
| 12 | 招标包：zip/多文件 → 自动解包 → 归为一个项目 → 按扩展名分流（可解析的解析，图纸只存） |
| 13 | **不做增量展示**（实测 P95 >10 分钟时重新评估）；`partial` 显式标注缺失项 |

### 4.4 抽取

| # | 决策 |
| --- | --- |
| 14 | **锚点驱动**——Agent 直接输出锚点，绝不做事后文本匹配 |
| 15 | 字段类型 = 单值 + 多值列表（**每项独立锚点**）；表格字段返回整表锚点 + 行数组，不承诺单元格级定位 |
| 16 | 多标段：结果带**适用范围**维度；识别不准时降级为全文适用 |
| 17 | **双路投票 + 低置信二次抽取必做**；多模态直读为开关，仅对表格类字段与扫描件启用 |
| 18 | 跨文件覆盖：**只标注冲突，不自动覆盖** |

### 4.5 结果与复核

| # | 决策 |
| --- | --- |
| 19 | 分级复核：高置信项可批量确认，低置信/冲突项逐条复核；复核方式分别记账 |
| 20 | 导出 **Excel**（字段/值/标段/页码/原文片段/置信度/尝试次数/复核状态），不做 Word |
| 21 | 每条结果明确显示待复核、已确认或已修正；未复核结果不标为正确 |

### 4.6 配置中心

| # | 决策 |
| --- | --- |
| 22 | 三层配置（L1 运行参数 / L2 解析配置 / L3 抽取配置），按生效代价分级 |
| 23 | 生效语义 = **新任务生效 + 任务创建时快照配置**（保障可复现） |
| 24 | 配置变更需回放已确认的纠错样本；回归不得退步，影响清单须逐条确认 |
| 25 | 配置审计 + 一键回滚；任务快照保证复现，动态并发配置 5 秒内生效 |
| 26 | 作用域一期全局，结构预留"按文档画像覆盖"；L1 归 `operator`，L2/L3 归 `admin` |

### 4.7 数据模型与权限

| # | 决策 |
| --- | --- |
| 27 | `project` 是**可变容器**：文件可随时增删改；改元数据就地更新 / 换内容 = 新版本 + 替代关系 / 删除 = 软删 + 结果标记"来源已移除" |
| 28 | 四角色（`viewer`/`reviewer`/`operator`/`admin`）；**下载原件限 `reviewer` 及以上**，全部进审计日志；四类审计日志留存 ≥180 天 |

### 4.8 复核、尝试与外部调用

| # | 决策 |
| --- | --- |
| 29 | 字段结果按尝试追加记录；首次自动抽取、每次重跑和人工修正均可追溯 |
| 30 | 统计首次通过率、逐次救回率、累计通过率与人工兜底率；按字段类型、触发方式和复核方式拆分 |
| 31 | 人工修正/补充必须关联用户选定的原文锚点；`not_found` 由用户确认是否确实未提及 |
| 32 | 重跑抽取复用既有坐标；MinerU 重新解析由管理员触发，旧锚点失效后相关结果重新复核 |
| 33 | 回归样本从已确认的人工修正/补充中积累；回归结果用于版本对比，不代表整体准确率 |
| 34 | 每周随机抽检字段实例，校准批量确认结果；报告抽样范围、样本量和估计结果 |
| 35 | 配置发布需满足零幻觉、零证据 404、回归不退步和变更影响清单逐条确认 |
| 36 | Gotenberg 先用同步 HTTP 调用并限制在途请求；P95 超过 2 分钟时再评估 webhook |
| 37 | MinerU ZIP 默认不下载；多模态图像按块 bbox 从 PDF 基座裁剪（按需生成、按区域复用），裁剪 DPI 独立配置 |

### 4.9 架构约定

| # | 决策 |
| --- | --- |
| 38 | 服务端 PDF 引擎用 **pypdfium2**（Apache-2.0 / BSD-3），排除 AGPL-3.0 的 PyMuPDF——内网 Web 服务会触发 AGPL 的网络条款 |
| 39 | 四条溯源不变量（锚点唯一、bbox 契约、证据非空、人工修正必须带锚点）写成**可执行断言**，在写入前拦截，不做文档约定 |
| 40 | `api` 与 `worker` **不互相依赖**，只通过数据库与队列通信，保证可独立扩容与独立重启（import-linter 在 CI 强制） |
| 41 | 队列消息只传 `snapshot_id`，不传配置值；worker 禁止直接读 active release，否则可复现性被绕过 |
| 42 | **服务端不渲染整页图、不生成缩略图**：在线预览由前端 `pdfjs-dist` 直接渲染 PDF 基座（Range 流式加载），定位靠归一化 bbox 现场换算；页码导航用页码跳转 + 章节树 |
| 43 | 部署参数（数据库地址、外部服务地址、密钥）与业务参数**分开**：前者走「环境变量 > `apps/api/.env` > 代码默认值」，取值规则只在 `core/settings.py` 一处；后者走配置中心，运行期即时生效。分界线是「重启前就定下来」还是「运行期随时改」 |
