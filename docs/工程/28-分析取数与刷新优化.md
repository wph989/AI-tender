# 28 · 分析取数与刷新优化

更新日期：2026-11-25。六项优化与验收已完成。

## 当前实现

- 最终提交按完整引文指纹去重解析，同一提交仍逐条检查本项目引用；工具保存与正式发布继续核验权限、版本和租约。
- 工具收尾只计算一次进度，事件使用已保存进度的浅拷贝，避免事件回调修改工作区。
- 质量问题为空时跳过冻结来源查询；正文引文仍实时核验，有质量问题才检查其可见性。
- 报告展示由既有仓储的 `report_view` 和 `report_module_summaries` 读取所需字段。Skill和正文JSON通过 `jsonb_to_record` 一次解析，避免逐字段重复解压；Worker、补跑与发布继续使用完整报告和模块读取。
- 分析页通过 `POST /analysis/reports/{report_id}/records` 合并读取全部专题。服务端先核验当前权限与版本，再按完整可见响应生成专题版本；相同版本省略正文，变化时返回完整专题数据。
- 删除 `DraftWorkspace.dependencies/signature/review_current` 的无生产消费者包装，内部计算保留；测试改用生产实际使用的 `current_reviews()`。

合并读取与单专题读取共用 `_module_records` 投影。同次合并请求复用完整引文解析和冻结输入核验，缓存不跨请求；前端只在报告与模块身份一致、上次读取成功且服务端返回相同版本时复用正文。最新执行进度仍取报告详情，所有专题的条目、总计数和关系继续保留。

单专题回执错误或正文绑定错误清除当前专题正文与版本，整批核验失败清除全部正文与版本；下一次成功读取重新获取完整内容。请求取消后不覆盖新报告。

## 实测收益

真实草稿工作区与用例的离线样本：

| 场景 | 优化前 | 当前 |
| --- | ---: | ---: |
| 40条草稿共享同一完整引文，最终提交解析次数 | 40 | 1 |
| 40条已自查草稿，工具收尾自查判断次数 | 80 | 40 |
| 空质量问题的全来源查询次数 | 1 | 0 |
| 13个专题每轮状态、详情和正文HTTP请求 | 15 | 3 |
| 13个专题、每专题40条记录的未变化正文刷新响应 | 345,827字节 | 1,632字节 |

独立原生PostgreSQL样本使用当前108个Skill文件和13个专题，每专题160条长记录。各取数预热后读取7次，计SQL往返与解码的中位耗时，字节数为取回对象的UTF-8 JSON大小：

| 仓储取数 | 完整读取 | 窄字段读取 |
| --- | ---: | ---: |
| 报告概览 | 246,240字节 / 3.818 ms | 1,555字节 / 2.142 ms |
| 报告及单专题输出声明 | 246,240字节 / 3.818 ms | 2,673字节 / 1.905 ms |
| 报告及13份输出声明 | 246,240字节 / 3.818 ms | 14,986字节 / 2.014 ms |
| 13个专题的状态与质量摘要 | 11,226,260字节 / 57.327 ms | 4,478字节 / 12.116 ms |

测量覆盖本机上述样本的取数成本。每轮权限核验仍会执行，未变化正文的优化收益来自减少重复解析、数据库传输、HTTP请求、响应传输和前端投影。
