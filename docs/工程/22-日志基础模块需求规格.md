# 日志基础模块需求规格

本文档是**需求规格**，描述一个后端日志基础模块要做什么、达到什么标准、如何验收，供实现方（人或 AI）在新项目中落地，不绑定任何已有实现、语言或框架。落地时接口命名可以替换，但文中"必须"级语义应保持不变。

## 1. 目标与范围

为下列三类进程提供统一日志能力：

- HTTP 接口进程（Web API）；
- 后台任务进程（异步任务消费者）；
- 定时调度进程。

要求：

1. **统一输出**：三类进程的日志格式、字段、脱敏、限长、文件管理行为一致，由同一套配置控制。
2. **统一关联**：请求与任务共享一组关联字段（见 4.5），可跨进程关联同一业务动作。
3. **安全默认**：脱敏和长度限制默认开启，敏感信息不因"忘记过滤"而落盘。
4. **故障隔离**：日志系统自身的任何故障（磁盘满、无权限、锁超时、格式化异常）不得中断或影响业务。
5. **框架解耦**：日志基础模块不依赖 Web 框架、任务队列或数据库；框架适配放在模块外围。

对应地，以下为非目标（见第 9 节详述）：不做分布式全链路追踪、不做日志查询平台/数据库日志表、不采集请求与响应正文、不保证断电零丢失。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 业务日志 | 应用代码主动输出的结构化事件记录 |
| 标准库日志 | 第三方库与框架经标准 logging 机制发出的日志 |
| 访问摘要 | 每个 HTTP 请求（受采样规则约束）输出的一条请求级记录 |
| 错误详情文件 | 记录完整异常堆栈的纯文本文件，与普通结构化文件分离 |
| 关联字段 | 用于跨进程、跨记录串联同一业务动作的 ID 字段 |

## 3. 配置需求

配置来自环境变量，其次读取部署目录下的 `.env` 文件；同名时环境变量优先。空字符串视为"未配置"。变更配置后需重启对应进程生效。配置必须独立于数据库（数据库不可用时仍能记录运行日志）。

| 配置键 | 默认值 | 校验规则 | 语义 |
| --- | --- | --- | --- |
| `LOG_LEVEL` | `INFO` | DEBUG / INFO / WARNING / ERROR / CRITICAL | 统一级别阈值，作用于所有输出目标 |
| `LOG_OUTPUT` | `both` | stdout / file / both | 输出目标：标准输出、文件、或两者 |
| `LOG_CONSOLE_FORMAT` | `text` | text / json | 控制台格式；普通文件固定 JSONL，错误文件固定纯文本 |
| `LOG_DIR` | `logs` | 相对路径按部署根解析，支持绝对路径 | 日志根目录，按服务名分子目录 |
| `LOG_RETENTION_DAYS` | `30` | 正整数 | 文件保留的自然日数，**包含当天** |
| `LOG_TIMEZONE` | `Asia/Singapore` | 合法 IANA 时区名 | 文件日期与分片切换采用的时区 |
| `LOG_MAX_FILE_BYTES` | `104857600`（100 MiB） | 整数，最小 65536 | 单个文件的大小上限 |
| `LOG_CLEANUP_INTERVAL_SECONDS` | `3600` | 正整数 | 后台过期清理检查周期 |

补充要求：

- 非法配置必须在启动时以明确错误终止，不允许静默降级为默认值。
- 日志记录的时间戳固定采用北京时间（UTC+8），ISO 8601 格式、毫秒精度、带 `+08:00` 偏移，例如 `2026-10-18T00:00:01.123+08:00`；文件日期则采用 `LOG_TIMEZONE`（默认同为 UTC+8）。
- 在不自带 IANA 时区库的平台上（如 Windows 无时区数据库），模块必须自带时区数据来源，不依赖系统安装。

## 4. 记录与字段规格

### 4.1 记录模型

- 每条记录的 `event` 是短名称字符串（点分小写，如 `task.start`），表示"发生了什么"，不用自然语言句子。
- 公共字段仅四个：`timestamp`、`level`、`event`、`location`。不为每条记录自动附加进程名、进程号、logger 名等噪音字段；"哪个服务"由文件目录或部署方式区分。
- `level` 输出为 `debug/info/warn/error/critical`；警告在控制台、JSONL与文本错误文件中统一显示为 `warn`。内部级别与调用方法保持 `WARNING`／`warning()`，配置仍使用 `LOG_LEVEL=WARNING`，不改变过滤和错误文件分流。
- 其余业务字段由调用方以键值对提供。
- 字段输出顺序：固定前缀字段按序在前（timestamp → level → event → location → request_id → task_id → job_id → report_id → run_id → module_key → invocation_id），其余字段按名称排序，异常堆栈放最后。
- 顶层 `None` 与空字符串省略；`0` 和 `False` 是有业务含义的值，必须保留。
- 指定事件的默认值例外：`module.start` 省略 `resumed=false`，`review.end` 省略 `needs_correction=false`，为 true 时必须保留。`review.start/end/fail`、`record.reject` 省略固定的 `agent_phase=verification`，`model.call` 仍保留阶段。报告共用的来源数量只在 `report.start` 输出，无已核实成果的失败原因显式写入脱敏后的 `error`，不重复同一 `reason`，避免500字符自动摘要截断后备模型的长原因；取消与部分成果原因继续保留。`skill.load` 保持 INFO，工具参数继续按既有脱敏和长度规则记录。
- 输出编码：普通文件 JSONL（一行一条，可含换行的堆栈经转义）；控制台按配置 text 或 json；所有输出明确使用 UTF-8。

### 4.2 `location` 定位

- 格式为「真实代码路径:行号」，能定位到具体代码行。
- 项目自身代码省略部署目录前缀，只保留包内相对路径；第三方来源保留原路径。
- 业务日志与标准库日志指向日志调用行。
- 访问摘要指向匹配到的接口定义处：有装饰器时从定义前的第一个装饰器行开始；必须支持同步函数、异步函数及使用通用包装器（保持原函数元信息的 wrapper）的接口。
- 没有匹配到任何端点的请求（404 等）回退到中间件自身的日志调用处。

### 4.3 事件字典（语义要求）

以下事件名是实现建议值，可替换，但语义必须覆盖：

| 事件 | 触发时机 | 必含字段 |
| --- | --- | --- |
| `http` / `http.abort` | 请求正常完成 / 中断（断连、取消） | 路由模板、方法、状态码、耗时 |
| `task.start/end/fail/retry` | 任务生命周期 | 任务短名（仅开始/失败/重试时提供）、重试次数（非 0 才输出）或耗时 |
| `task.stop` | 任务以非成功非失败非重试状态结束 | 状态、耗时 |
| `report.start/end/abort`、`module.start/end/fail/cancel` | 报告/模块（专题）生命周期 | 耗时；开始时可带项目与范围标识 |
| `model.call` | 一次模型路由调用整体结束时记录一次 | 实际使用的模型名、累计输入/输出 token 数、总耗时、状态、错误摘要 |
| `tool.call` | 每个 Agent 工具调用完成时记录一次 | 工具名、脱敏后的参数、耗时、状态 |

语义约束：

- 访问摘要不得读取请求体、查询字符串或鉴权头。
- 任务日志不得采集任务的参数、关键字参数或返回值正文。
- 模型调用的每次供应商请求、重试与切换写入调用账本（业务数据），运行日志不重复输出全过程事件。
- 失败/重试后不再补记一条"正常结束"，避免被误读为成功；"正常结束"仅表示函数返回，不表示业务成功。

### 4.4 关联字段

- 字段集合：`request_id`、`task_id`、`job_id`、`report_id`、`run_id`、`module_key`、`invocation_id`。
- 有来源才提供，缺失不伪造。
- **自动生成的 ID 必须短**：固定 12 位 URL 安全字符（base64url 字符集，约 72 位随机熵）；请求 ID 与任务 ID 共用同一生成逻辑、同规格。**不得使用 UUID 或其他长格式标识**——ID 会出现在每条日志、消息头与响应头中，长度必须可控、可人工比对。
- **外部传入 ID 的合法性与长度上限**：请求头或任务消息头传入的 ID 只有通过校验才被采纳——字符集限于 `[A-Za-z0-9_.:-]`、长度 1–128。超出上限或含其他字符即非法：请求头非法时改用自动生成的短 ID 并在响应头回传；消息头中的非法字段直接丢弃、不绑定，不用默认值伪造。校验同时防止超长或可疑值进入每一条日志。
- 合法 ID 一律原样沿用、不截短（截短会破坏跨服务关联）；上下文绑定同样只接受合法 ID 或整数。
- HTTP 入口：读取请求头 `X-Request-ID`，合法则沿用；缺失或非法则生成并在响应中回传，供客户端与后续请求关联。
- 任务发布：把发布时刻已有的关联字段随消息头传递（不含子任务自身的 task_id）；任务执行前绑定、执行结束后恢复。嵌套调用（含同步内联执行的测试模式）与线程池并发互不串号，子任务始终使用自己的 `task_id`。
- 业务实体 ID（job、report 等）由业务系统生成，本模块只做合法性判断与透传，不改造、不截断。

### 4.5 上下文管理

- 提供"绑定关联字段"的上下文管理器：支持嵌套，退出时恢复外层值；线程与协程之间隔离。
- 另提供读取当前上下文与清空上下文的操作，供消息发布等场景读取。

## 5. 脱敏与内容限制（安全需求）

### 5.1 结构化字段过滤

- 字典键名归一化（去除非字母数字并小写）后，命中敏感名单（如 authorization、cookie、api key、password、secret、token、credential 及以 password/apikey/secretkey/accesstoken 结尾的键）时，值替换为固定占位符。
- 默认屏蔽：请求/响应正文、prompt、messages、文档正文、任务参数与结果、任务 kwargs、result 类字段。
- 字段名本身也是格式契约，不得被文本级替换改写为其他名字。

### 5.2 文本级清洗

- 启动时收集环境中的已知凭证（如对象存储、第三方 API、加密主密钥等），在文本中做全文替换。
- 通用规则：`Bearer`/`Basic` 认证串、常见 `key=value` 形式的密钥字段、连接串中的 `user:password@` 凭证，全部替换为占位符。
- 不要求识别任意自由文本中的未知凭证；因此需求上同时约束"不要主动记录原文或完整请求对象"。

### 5.3 对象与数值

- 未知类型对象只输出类型名，禁止调用其字符串化或 `repr`（可能触发属性访问、再次抛错或泄漏正文）。
- 非有限浮点数转为字符串输出。

### 5.4 长度与深度限制

- 单字段最长约 16000 字符；嵌套深度 ≤8 层；容器元素 ≤100 项；超限另行标记（如 `[条目已截断]`、`truncated: true`）。
- 单条记录按最终编码（UTF-8，含换行）不超过 64 KiB；超限必须明确标记，不允许截出半条 JSON。
- 长堆栈保留首尾（约各 1/4 或各 7900 字符），确保保留最终异常原因；截断处显式标记。
- 超限处理顺序：先删除业务字段、保留事件/位置/关联字段/堆栈；若保留字段仍超限，继续缩短当前最大的字段，循环到达标为止；不能只按字符数估算或直接丢弃业务字段来判断"已满足限制"。
- 最终限长校验以真实字节数为准（文本格式渲染结果按 UTF-8 字节数校验）。

### 5.5 异常处理边界

- 已知业务异常：只格式化业务异常自身堆栈，不回放底层 SDK 的原始异常链（链上可能带供应商密钥或原始请求）。
- 未知异常：保留完整异常链，但统一经过脱敏与限长。
- 保留异常类型与堆栈，不采局部变量。

## 6. 文件生命周期

### 6.1 目录与命名

- 目录结构：`LOG_DIR/<服务名>/`，服务名限 `[a-z][a-z0-9_-]{0,31}`。
- 普通文件：`日期.分片序号.jsonl`；错误详情文件：`日期.分片序号.error.log`；序号为 3 位起步的数字，超 999 自然进位。
- 日期按 `LOG_TIMEZONE` 计算；文件名不包含启动时间、PID 或随机标识。
- 同一服务同一天多次启动、多进程运行均**追加**当天最新分片；重启时扫描目录取数字最大的既有分片继续，不覆盖已有内容，也不回填较早分片。
- 出现下列任一情况时切换到下一分片（在锁内重新判断实际大小，防止多进程同时轮转）：下一条记录会超出 `LOG_MAX_FILE_BYTES`；文件尾部没有换行（写入中断残留的半行/半个字符）。残缺尾行保留原样供排查，不拼接、不修补。
- 跨天第一条记录写入新日期的 001 分片。

### 6.2 进程间安全

- 每个服务目录内使用固定锁文件（不随清理删除、不随重启改名）。
- 写入、读取实际大小、轮转决策、清理必须在同一把操作系统级文件锁内执行；多条记录、整段堆栈不得交错。
- 锁等待超时（建议 5 秒）按"写入失败"进入回退路径，不无限阻塞业务。
- 每条记录写完立即关闭文件句柄，不保留跨记录的长生命周期句柄（兼容 Windows 清理与进程复制场景）。
- 不引入应用级日志缓冲队列；每条记录写入后 flush。flush 不等于 fsync——断电或进程被强杀时允许丢失，验收预期以此为准。

### 6.3 错误详情文件

- 写入对象：ERROR/CRITICAL 级别的记录，以及**任何带堆栈的记录**（包括容错分支以 WARNING 继续执行但附带了异常堆栈的情况）。
- 格式：UTF-8 纯文本，含完整堆栈。
- 普通结构化文件与控制台只保留摘要和简短错误信息（如最后一行异常信息），不重复输出完整堆栈。
- 两个文件各自独立创建与分片，序号不要求一一对应；通过时间、事件名与关联 ID 互查。
- 无对应记录时不创建空文件。
- `LOG_OUTPUT=stdout` 时不创建任何文件，此时控制台输出必须保留堆栈，避免容器场景丢失诊断信息。

### 6.4 过期清理

- 启动时执行一次，之后按 `LOG_CLEANUP_INTERVAL_SECONDS` 周期执行；独立于日志写入，没有新日志也要清理闲置服务。
- 判断依据为文件名所属日期：保留"今天往前数 `LOG_RETENTION_DAYS` 个自然日（含当天）"，更早删除。
- 只删除当前服务目录下、符合本模块完整命名规则的普通文件：不递归、不删符号链接、不删其他文件、不以文件修改时间推测日期。
- 当天存在多个分片不影响保留天数计算。
- 删除失败（文件被占用等）保留文件、下次重试；多实例并发清理允许先删者胜出。
- 全部服务停止期间没有清理进程，下次启动补清；运行期允许存在至多一个检查周期的清理延迟。

### 6.5 故障回退

- 文件创建、写入、清理任一环节失败：以固定错误事件限频上报（建议同一事件 60 秒内只报一次），写失败的记录（已脱敏、已限长）回退到标准错误输出。
- 标准流写入失败同样以固定事件限频上报。
- 记录格式化失败时输出固定的最小兜底 JSON，不递归触发新日志。
- 任何日志故障都不得抛出到业务代码、不得终止业务。

## 7. 接入需求

### 7.1 公共接口（建议命名，可替换）

| 接口 | 语义 |
| --- | --- |
| `get_logger(name)` | 获取业务 logger，支持 `debug/info/warning/error/exception(event, **fields)` |
| `configure_logging(service, options=None)` | 装配日志；同参数重复调用幂等；参数变化先关闭旧资源再重建；服务名校验 |
| `shutdown_logging()` | 释放清理线程与文件句柄；注册到进程退出钩子 |
| `bind_context(**ids)` | 上下文管理器，绑定关联字段，支持嵌套与恢复 |
| `get_context()` / `clear_context()` | 读取（仅返回合法关联字段）/ 清空当前上下文 |
| `new_short_id()` | 生成 12 位 URL 安全随机 ID，供请求与任务共用 |

### 7.2 标准库日志兼容

- 标准库 logging 与业务日志共用同一格式、脱敏与限长管线；第三方库的日志记录（无结构化字段）必须同样被脱敏和限长。
- 对指定的框架 logger（Web 服务器、任务队列等）：清空其自带 handler、改为向上传播到统一管线；关闭由本模块替代的重复输出（如框架自带的访问日志、已记录异常的重复堆栈打印）。
- 已知噪音库（HTTP 客户端、数据库引擎、云 SDK 等）固定为 WARNING 档，其 INFO 及以下不进入统一日志。
- 只接管明确列出的框架 logger，不移除测试框架或宿主应用自己的根处理器。

### 7.3 进程接入

- 每个进程启动时初始化一次：API 进程用服务名 `api`，任务进程按角色（worker / beat 等）区分，日志目录按服务分。
- 任务进程：连接发布信号（把上下文写入消息头）与执行前/后、失败、重试信号（绑定、记录、恢复）。
- 装配失败时（应用初始化异常）：先以固定事件记录摘要与堆栈（摘要入普通文件、堆栈入错误详情文件），再让进程失败退出；启动脚本可从普通文件读取摘要定位问题。

## 8. 访问日志与限频需求

- **标记范围：前端存在定时轮询调用链的只读接口必须逐个加限流装饰器**，例如任务进度、项目/文件处理进度、分析报告与专题记录、知识库入库进度、问答进度、模型设置读取等轮询接口。清单随前端轮询链路变化同步维护，新增轮询接口时必须补标记。
- 禁止两种做法：把中间件改成"全部 GET 限频"或"全部接口限频"默认生效（吞掉业务接口的正常访问摘要）；漏标轮询接口（每秒一条、长任务期间淹没日志）。
- 已标记清单必须可校验：用自动化测试枚举各路由的实际标记并与预期清单比对，防止范围扩成全局或点漏。
- 仅对**显式标记**的接口生效（轮询类只读接口）；默认窗口 60 秒，标记时可覆盖（如 15 秒），传 0 关闭。默认值写在代码中，不进入环境配置。
- 采样分组键 = HTTP 方法 + 路由模板 + 状态码；路径参数与查询参数不参与分组，避免同一轮询接口因参数不同反复输出。
- 窗口语义：首条立即记录，窗口从该次记录开始计时；窗口内重复的成功请求不输出，且不延长窗口；到期后的首条再次记录。
- 4xx、5xx、异常、断流、取消**不受限频影响**，始终逐条记录，也不重置成功分组的窗口。
- 已发出 200 响应头后中断的请求：保留实际状态码，以 ERROR 级别按中断事件逐条记录。
- 窗口使用单调时钟；每个应用实例独立计时，重启后重新开始；线程间检查与更新互斥。
- 不同窗口长度的接口使用独立缓存，互不提前淘汰；过期分组的清理不得淘汰仍在窗口内的分组；无新请求时不启动额外清理任务。
- 限频只决定"当前摘要是否输出"，不统计被压制的数量，日志不作为请求总量或审计凭证。
- 标记方式必须不改变框架对接口的处理：不包装业务函数，不影响签名解析、依赖注入与同步/异步调度。实现方式建议：装饰器只给原函数附加标记属性，中间件在响应结束后读取实际匹配端点上的标记决定是否记录。

## 9. 非目标

1. 不做完整分布式追踪：只传播实际存在的关联 ID，不虚构链路；跨进程链路在缺少贯穿 ID 的环节明确断开。
2. 不提供日志查询页面、数据库日志表、指标或追踪平台；运行日志与业务侧调用账本、审计记录各自独立。
3. 不采集：请求/响应正文、查询字符串、鉴权头、任务参数与结果、模型请求正文、文档内容。
4. 不引入日志缓冲队列，不承诺 fsync 级零丢失。
5. 不按文件修改时间做清理，不自动合并历史遗留的旧命名文件（旧文件保持原名并参与清理即可）。

## 10. 验收清单

| 类别 | 验收项 |
| --- | --- |
| 时区 | 跨 UTC 日界时时间戳与文件日期正确（时间戳固定 UTC+8，文件日期用配置时区） |
| 分片 | 按大小轮转；残缺尾行隔离到旧分片；重启取最大序号追加不覆盖；跨天开新 001 |
| 锁 | 多进程并发写入不交错；单条记录与整段堆栈不拆分；锁超时走回退路径 |
| 清理 | 保留天数含当天；对旧命名/无关文件不动；删除失败可重试；空闲时仍周期清理 |
| 脱敏 | 嵌套结构敏感键替换；文本凭证替换；未知对象只出类型名 |
| 限长 | 单字段/嵌套/容器/单条 64 KiB 全部在真实字节层面生效；长堆栈保留首尾与最终原因；主字段优先保留 |
| 错误文件 | ERROR 与带堆栈的 WARNING 均入错误文件；普通文件只留摘要；stdout 模式保留堆栈 |
| 回退 | 不可写目录、格式化异常、标准流失败：不崩溃、回退到 stderr、限频告警 |
| 访问摘要 | 分组按路由模板；首条立记与窗口不延长；异常/断流/4xx/5xx 不受限频；未标记接口逐条记录；不同窗口长度独立；轮询接口标记清单经自动化测试校验（既无全局限频、也无漏标） |
| 定位 | 访问摘要指向接口定义处（含装饰器首行）；未匹配请求回退中间件；业务日志指向调用行 |
| 关联 | 自动生成 ID 为 12 位短格式且非 UUID；外部 ID 超长/非法时生成侧替换、消息头侧丢弃，合法值不截断；请求 ID 回传；任务上下文经消息头传播、嵌套与并发不串号；子任务用自身 ID |
| 集成 | API / 任务 / 调度三类进程加载同一配置，字段与格式一致；无匹配记录时不产生空文件 |
