## 1. 架构总览

### 1.1 同一代码库，三个进程角色

后端采用**按业务组织的模块化单体，配合异步 Worker**：API、Worker、Beat 共用 tender 包、业务模型和数据库，但以不同进程运行。业务目录目前没有各自独立的数据库、部署单元或网络接口，因此不属于按业务拆分的微服务。

| 进程角色 | 实际入口 | 负责什么 |
| --- | --- | --- |
| API | tender.api.app:app | HTTP 请求、参数校验、调用用例、结果查询、文件传输与任务 SSE |
| Worker | tender.worker.celery_app | 消费队列，执行转换、解析、知识索引、问答和专题分析，也执行派发任务 |
| Beat | 同一个 Celery app 的 beat 命令 | 按时间发送派发任务消息，由 Worker 执行数据库扫描与后续投递 |

**Beat 负责定时发消息，派发任务实际在 Worker 中执行。** 源码文件叫 worker/dispatch.py，并不意味着 Beat 进程直接运行其中的查询。

~~~mermaid
flowchart LR
    U["浏览器"] -->|"HTTP / SSE"| API["API 进程"]
    B["Beat 进程"] -->|"定时任务消息"| R["Redis：队列 / 配置缓存"]
    R -->|"消费消息"| W["Worker 进程"]
    API --> PG["PostgreSQL：业务状态 / 任务 / 运行记录"]
    W --> PG
    API --> S3["S3 / MinIO：文件与解析产物"]
    W --> S3
    API -->|"配置读取等"| R
    W -->|"继续投递 / 轮询任务"| R
    W --> DOC["Gotenberg / MinerU"]
    W --> MODEL["模型服务"]
    API -->|"模型测试 / 检索等用例"| MODEL
~~~

图中连线表示进程之间的运行关系，省略了进程内部的路由、用例和适配器。

分进程的原因是负载不同：API 服务用户交互，文档解析与模型分析可能持续较长时间；Worker 可以单独调整消费队列、并发和资源。共用代码库则减少模型、接口和迁移版本的同步成本。

成本也很明确：必须维护队列、派发、重试、任务状态和部署一致性。API、一个 Worker 与 Beat 仍共享数据库与资源，不能据此宣称故障完全隔离。

### 1.2 外部依赖及选型目的

| 技术 | 当前用途 | 选择它解决的问题 |
| --- | --- | --- |
| Python 3.12+、FastAPI、Pydantic | 后端与 HTTP 契约 | 复用 Python 文档/模型生态，并把请求结构校验集中在入口 |
| SQLAlchemy、PostgreSQL | 表定义、查询、事务、JSON 数据、锁 | 同时保存结构化业务状态和分析数据，并提供事务与并发控制 |
| Alembic | 数据库迁移 | 数据库变更可排序、可部署、可核对 |
| Celery、Redis | 异步任务、定时派发；Redis 还用于配置缓存 | 长任务脱离 HTTP 请求生命周期 |
| S3 协议、MinIO | 原件、PDF、MiddleJson 等对象 | 大文件通过对象存储读写，关系库保存关联与状态 |
| Gotenberg | Office 等文件转换为 PDF | 把转换引擎及字体环境放在独立服务中 |
| MinerU | 文档版面与文本解析 | 通过自有解析端口接入外部解析服务 |
| pypdfium2 | 页面几何、PDF 局部处理 | 为坐标换算和原文定位提供稳定输入 |
| DeepAgents、LangGraph | 专题 Agent、工具调用、状态与检查点 | 支持多步研究、恢复和过程控制，代价是运行时复杂度及框架依赖 |

API 进程并非完全不访问外部服务：上传、模型测试和部分检索就在请求路径中执行。耗时的批量转换、解析和报告生成主要由 Worker 承担。

### 2.2 各层应承担的工作

| 目录 | 应承担 | 应避免 |
| --- | --- | --- |
| api | DTO、请求上下文、调用服务、HTTP 状态与响应、传输协议 | 直接查询数据库、在路由里编写业务流程 |
| application | 业务校验、状态判断、跨操作编排、结果整形、Agent 行为 | 创建数据库引擎、引用具体仓储、处理 HTTP 响应 |
| ports | 调用者需要的方法、参数、返回值及跨实现数据契约 | SQL、HTTP 请求、具体 SDK 客户端 |
| adapters | 将端口能力落实为数据库、HTTP、对象存储等操作 | 承担面向用户的业务决策 |
| domain | 锚点、坐标、页面几何、文本/摘要等可独立计算的规则 | 数据库、网络、FastAPI 与 Celery |
| worker | 队列入口、生命周期、重试、调用锁/租约端口、任务执行装配 | 直接操作 ORM、持有数据库连接，或复制与 API 不同的业务规则 |
| core | 装配、日志、环境设置、密钥与脱敏 | 变成所有业务代码的默认存放点 |
| config | 配置 schema、门禁、活动配置读取、快照支持 | 与 configuration 业务目录重复实现发布用例 |

domain 当前是较轻的纯规则层，没有为每张表建立领域实体，也没有完整采用复杂的领域驱动设计模型。application 中的 Agent 代码直接依赖 DeepAgents/LangGraph；“隔离外部数据访问实现”不等于“所有业务代码都不依赖任何框架”。

### 2.3 service、crud、agent 如何对应现有目录

这三个词描述职责：

- service：通常对应 application 内的业务用例。
- crud：描述数据增删改查；数据库实现归入 adapters/pg/repositories。
- agent：专题研究和问答编排归入 application/analysis、application/knowledge；数据库检查点归入 adapters/pg/analysis；执行生命周期由 Worker 接入。

因此，不再增加与 application、ports、adapters 并列的 services、crud、agent 根目录。单个业务内使用 service.py、agent.py 是合理的文件命名。

## 3. 按业务分类的边界

### 3.1 当前业务分组

| 业务名 | 主要内容 | 边界说明 |
| --- | --- | --- |
| projects | 项目元数据、项目文件上传/替换/删除、文件角色 | 管理“项目拥有哪些文件” |
| documents | 文档版本、转换、解析、页面、章节与原文 | 管理“文件内容如何被处理和定位” |
| knowledge | 知识库、来源、索引、检索、引用、问答 | 提供可供查询和研究使用的资料 |
| analysis | 项目专题分析、报告、研究过程、证据与结果快照 | 组织多个来源形成项目分析结果 |
| llm | 供应商、模型、功能绑定、测试、路由、调用记录 | 管理模型能力及其调用策略 |
| configuration | 配置发布、激活、回滚等管理用例 | 与 core/settings 的部署参数区分 |
| jobs | 任务查询、取消、进度和任务投递接口 | 支撑任务的通用生命周期与交互 |

文件上传放在 projects/files，解析放在 documents，并不是按文件扩展名分类，而是按操作的业务目的分类。

### 3.2 为什么单文件业务也建目录

已确定业务的目录归属不随文件数量变化。例如 configuration 当前某层只有 service.py，仍放入 configuration/，后续增加功能时位置稳定，跨层查找也更直接。

代价是路径变长、包数量增加。因此只为**已经存在的业务**建目录，不建空的未来模块；core、数据库连接、ORM 表定义等基础设施继续按技术职责组织。

不同层复用同一个业务名称，有助于查找，但不要求每个业务在所有层都具有相同文件数，也不要求每个接口都新建一个服务类和仓储类。

### 3.3 允许必要的业务协作

例如 AnalysisService 使用 KnowledgeService 与 ReportRepository 端口，分析报告需要读取知识来源与快照；KnowledgeStore 实现保留知识与报告的联合操作，业务用例按职责依赖窄端口，组合端口仅供装配使用。强行按目录拆成两份 SQL 或增加一个纯转发仓储，会扩大维护成本。

shared 只接收多个业务实际共用的代码。不能因为跨业务调用存在，就把所有相关代码都挪入 shared；应优先明确谁拥有规则，谁只是调用者。

## 4. ports、adapters 与依赖注入

### 4.1 名称的含义

名称来自 Ports and Adapters，也称端口与适配器架构。

**ports 是接口抽象层**，表达业务需要什么能力。例如“按项目 ID 读取项目”“在同一事务中写任务与配置快照”“请求模型返回补全结果”。

**adapters 是具体实现**，把能力落实到 PostgreSQL、S3、Celery 或 HTTP 服务上。它需要满足端口约定，但端口通常不规定 SQL 如何编写、连接池如何配置。

| 端口 | 具体实现 |
| --- | --- |
| ports/repository/projects/projects.py | adapters/pg/repositories/projects/projects.py |
| ports/repository/documents/parsing.py | adapters/pg/repositories/documents/parsing.py |
| ports/repository/documents/pipeline.py | adapters/pg/repositories/documents/pipeline.py |
| ports/repository/jobs/dispatch.py | adapters/pg/repositories/jobs/dispatch.py |
| ports/jobs/coordination.py | adapters/pg/repositories/jobs/coordination.py |
| ports/repository/llm/runtime.py | adapters/pg/repositories/llm/runtime.py |
| ports/storage/blob_store.py | adapters/storage/s3.py |
| ports/documents/parser.py | adapters/documents/mineru.py |
| ports/llm/chat.py | adapters/llm/openai_chat.py 等模型接入代码 |
| ports/jobs/queue.py | adapters/jobs/celery_queue.py |

仓储是“围绕业务数据提供操作”的对象，不等于一张表的包装。一个仓储方法可以查询多个表，一个事务端口可以组织多个相关操作。

### 4.2 代码依赖方向与运行时调用方向不同

运行时，服务持有的是已经创建好的具体对象：

~~~text
HTTP 请求 → api 路由 → application 服务 → 具体仓储对象 → PostgreSQL
~~~

ports 不处理请求，也不把请求转发一次。下面这张图表示**源码依赖与契约关系**：

~~~mermaid
flowchart TB
    API["api"] --> APP["application"]
    WORKER["worker"] --> APP
    APP --> PORTS["ports：接口与数据契约"]
    WORKER --> PORTS
    APP --> DOMAIN["domain：纯规则"]
    PORTS --> DOMAIN
    AD["adapters：具体实现"] -.->|"符合契约，未必显式继承"| PORTS
    DI["core/di：装配"] --> APP
    DI --> AD
~~~

application 导入 ports 中的接口，而不导入 adapters 中的具体仓储。core/di 同时知道业务服务和具体实现，负责把它们连接起来。

箭头不是要求每次调用都走遍每一层。例如读取项目列表未必调用 domain；协议中纯粹的方法声明也不会在运行时执行。

### 4.3 Python Protocol 实际约束什么

当前端口主要使用 typing.Protocol。以下省略非创建方法，用于说明真实结构：

~~~python
# ports/repository/projects/projects.py
class ProjectRepository(Protocol):
    def create(
        self, *, name: str, project_no: str | None, owner: str | None
    ) -> dict[str, Any]: ...

# application/projects/service.py
class ProjectService:
    def __init__(self, repository: ProjectRepository, company_id: int) -> None:
        # 接收依赖，使业务规则可以在不连接 PostgreSQL 的条件下验证。
        self.repository = repository
~~~

Protocol 采用结构化类型：实现只要提供兼容的方法即可，不必显式继承这个协议。它也不会仅因为写了类型注解，就在运行时验证参数和返回值。

需要区分三个机制：

| 机制 | 解决的问题 | 不负责什么 |
| --- | --- | --- |
| 依赖注入 | 调用方拿到可替换的对象 | 不自动定义对象应有的方法 |
| Protocol | 明确方法、参数、返回类型，供阅读和静态检查 | 不自动执行运行时校验 |
| 测试 | 验证业务规则、事务行为、具体实现行为 | 有限用例不能证明所有类型和路径都正确 |

即使删去 repository 的类型注解，Python 仍可以注入假仓储。**可替换性首先来自依赖注入，ports 增加的是显式契约。**

当前已接入 mypy，检查全部 ports 与 core/di.py 的真实装配：当具体实现传入接收协议的用例，或从声明返回协议的工厂返回时，检查方法是否存在、参数与返回类型是否兼容。检查使用 follow_imports = "silent" 读取实现类型，不能改成 skip 把实现降为 Any。

这项检查已纳入普通离线 pytest。test_protocol_types.py 同时运行正向检查与反向探针：将真实仓储赋给缺少方法或签名不匹配的协议，必须报错。因此不是仅检查协议文件本身能否通过语法检查。

检查还覆盖 Agent 状态与研究流程、应用检索、任务服务、领域分块，以及报告和检索模型查询模块，尚未开启全项目 strict 检查；Ruff 和 import-linter 各自负责不同问题。dict[str, Any] 的内部字段、通过 Any 传递的对象，以及运行时业务语义仍需测试验证。

### 4.4 core/di 如何装配

实际 [create_project_service](../../apps/api/src/tender/core/di.py) 创建 PostgreSQL 仓储并交给业务服务：

~~~python
def create_project_service(engine: Engine, company_id: int) -> ProjectService:
    return ProjectService(ProjectRepository(engine, company_id), company_id)
~~~

这里 ProjectRepository 指具体实现；业务服务文件中的同名类型指 ports 协议，阅读时应查看导入来源。

当前使用普通工厂函数装配，没有额外引入依赖注入容器框架。API 的公共组件在 create_app 时创建并保存到 app.state，退出时关闭相关资源；路由再通过工厂创建用例。它们复用进程资源，不等于每个请求都新建数据库连接池。

core/di 已管理 API 用例、Worker 仓储、任务锁、配置读取、解析器和模型网关的装配；Worker 的数据库引擎在装配点按进程复用，任务入口不接收数据库连接。检查点连接也经装配函数提供，随单次运行关闭。Worker 仍有 Gotenberg、PDFium、S3 等非数据库客户端的局部装配，不能描述为“全项目所有对象已经由一个容器统一创建”。

### 4.5 ports 值得保留的范围

外部模型、对象存储、队列、复杂仓储及事务接口具有明确边界，端口通常有价值。简单 CRUD 的端口则可能只是复制一组方法声明，收益需要结合测试替换、调用者数量和维护成本判断。

后续新增端口应描述调用者真正需要的能力，优先复用既有端口；不为了目录对称给每个类补一个协议，也不把 SQLAlchemy Connection、HTTP Response 等具体对象放进业务端口。

### 6.1 请求受理与任务执行分开

### 6.2 关键落点

1. [api/documents/parsing.py](../../apps/api/src/tender/api/documents/parsing.py) 解析参数，调用 ParseService。
2. [application/documents/parsing.py](../../apps/api/src/tender/application/documents/parsing.py) 检查版本存在性，预读活动配置，在仓储事务内锁文件、检查重复任务/既有结果，写快照和任务。
3. [worker/dispatch.py](../../apps/api/src/tender/worker/dispatch.py) 根据实时配置与在途数量派发差额；Beat 每秒发送唤醒消息，实际派发间隔由运行配置控制。DispatchRepository 的事务把在途计数、候选行锁和派发标记留在同一连接上。
4. [worker/documents/tasks.py](../../apps/api/src/tender/worker/documents/tasks.py) 负责提交、延迟轮询、外部产物读取和状态收敛。Office 文件还有前置转换，PDF 文件有页面几何处理。
5. [application/documents/middle_json.py](../../apps/api/src/tender/application/documents/middle_json.py) 归一化解析产物；最终元素、父子关系、ParseRun 与 Job 状态在同一数据库事务中保存。
6. [api/jobs/routes.py](../../apps/api/src/tender/api/jobs/routes.py) 提供查询和 SSE。当前 SSE 每秒经服务读取数据库，并按变化发送事件，不是从 Redis 订阅 Worker 推送的进度。

这些事务边界避免“任务显示完成，但可供检索和定位的元素尚未写入”。文档 Worker 通过 [DocumentPipelineRepository 端口](../../apps/api/src/tender/ports/repository/documents/pipeline.py) 读取、认领和更新任务；[PostgreSQL 实现](../../apps/api/src/tender/adapters/pg/repositories/documents/pipeline.py) 负责 SQL、执行起点、版本落库和解析结果的原子写入。任务互斥通过 TaskLocks 端口获取，不向 Worker 暴露数据库连接。

取消请求与执行结束分开记录：`pending` 可立即取消，执行中的任务先进入非终态 `canceling`，保留派发标记、配额与恢复扫描。本地任务退出后收尾；远端解析仅继续查询状态，直到终态或确认任务不存在，再原子收敛 Job 与 ParseRun，不下载成果或重提任务。转换完成、提交回执和解析落库均检查并发取消，避免继续创建版本、发布成果或丢失远端句柄。远端受理结果未知时保留占用，提示人工核对；原执行预算耗尽不能作为释放远端配额的依据。

解析超时、轮询预算耗尽等本地失败进入非终态 `draining`，保存首次错误并保留活动 ParseRun、配额与恢复能力；只有确认远端终态或任务不存在后，才同事务将 Job/ParseRun 收敛为 `failed`。提交结果未知时也进入排空等待，但无句柄或处于未知重提阶段的任务只能人工核对，不能查询旧句柄后释放新提交的占用。解析适配器的状态轮询不要求成果有效：缺少 MiddleJson 的 completed 也可完成排空，正常消费路径仍拒绝缺失成果。

知识来源首次处理与已有版本解析共用 `parse_options`，从同一活动配置读取 `mineru.tier` 与 `mineru.ocr_mode`；入队时连同执行参数冻结到任务快照，避免首次处理静默回退到默认档位。

### 6.3 队列与消息契约

当前生产者路由在 [adapters/jobs/celery_queue.py](../../apps/api/src/tender/adapters/jobs/celery_queue.py)：

| 队列 | 消费内容 |
| --- | --- |
| tender | 文档派发、知识任务派发 |
| convert | 文件转换与预处理 |
| parse | 提交解析 |
| poll | 解析状态轮询及产物读取 |
| analysis | 知识索引、专题报告、问答 |

默认使用一个 Worker 消费 `convert,parse,tender,poll,analysis`，线程池并发为7，减少常驻解释器和连接池。任务仍按队列分类并遵守业务配额；长任务占满线程时调度和轮询会等待，后续是否拆分进程应由实际负载决定。

旧的 extract、regression 不属于当前这份 Celery 路由表。部署时 Worker 必须消费实际投递的队列。

Python 模块路径与 Celery 消息名是两份契约。例如代码已移到 worker/documents/tasks.py，但消息仍使用 tender.worker.tasks.submit_parse。worker/knowledge/tasks.py 中的消息仍使用 tender.worker.knowledge.*。目录迁移不能直接替换消息名，否则排队中的消息会找不到任务。

## 7. 专题分析与模型调用

### 7.1 从分析请求到报告

入口为 POST /api/v1/projects/{project_id}/analysis。

1. [AnalysisService.start_analysis](../../apps/api/src/tender/application/analysis/service.py) 检查项目分类与资料，必要时触发资料处理，收集来源、参考资料、Skill 与运行限制。
2. 在锁定项目的事务中检查进行中的报告，写入报告及相关快照，返回报告标识。
3. Beat 每15秒发送 dispatch_knowledge；Worker 为可处理资料建立索引记录，并认领、派发索引、报告和问答任务。
4. [worker/knowledge/tasks.py](../../apps/api/src/tender/worker/knowledge/tasks.py) 的 analyze_project 获取报告锁，再调用 `core/di.py` 装配的 AnalysisExecutor；结构和运行版本门禁属于执行用例。
5. [application/analysis/execution.py](../../apps/api/src/tender/application/analysis/execution.py) 检查资料可用性。资料未就绪时可延期等待；是否允许部分分析影响能否开始。
6. 控制器先持久化模块和运行记录，再为各专题创建异步执行任务；实际运行受配额、权限、截止时间和取消状态约束。
7. 各专题检索和阅读证据，按 Skill 汇总并校验结构、引用与内容；成果、缺口及运行状态分别保存。
8. 控制器根据模块结果收敛报告为完成、部分完成或失败，并发布可供读取的结果数据快照。

这一流程不会重新进入已下线的固定字段抽取流水线。历史运行版本不兼容时会拒绝继续执行，避免用新规则静默重跑旧任务。

### 7.2 Agent 为什么分成这些文件

| 文件/目录 | 职责与原因 |
| --- | --- |
| application/analysis/service.py | 报告管理用例与查询，服务 HTTP 等调用者 |
| application/analysis/agent.py | 构建专题 Agent、工具和过程控制，集中定义研究行为 |
| application/analysis/research.py、policy.py | 研究会话与约束，避免全部规则堆进任务入口 |
| application/analysis/skills.py、output.py | 定位 Skill 资源，构建/校验输出 |
| application/analysis/runtime.py | 运行状态、配额、预算、事件等编排，通过仓储契约访问持久设施 |
| ports/repository/analysis/runtime.py | 运行持久化与配额能力的契约 |
| adapters/pg/repositories/analysis/runtime.py | 数据库运行账和锁等实现 |
| adapters/pg/analysis/checkpoints.py | PostgreSQL 检查点与异步运行支持 |
| application/analysis/execution.py | 报告准备、专题执行、成果合并、校验与发布 |
| application/analysis/state.py | 研究失效、暂存、校验、完成意图与发布的核心状态转换 |
| application/knowledge/execution.py | 索引构建与问答业务执行 |

核心业务状态由 `AnalysisState` 声明，`AnalysisTransitions` 集中处理新证据失效、暂存替换、核实标记、单次完成意图消费、草稿发布和失败改写回滚。检查点沿用原字典及未知历史字段，预算与工具重放账不被状态转换清除。框架回调只触发这些转换，未将研究账、证据和模型消息强行改成新存储格式。

Agent 放在 application，是因为检索策略、证据规则和专题汇总属于业务流程。数据库检查点放在 adapters，是因为连接、建表和持久化属于技术实现。

独立专题 Agent 是应用内部的运行结构，不等于每个专题部署一个服务，也不等于给每个专题启动一个 Celery 进程。

### 7.3 模型策略与模型传输的区别

application/llm/routing.py 处理模型候选、调用预算、重试与故障转移等策略；adapters/llm 处理协议请求、流式响应、嵌入、重排、生图等具体接入。application/llm/factory.py 通过 ModelRuntimeRepository 端口读取候选与策略、记录调用账本，并处理密钥解密；其仓储、冷却和模型网关由 `core/di.py` 注入。模型测试维护也经同一仓储入口访问数据库。

文本请求在适配器中共用一个可续期的 `asyncio.timeout_at`：发送前开始首增量等待，新增推理、正文和工具参数刷新响应间隔；心跳、空事件及元信息不刷新。`timeout_seconds` 必填正数，新建和导入默认10秒；可空的 `total_timeout_seconds` 控制单次总时限，两者取较早截止。非文本模型沿用请求总超时。SDK的重叠请求／分块超时和隐式重试关闭，原有客户端连接池继续复用。

功能绑定只限制总次数、额外重试和切换级数，删除绑定时间截止及候选时间分摊。恢复旧未结束窗口忽略窗口自己的旧截止，保留请求身份、次数、结果与终态；模块总预算继续覆盖请求、工具、重试及等待。完整结束和原始工具JSON校验均通过后才能结算成功，避免SDK补齐半截参数后执行业务工具。

文本模型测试每15秒通过仓储端口续租，60秒未续租时收敛为未知；历史无心跳测试按原规则清理。结束时锁定测试，在同一事务保存结果、调用账和终态，迟到结果不能覆盖维护清理。计时日志记录首增量耗时、最大间隔及超时类型，生产调用不增加逐增量数据库写入。迁移与上线次序见[LLM管理与模型路由第13节](../设计/12-LLM管理与模型路由.md#13-模型响应间隔与迁移-00202026-11-13)。

异步管理接口中的配置、权限与模型测试数据库操作通过 `asyncio.to_thread` 执行。模型路由中的候选复核、共享冷却、请求预占和调用记账同样在线程执行，并保持发送前预占、每次请求后记账的顺序，避免同步数据库等待阻塞事件循环。

发送前预占期间收到取消时，先等待预占线程落定，再把同一调用账补为 `error`，明确记录未向供应商发送请求，然后向调用方传播取消；重复取消也不能打断这段收尾，避免迟到的 `running` 写入覆盖终态。请求已发出后的取消仍记录 `unknown`，不能据此断言供应商已经停止。

分开后，业务可以基于统一结果处理 token、模型信息和错误，而不在各专题里复制 HTTP 请求代码。代价是协议、供应商能力与路由策略需要分别维护。

检查点、快照和调用记录提高可追溯性，但不保证模型输出完全确定，也不保证远端请求在进程中断后绝不重复。恢复能力应依据具体运行版本和持久化记录判断。

### 7.4 检索的执行边界

已完成索引复用持久化分块；PostgreSQL 内执行词法命中、余弦、阈值、同分次序和 RRF，最后 LIMIT，仅返回有限候选与语义来源 ID。SQL 仍通过原文权限连接核对公司、来源、文件、版本和解析批次。未建成或旧分块版本回退到原文分块，使用一个 JSONB 参数参与同一排名。同步查询在线程池运行，避免在事件循环内扫描和排序全部向量。

重排仅调整前 30 个候选的顺序。供应商只返回部分 `top_n` 时，先放返回项，再按原顺序保留这 30 项中未返回的候选，最后接其余候选；统一截断前不丢候选，保证返回数量和 `search_limited` 仍反映实际候选集。

专题候选窗口由 `AgentLimits.search_window` 统一计算为单页数量乘以最多五页，检索执行与分页共用该值。同一查询的并发分页通过会话内查询锁合并召回，候选缓存最多八组；查询内部空格与HTML实体不归一化，避免复用不同语义的结果。每次工具调用仍计入预算并复核权限，有下一页时优先读取缓存，窗口耗尽后再拆主题。嵌入／重排连接关闭失败记录日志，不覆盖已取得的候选或关键词回退结果，任务取消仍传播。

专题与问答的显式原文/邻域补读向仓储传递 offset/limit，每次最多12块，并在读取后再次校验权限。有效索引直接按块序号取窗口并返回精确 total；旧索引或未建索引使用服务端游标与流式分块，扫描所需前缀及窗口后一块后停止。未到末尾时 total 为 null，使用 next_offset 继续读取；深 offset 仍需扫描前缀，单条大元素仍需取得该元素正文。支持性证据扩展的原文归属校验仍使用独立全文读取，本轮没有消除该路径的全文成本。

该实现保留精确排名语义，没有新增 ANN 引擎或近似向量索引；数据库计算量仍随候选块增长。收益是消除索引路径的反复分块、全文及全量向量传输；大语料性能仍需按真实规模测量，再决定是否引入新索引能力。

## 8. 数据、事务与一致性

### 8.1 不同“模型”解决不同问题

| 表达形式 | 例子 | 目的 |
| --- | --- | --- |
| HTTP DTO | ProjectCreate | 定义客户端可以提交哪些字段 |
| 端口数据契约 | Completion、ActiveConfig | 约定实现与调用者交换的数据 |
| 领域值对象 | Anchor、Bbox、PageGeometry | 表达格式、坐标和计算规则 |
| ORM 模型 | Project、ParseRun、Element | 表达数据库表、列和关系 |
| 仓储返回数据 | 项目字典、来源列表 | 提供用例所需的查询结果 |

ORM 模型不应成为 API 和用例必须理解的数据库对象。当前很多查询返回普通字典，但字典并不天然保证边界合理；若里面泄漏数据库连接、延迟查询对象或驱动异常，仍然会造成耦合。

### 8.2 domain 为什么单独保留

锚点与坐标错误可能不抛异常，却把用户定位到错误原文。因此把格式、归一化范围和旋转换算放到纯函数/值对象里，更容易独立验证。

[domain/documents](../../apps/api/src/tender/domain/documents) 当前包含锚点、bbox、页面几何与归一化元素；bbox 使用 Decimal 处理十进制精度。NormalizedElement 放在领域层，PDF 检查结果放在 ports/documents/inspection.py，使解析用例和数据库适配器共享中立数据类型，不必让仓储反向依赖 application 或具体 PDF 客户端。坐标以归一化比例、左上原点和视觉方向表达，前后端通过共享契约向量验证。

页面几何属于文档版本，解析元素属于某次解析运行。证据定位必须保留来源和运行关联，不能仅靠一段文字相似就断定属于同一份产物。

### 8.3 谁决定事务边界

有两种现有方式：

- 单次完整操作：仓储方法内部开事务，例如创建项目及关联知识集合。
- 多步业务编排：application 使用 with repository.transaction()，判断要做哪些步骤；adapters 提供的事务对象负责真实连接、SQL、锁、提交和回滚，例如创建解析任务。

~~~python
# 结构示意：省略业务校验，展示现有 ParseService 的事务使用方式。
active = configs.active(company_id)
with repository.transaction() as tx:
    snapshot_id = tx.snapshot_for_job(active)
    tx.insert_job({**job_values, "config_snapshot_id": snapshot_id})
~~~

快照与任务使用同一事务，避免任务指向不存在的快照。业务层不接收 SQLAlchemy Connection。配置预读放在事务前是为了缩短持锁时间；snapshot_for_job 使用传入的活动配置，显式传入 None 表示本次预读没有活动版本，不再在事务内回源读取另一版本。此时快照 ID 为空，但任务行仍保存包含默认值的执行参数快照。

### 8.4 PostgreSQL 事务不能覆盖所有系统

| 边界 | 当前处理 | 能力限制 |
| --- | --- | --- |
| 关系数据 | 数据库事务、约束、行锁/咨询锁 | 原子性只覆盖该数据库事务 |
| 数据库与队列 | 持久任务、派发标记、状态检查、任务锁、部分租约机制 | 没有全局分布式事务，也不保证恰好执行一次 |
| 数据库与对象存储 | 对象键/摘要、业务记录及错误处理 | 数据库回滚不会自动撤销已上传对象 |
| 数据库与模型/解析服务 | 外部任务标识、请求记录、重试与错误状态 | 超时不一定表示远端没有执行 |

例如文档派发会先发消息，再在同一数据库事务中记录 dispatched_at。若提交失败，后续可能重复派发，任务侧通过锁与状态判断减少重复执行。`next_attempt_at` 持久化下一轮时间，`dispatch_lease_until` 标记 60 秒消息租约；每次调度先恢复已到期的执行或丢失消息，再处理新任务配额与派发间隔。执行不会早于下次时间，实际唤醒受约一秒的扫描周期和队列等待影响。仍持有会话锁的活跃执行者会延长扫描租约，避免前面的长任务饿死后续失联任务。提前重复消息不能消耗轮询次数，过时的跨阶段消息不能重新设置派发标记；网络重试计数随下次时间持久化，恢复不重置退避和执行预算。提交结果未知时进入 `draining` 并保留占用，等待人工核对；已有取消请求的任务继续保持 `canceling`。

并发配额在公司/资源的事务咨询锁内统计：解析覆盖 submitting/parsing/resubmitting，转换覆盖 converting/probing/geometry。阶段交接结束旧配额占用，再等待下一资源的派发。当前没有完整的事务发件箱（Outbox）机制，不能把“任务持久化”写成“消息和数据库原子提交”。

PostgreSQL 是任务和报告状态的主要读取来源，Redis 队列负责触发执行。Celery 函数正常返回只表示任务函数结束，业务是否成功应查看数据库中的终态。

### 8.5 数据库结构如何维护

[adapters/pg/session.py](../../apps/api/src/tender/adapters/pg/session.py) 是业务库引擎构造入口，统一连接参数；不同进程仍有各自的引擎实例。仓储既使用 ORM 表定义，也使用 SQLAlchemy 的表达式与 Connection 执行语句，不是所有操作都走 ORM Session。

结构变更通过 Alembic。项目还维护设计文档中的 DDL，并以契约测试核对文档、迁移和 ORM。正式表结构说明分布在数据模型、配置、模型管理、知识分析等文档中，本文不复制 DDL。

运行环境究竟处于哪个迁移版本，需要现场查询；源码中存在迁移文件，不代表业务库已经应用。

## 9. 配置分层与快照

| 配置类别 | 主要位置 | 为什么分开 |
| --- | --- | --- |
| 部署参数 | core/settings.py | 数据库、Redis、存储、服务地址与密钥等由部署环境提供 |
| 业务配置规则 | config/schema.py、gate.py | 定义配置项、默认值、解析规则与发布门禁 |
| 配置管理用例 | application/configuration/service.py | 激活、回滚、影响确认等业务流程 |
| 配置持久化与缓存 | adapters/pg/repositories/configuration、config/registry.py、adapters/configuration | 活动版本先持久化，再更新缓存 |
| 任务配置 | job.config_snapshot、job_config_snapshot | 保存任务参数与创建时的配置上下文 |
| 报告运行配置 | 报告来源、Skill、运行版本和限制快照 | 固定分析所依据的材料与规则 |

config 是此前已经存在的基础设施包：registry.py、snapshot.py 仍包含数据库访问，schema.py、gate.py 则主要是规则。因此不能把整个 config 都说成纯领域层，也不能说所有持久化代码已集中到 adapters。

用例和调度 Worker 通过 ports/configuration/registry.py 中的 ConfigReader 读取配置，避免直接绑定具体 ConfigRegistry；装配点和仓储内部可以使用该实现。

**文档执行参数按任务冻结，派发参数保持实时。** 二者解决不同问题：执行预算稳定才能解释同一任务的重试；实时调度才能在资源紧张时暂停新派发。

| 参数 | 生效边界 |
| --- | --- |
| job.poll.initial_interval_ms、job.poll.max_interval_ms | 创建时固定轮询退避区间 |
| job.poll.max_attempts | 创建时固定累计轮询次数上限 |
| job.timeout.convert_minutes、job.timeout.parse_minutes | 创建时固定转换/解析累计时限 |
| job.retry.convert_500 | 创建时固定转换额外重试次数 |
| convert.max_inflight、parse.max_inflight、dispatch.interval_seconds | 派发时读当前配置；不修改已有任务的执行预算 |

上传项目文件、直接发起解析、知识资料处理这三个任务创建入口，都将六项执行参数写入 job.config_snapshot.execution，标记 execution_origin = "created"；有活动版本时还在同一事务写 job_config_snapshot。没有活动版本时，内嵌执行快照使用默认值，不能因为快照 ID 为空而在后续执行中随配置变化。

DocumentPipelineRepository.runtime_values() 按以下顺序读取旧任务：

1. 已有 execution：直接使用，不重读活动配置。
2. 没有 execution，但有 job_config_snapshot：从历史 resolved 补齐，来源标记为 job_config_snapshot。
3. 两者都没有：在首次执行时读取当前配置，来源标记为 legacy_first_execution；这无法还原未知的创建时配置。

补齐时先预读配置，再锁定任务行复查并保存 execution 和 execution_frozen_at；并发调用采用先写入者的值。重试、恢复和阶段切换继续使用同一份执行参数，不重置既有累计时间与次数。

冻结范围不包括服务地址、凭证、实时并发、权限和取消状态，也不保证远端模型结果相同。新增配置项必须明确生效边界，不能仅凭 L1 分类就认定立即影响运行中的任务。

## 10. 异常、日志与运行边界

### 10.1 错误由对应边界解释

业务服务抛 ServiceError 及其子类，表达参数无效、不存在、冲突等语义；领域和外部调用还使用 TenderError 体系。api/shared/errors.py 将这些错误转换为统一 HTTP 响应。

HTTP 错误映射留在 API，避免业务用例依赖 FastAPI。现有全局处理器允许捕获 SQLAlchemy IntegrityError 作为兜底，这是明确的例外，不代表 API 可以执行数据库查询。

Worker 必须把业务失败保存到任务/报告中。捕获异常后正常返回的任务仍可能是业务失败，不能只看 Celery 的成功标记。

### 10.2 日志与数据记录各有用途

core/logging 统一上下文、格式化、脱敏和文件写入。不同 ID 的含义分别是：

| ID | 定位对象 |
| --- | --- |
| request_id | 一次 HTTP 请求 |
| task_id | 一次 Celery 执行 |
| job_id | 一条文档业务任务 |
| report_id | 一份分析报告 |
| run_id、module_key | 某次运行及专题 |
| invocation_id | 模型调用关联 |

自动生成的 request_id 与 task_id 使用同一短 ID 规则，但两者不是同一个概念。

文件日志模式下，普通摘要与错误堆栈分别保存为同目录的日期分片，支持同日重启追加。模型逻辑调用和工具调用在结束时记录摘要；调用账本、报告结果和检查点则承担业务追踪与恢复用途。

API 写任务后由 Beat 再派发的路径，尚未完整持久化贯通原请求 ID，因此当前不是完整分布式追踪。格式和留存细节见 [20-后端日志基础服务](20-后端日志基础服务.md)。

### 10.3 身份与租户的实际边界

当前使用部署公司上下文及部分业务权限检查。公共请求辅助函数从 x-role、x-actor 读取角色与操作者，缺省采用本地部署值，不能等同于完整的用户认证、SSO 或严格的多租户身份系统。

这是部署信任边界的一部分。未来若改变为不可信客户端直接访问，需要专门设计身份认证与授权，不能仅凭已有 company_id 字段认定隔离已完整实现。

### 10.4 部署和资源生命周期

实际启动入口见 [scripts/start-backend.ps1](../../scripts/start-backend.ps1) 与 [docker-compose.yml](../../docker-compose.yml)。Windows 本地和容器部署的进程池、路径和参数可能不同，应以对应脚本为准。

API、Worker、Beat 应加载兼容的代码、消息名和数据库结构。部署变更需考虑队列中的旧消息；数据库迁移与检查点初始化是部署操作，普通架构检查不需要执行它们。

当前检查点初始化入口为 tender.adapters.pg.analysis.checkpoints，运行方法和数据库迁移说明见 [17-数据库迁移](17-数据库迁移.md)。

## 11. 为什么采用这种结构，以及代价是什么

| 设计选择 | 当前收益 | 代价与适用边界 |
| --- | --- | --- |
| 模块化单体、共享数据库 | 项目、文档、知识和报告可以直接协作，事务与版本管理较简单 | 数据和部署仍耦合；业务目录不是微服务边界 |
| API 与 Worker 分进程 | 长任务不占用一次 HTTP 交互，执行资源可独立调整 | 增加队列、任务状态、重试和部署成本 |
| 架构层内按业务分类 | 查找同一业务在不同职责中的代码更直接 | 路径变长；必须维护业务边界，避免强制目录对称 |
| API / application / 仓储分工 | HTTP、业务判断、数据访问可以分别修改与验证 | 简单 CRUD 会增加跳转层数，不能无限细拆 |
| ports 与依赖注入 | 用例声明所需能力，测试可替换外部对象 | 协议需要维护；只有一个简单实现时收益可能较低 |
| 轻量 domain | 高风险的坐标、锚点规则可以独立验证 | 不必为每张表复制一个领域类 |
| 集中装配函数 | 明确实现选择，减少业务层对具体技术的依赖 | 工厂列表会增长，Worker 现有装配仍不完全统一 |
| 外部服务适配器 | 协议变更主要集中在接入位置 | 无法屏蔽所有能力差异，换供应商仍需验证 |
| 持久任务、快照与检查点 | 能查询过程、解释配置与来源、支持部分恢复 | 不能自动解决跨系统一致性或模型不确定性 |

当前没有充分理由仅因目录多就改成微服务，也没有理由为了“简单”把模型调用、数据库查询和业务规则重新塞回路由。合适的复杂度应由实际调用者、失败模式和验证需要决定。

## 12. 已落实的约束与现有限制

### 12.1 有哪些可执行检查

| 检查 | 已覆盖 | 不能据此推断 |
| --- | --- | --- |
| import-linter | 分层依赖、application/adapters 互不引用、api/worker 互不引用、部分 core/domain 边界 | 全部代码的行为正确或所有第三方依赖都被禁止 |
| test_layer_boundaries.py | 直接/相对导入、重复职责根目录、业务文件分类、当前业务目录名称 | Protocol 签名与实现一致 |
| mypy / test_protocol_types.py | 全部端口、真实装配点，以及 Agent 状态/研究、检索、任务服务、分块和新拆查询模块；反向探针防止实现退化为 Any | 全项目 strict、字典内部字段和运行时业务行为 |
| API/任务契约测试 | 路由、队列与注册消息等一致性 | 正在运行的部署一定消费了对应队列 |
| DDL/ORM 契约测试 | 迁移、文档和表定义的相应结构约定 | 现场数据库已迁移 |
| 用例单元测试 | 假仓储、事务编排、冲突回滚、业务规则 | 假实现完全等同真实数据库 |
| 数据库集成测试 | SQL、锁、事务与运行记录等真实数据库行为 | 真实模型、解析器、存储和部署链路都已验收 |

test_management_ports.py 使用不提供数据库连接的假事务验证“配置预读、快照与任务同事务、冲突回滚”；协议兼容另由 mypy 验证。Worker 的架构契约禁止直接导入 sqlalchemy、adapters.pg、config.registry 和 config.snapshot，防止数据库操作再次回到入口层。

当前目录检查要求七个已有业务在 API、用例、仓储端口和仓储实现中存在，这是现有检查的实际行为。它有固定布局的成本，不应推广成“未来每项功能都必须补齐四层目录”。若调整这一规则，应单独变更实现和测试，本文不暗示检查已经放宽。

### 12.2 当前需要如实承认的限制

- API、用例与 Worker 的业务数据库访问已经通过端口隔离；Worker 仍有非数据库客户端的局部装配。
- config/registry.py 与 snapshot.py 仍承载配置持久化设施；不能将整个 config 视为纯规则。
- 自动类型检查已扩大到上述关键执行模块，尚非全项目 strict；Any/字典内部字段约束仍有缺口。
- 简单 CRUD 的协议可能维护收益较低；报告只读与检索模型配置查询已分别拆为 `ReportQueries` 和 `RetrievalModelQueries`，由 KnowledgeStore 组合。其余实现仍较大，用例继续只依赖各自的窄端口，共享事务没有拆散。
- 任务投递没有完整 Outbox 或分布式事务，外部副作用需要结合重试、锁与状态逐项分析。
- 配置快照和检查点提供追踪依据，但不是所有运行参数冻结，也不能保证逐次模型结果相同。
- 身份认证和端到端请求追踪仍有上述边界，不能从目录结构推断它们已经完成。

这些是后续架构评估项。调整时需要同步源码、契约和验证方式，不能只修改文档中的描述。

## 13. 后续开发与阅读指引

### 13.1 新增功能时如何决定文件位置

1. 确定业务归属：项目文件管理、文档处理、知识服务还是报告分析；已有单文件业务也继续使用其业务目录。
2. 如果有 HTTP 入口，在 api 对应业务添加 DTO 和路由；内部能力无需为了对称新增 API。
3. 把业务判断和多步流程放在 application；可独立计算的通用领域规则再考虑 domain。
4. 需要外部能力时先检查已有 ports，按实际调用需求扩展契约，避免一操作一接口。
5. 在对应 adapters 中实现数据访问或服务接入；纯计算不需要仓储。
6. 在装配位置连接依赖。长任务还要确认持久状态、消息名称、队列消费者、取消和重试语义。
7. 按行为风险验证：重点看接口兼容、事务、重复投递、引用定位和真实实现，不只检查文件位置。

例如给项目增加一个校验规则，可能只需修改 application/projects/service.py 和业务测试；给项目增加持久化字段，才可能涉及 DTO、契约、仓储、模型和迁移。改动范围由行为变化决定。

### 13.2 推荐阅读代码顺序

- 先读 api/projects/routes.py → core/di.py → application/projects/service.py → ports/repository/projects/projects.py → 对应 PostgreSQL 仓储，理解同步调用。
- 再读 application/documents/parsing.py → worker/dispatch.py → worker/documents/tasks.py，理解事务与异步边界。
- 最后读 application/analysis/service.py → worker/knowledge/tasks.py → application/analysis/execution.py → application/analysis/agent.py，理解报告与 Agent 生命周期。
