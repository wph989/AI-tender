# 11 · 架构设计

> 本文承接 [10-技术选型与工程结构.md](10-技术选型与工程结构.md) 的分层约定，把架构落到**可直接实施**的粒度：领域模型、用例时序、事务边界、依赖装配、跨切面约定与测试策略。
> 本文不重复 10 已定的目录布局与选型理由，也不重复 [03-数据模型与溯源设计.md](../设计/03-数据模型与溯源设计.md) 的表结构（DDL 的唯一权威在 03）。

## 1. 架构总览

### 1.1 三个进程，一条数据主干

```
浏览器 ──REST / SSE──▶ api（FastAPI）
                         │  只做：鉴权、校验、编排入队、读模型查询
                         │  不碰：MinerU / Gotenberg / LLM
                         │
                         ├──▶ PostgreSQL   业务状态 + 任务状态
                         ├──▶ Redis        队列 + 进度事件
                         └──▶ MinIO        原件 / 转换产物 / 裁剪图 / MiddleJson 存档
                                 ▲
worker（Celery）──────────────────┘
  只做外部调用与产物落库；不提供 HTTP 服务
  ├── convert 队列     → Gotenberg
  ├── parse 队列       → MinerU（提交即返回 + 自重排轮询）
  ├── extract 队列     → LLM 网关
  └── regression 队列  → 低优先级回放

scheduler（Celery beat）
  每 5 秒：读配置 → 统计在途 → 提交差额
```

**为什么把调度单独抽成 beat，而不是放进 worker**：并发上限是**集群级**概念，而每个 worker 进程只能看见自己。让一个中心化的 tick 去读配置、数在途、提交差额，是「页面上改并发、立即生效」唯一不需要重启进程的实现方式（见 [10](10-技术选型与工程结构.md) 第 3.5 节）。

**为什么 `api` 与 `worker` 必须能独立扩容**：api 的负载是「人点页面的频率」，worker 的负载是「文档量与外部服务吞吐」，两者没有固定比例。合成一个进程后，为 worker 加算力会顺带把 api 的内存撑爆。

### 1.2 依赖方向

```
domain ← application ← adapters / api / worker / config
```

- `domain`：纯数据与纯函数，无框架、无 IO、无数据库，**可脱离一切外部服务单测**。
- `application`：用例编排，只依赖 `domain` + `ports`（`typing.Protocol`）。
- `adapters` / `api` / `worker` / `config`：实现细节，可替换、可 mock。

**唯一的例外与它的理由**：`api` 与 `worker` 都直接依赖 `adapters`，但**彼此不依赖**。二者通过数据库与队列通信，不通过函数调用——否则就无法独立扩容、独立重启。这条约束由 import-linter 在 CI 强制（见 [10](10-技术选型与工程结构.md) 第 4.4 节）。

## 2. 领域模型

### 2.1 四条不变量

领域层要守住的不变量只有四条，但**任何一条被破坏都会让溯源失效**：

| # | 不变量 | 破坏后的后果 |
| --- | --- | --- |
| 1 | 锚点 `p{page}b{block}` 在同一个 `parse_run` 内唯一 | 同一条证据指向两处，高亮随机跳 |
| 2 | bbox 为 0–1 归一化、左上原点、视觉方向 | 高亮框整体偏移或上下翻转 |
| 3 | 每条自动结果至少有一条证据，且锚点能在该 `parse_run` 的 `element` 中查到 | 点结果无处可跳，溯源断裂 |
| 4 | `manual_edit` 结果必须带用户选定的锚点，或显式声明 `not_found` | gold 集被污染，回归集失去意义 |

> `domain/bbox.py` 与 `domain/anchor.py` 在前端各有一份对应实现（`lib/coords/`）。同一契约的两份实现必然漂移，防漂移机制见 [10](10-技术选型与工程结构.md) 第 4.5 节。

**为什么把不变量写成可执行断言，而不是文档约定**：这四条都属于「破坏之后不报错、只静默给出错误结果」的类型。业务逻辑写错会抛异常，坐标写错只会把高亮画偏——而用户看到高亮偏一次，就再也不会相信这套系统。它必须由代码在写入前拦住。

### 2.2 值对象（domain，纯函数）

```python
# domain/anchor.py
# 锚点的唯一权威定义。格式 p{page}b{block}，均 1-based。
@dataclass(frozen=True, slots=True)
class Anchor:
    page_no: int
    block_no: int

    # 解析失败必须抛错，绝不返回 None：逼调用方显式处理「锚点坏了」这件事
    @classmethod
    def parse(cls, raw: str) -> "Anchor": ...

    def __str__(self) -> str: ...
```

```python
# domain/bbox.py
# 坐标契约：0-1 归一化、左上原点、视觉方向。
# 为什么用 Decimal 而不是 float：归一化坐标要落 NUMERIC(7,6) 并参与相等比较，
# float 的舍入会让「同一条证据」在两次读取中不相等。
@dataclass(frozen=True, slots=True)
class Bbox:
    x0: Decimal
    y0: Decimal
    x1: Decimal
    y1: Decimal

    def to_pixels(self, width_px: int, height_px: int) -> "PixelBox": ...
    def from_pixels(cls, box: "PixelBox", width_px: int, height_px: int) -> "Bbox": ...
    def union(self, other: "Bbox") -> "Bbox": ...
    def is_valid(self) -> bool: ...   # 0 <= x0 < x1 <= 1 且 0 <= y0 < y1 <= 1
```

```python
# domain/page.py
# 页面几何：坐标换算所需的全部输入集中在这里，不让调用方自己去查
# 不含页面像素尺寸：本期不生成整页位图，像素尺寸没有消费方（03 表里的同名列是预留）
@dataclass(frozen=True, slots=True)
class PageGeometry:
    page_no: int
    width_pt: Decimal
    height_pt: Decimal
    rotation: int          # 0 / 90 / 180 / 270，原始 /Rotate

    # 视口尺寸 = 应用 rotation 之后的尺寸。前端与后端必须用同一个换算。
    def viewport_size(self) -> tuple[Decimal, Decimal]: ...
```

**为什么 `rotation` 放在领域层而不是渲染层**：旋转决定了「视觉方向」的含义，而 bbox 契约写的正是视觉方向。把旋转换算留在渲染层，就会出现前端与后端各按各的理解换算，表现为「90 度页面上的高亮横竖颠倒」——这是最典型的坐标系错误，而且只在旋转页复现，测试极易漏掉。

### 2.3 聚合与聚合根

| 聚合 | 聚合根 | 包含 | 关键不变量 |
| --- | --- | --- | --- |
| 文档 | `DocumentVersion` | `Page` / `Element`（按 run 归属） | 锚点在 run 内唯一 |
| 结果 | `FieldInstance` | `Extraction`（尝试链） / `Evidence` / `ReviewAction` | 至多一条 `is_current`；证据非空 |
| 配置 | `ConfigRelease` | 值 / 审计 / 影响清单确认 | 同租户至多一条 `active` |
| 回归 | `GoldItem` | — | `expected_anchors` 非空 |

**为什么聚合根是 `FieldInstance` 而不是 `Extraction`**：复核状态、尝试链长度、收敛判定都属于「这个字段在这份文档上」这个整体，不属于某一次尝试。把根放在 `Extraction` 上，立刻会遇到「重跑之后，之前的复核状态该挂在哪一条」这种无解的问题。

### 2.4 领域服务

纯逻辑但跨实体，放 `domain/`：

| 服务 | 职责 |
| --- | --- |
| `AnchorValidator` | 锚点格式 + 存在性 + 归属 run 的校验（不变量 1、3） |
| `EvidenceMatcher` | quote 与 `element.text` 的归一化比对，产出字符区间 |
| `ConfidencePolicy` | 由校验结果计算折扣后的置信度（见 [04](../设计/04-解析流水线与抽取Agent.md) 第 6 节） |
| `FieldDefinition` | 字段定义（单值 / 多值 / 表格）的解析与 JSON Schema 生成 |

## 3. 用例时序

### 3.1 上传到可复核（主链路）

```
① 浏览器 POST /documents  ──▶ api
     api: 落 document + document_version（status=pending）
          写原件到 MinIO（按 sha256 寻址）
          入队 convert 或 parse（PDF 直通 parse）
          立即返回 202 + job_id
② convert 队列 ──▶ worker
     worker: 取 convert.max_inflight 许可
             POST Gotenberg（同步，带 Gotenberg-Trace）
             校验回传 trace → 落 pdf_key / pdf_sha256 / converter_version
             入队 parse，释放许可
③ parse 队列 ──▶ worker
     worker: 探测页面几何（pypdfium2）→ 按 version 幂等 upsert page
             （页面几何是版本的属性，reparse 不重写）
             提交 MinerU job（202 即返回）→ 记 provider_job_id
             用 countdown 重排 poll_parse
     poll_parse: 非终态则指数退避重排；终态则取 middle_json
④ 产物归一化（单个事务）
     worker: 解析 MiddleJson → 写 element（锚点、bbox）
             写章节树
             更新 parse_run.status = completed
             ★ 事务边界：element / 章节树必须与 run 状态一起提交
             入队 extract
⑤ extract 队列 ──▶ worker
     worker: 取 extract.max_inflight 许可
             构造锚点文档（两遍式）→ 调 LLM（带 JSON Schema 约束）
             校验 ① 锚点存在性 → ② quote 一致性 → ③ 规则冲突
             写 field_instance + extraction(is_current) + evidence
             跨文件冲突检测 → 写 extraction_conflict
             更新 job 进度 → 发 SSE 事件
⑥ 浏览器 GET /extractions  ──▶ 结果面板可用
```

**★ 第 ④ 步的事务边界为什么必须钉死**：`element` 是锚点的物理落点，`parse_run.status` 是「可以开始抽取」的信号。如果先提交 run 状态、再写 element，抽取任务可能在 element 还没写完时就启动，校验 ① 会因为「查不到锚点」把**全部证据丢弃**，结果是整份文档被判定为 `not_found`——而且看起来像「模型没抽出来」，排查方向完全错。

### 3.2 复核与人工修正

```
POST /instances/{iid}/reviews  ──▶ api
  api: 校验 action 与必填项（correct / supplement 必须有 evidence）
       校验锚点存在性（查该 instance 当前 run 的 element）
       ★ 事务：写 review_action
               +（correct / supplement 时）新建 trigger=manual_edit 的 extraction 快照
               + 切换 field_instance.current_extraction_id
               + 解析关联的 review_task
       提交后：correct / supplement → 异步沉淀 gold_item
```

**为什么要新建一条 `manual_edit` 快照，而不是就地改值**：尝试链要能完整回放。就地改值会让「这条值是谁给的、模型原先给的是什么」永久丢失，而这两项分别是人工兜底率与错误分析的基础。

**为什么 gold 沉淀异步**：它是统计资产，不属于用户的操作结果。放进同一事务，等于让用户的写操作去等一个可以迟到的写。

### 3.3 重跑

| 触发 | 复用 | 新增 | 事务 |
| --- | --- | --- | --- |
| 单字段重跑 | `parse_run` / `element` | 一条 extraction（机器序号 +1） | 单事务：新尝试 + 切 current |
| 重新解析 | 无（新建 `parse_run`） | 新 run + 新 element + 全量重抽 | 分阶段：先建 run，产物就绪后整体切 current |

**为什么重新解析不能「边解析边切 current」**：中途切换会让用户看到一半新锚点、一半旧锚点混在同一页，此时任何一次修正都会把锚点写进即将作废的 run。必须等整份新产物落库、且通过锚点唯一性校验后，才整体切换。

### 3.4 失败与补偿

| 失败点 | 补偿 |
| --- | --- |
| Gotenberg 400 | 直接 `failed`，不重试（文件本身的问题） |
| Gotenberg 5xx | 指数退避重试 ≤3 次；超限进死信 |
| MinerU 提交失败 | 不写 `provider_job_id`，任务回到 pending 由调度器重新提交 |
| MinerU 服务重启导致 job 丢失 | 按 `sha256` 重新提交（**ID 是进程内状态，不可续跑**） |
| MinerU `partial` | 保存已完成产物，`status=partial`，缺失页显式标注 |
| LLM 失败 | 单字段失败不影响其他字段；该字段留在 `need_review` |
| 产物归一化中途崩溃 | 事务未提交 → 重跑该阶段；**幂等**：先按 `run_id` 清掉未完成产物再重建 |

**幂等键的唯一选择是 `run_id`**：一个 `parse_run` 的 `element` 集合是确定的，重建它不产生歧义。用 `(version_id, anchor)` 当键会在两次 run 之间打架。

### 3.5 页面几何与裁剪图的落位

选型与许可理由见 [10](10-技术选型与工程结构.md) 第 3.11 节（pypdfium2 + Pillow）。本节只记它在时序里的位置与约束：

- **页面几何在第 ③ 步写入**（MinerU 解析之前），按 `version_id` 幂等 upsert：它属于版本而不是某次 `parse_run`，重新解析不重写；
- **第 ④ 步的事务边界只覆盖 `element` / 章节树 / `parse_run.status`**：`element` 是锚点的物理落点，run 状态是「可以开始抽取」的信号，两者必须原子提交（见 3.1 的失败模式）；
- **多模态裁剪图按需生成**，不进事务，也不进 `page` 表——key 由 `(version_id, page_no, bbox, dpi)` 决定，同一区域重复使用时直接命中缓存；
- 预览不经过后端位图：坐标换算由领域层纯函数负责（见 2.2），因此前后端渲染引擎不同（pypdfium2 vs `pdfjs-dist`）不影响定位精度。

## 4. 依赖装配与配置传递

### 4.1 装配点

```
api/app.py:create_app()      → 装配 ports 的真实实现，从环境读连接信息
worker/main.py               → 复用同一装配函数，只是入口不同
tests/conftest.py            → 装配假适配器（内存实现）
```

**为什么装配函数必须唯一**：`api` 与 `worker` 共用同一份装配代码，是「业务代码在两种进程里行为一致」的前提。各写一份，迟早出现「worker 里 MinerU 超时 30 秒、api 里 10 秒」这类只在特定路径暴露的差异。

### 4.2 配置快照的传递路径

```
任务创建（api）
  └─▶ 读 active release + 覆盖项 → 解析成完整值
        └─▶ 写 job_config_snapshot
              └─▶ 队列消息 = { job_id, snapshot_id }      ← 只传 id，不传值
                    └─▶ worker 用 snapshot_id 取配置
```

**为什么消息里只放 `snapshot_id`**：把配置值塞进队列消息，会让「这个任务用的是哪份配置」变成消息体的隐式属性——改一次配置，就可能让同一条消息在重试时用上不同的值。传 id，配置就是不可变的。

**worker 里禁止直接读 active release**：那等于绕过快照，直接破坏可复现性。这条要写进 code review 检查项。

## 5. 跨切面约定

### 5.1 异常与错误码

```
domain/errors.py     TenderError（基类，带 code）
application 用例      抛 TenderError 子类，不关心 HTTP
api/errors.py        唯一一处做 TenderError → HTTP 状态 + 错误码的映射
```

错误码表是契约（见 [05](../设计/05-后端API设计.md) 第 5 节）。

**映射只允许出现在 `api/errors.py` 一处**：散落各处会让同一个错误在不同接口返回不同状态码，前端只能靠猜——而错误码正是前端决定「重试按钮是否可用」的依据。

### 5.2 审计写入点

审计不是「每个接口各写一次」，而是三类固定写入点：

| 写入点 | 内容 |
| --- | --- |
| 下载原件 | 谁 / 何时 / 下载了哪一版 |
| 复核与重跑 | 谁 / 何时 / 对哪个实例做了什么 |
| 配置发布 | 谁 / 何时 / 改了什么 / 为什么 / 影响清单确认 |

**为什么审计写入点要收敛**：审计的价值在于四类日志的留存与检索口径一致（见 [README](../README.md) 决策 32）。散开写会立刻出现字段名不统一、时间戳时区不一致这类问题，等到真要查的时候才发现查不全。

### 5.3 日志字段

全链路串联靠两个 id，**所有日志必须带**：

| 字段 | 含义 |
| --- | --- |
| `job_id` | 一次业务任务（上传 / 解析 / 抽取 / 回放） |
| `request_id` | 一次 HTTP 请求；外部调用回传（`Gotenberg-Trace`）与之对齐 |

`parse_run_id` / `instance_id` 作为上下文补充，用于定位到具体产物。

## 6. 前端架构

### 6.1 数据流边界

| 状态 | 归属 | 理由 |
| --- | --- | --- |
| 服务端数据（项目 / 页面 / 元素 / 结果 / 证据） | TanStack Query | 需要缓存、失效、重试 |
| 当前高亮、缩放、标段筛选 | Zustand | 纯 UI 状态，且缩放 / resize 时要靠它重算 overlay |
| SSE 进度 | Query 的 `setQueryData` 注入 | 避免再引一套状态 |

### 6.2 Query key 设计

```
['project', projectId]
['project', projectId, 'files']
['version', versionId, 'pages']
['version', versionId, 'outline']
['version', versionId, 'evidence-map']        ← 一次拉取，长期缓存
['version', versionId, 'extractions', filters]
['instance', instanceId, 'attempts']
```

**`evidence-map` 为什么必须单独一个 key 且缓存最久**：它是「点击结果秒级定位」的性能基础（见 [05](../设计/05-后端API设计.md) 第 3.6 节）。它的失效条件只有一个——该 version 的 `parse_run` 换了。把它挂在结果列表的 key 下，会导致每次翻页与筛选都重新拉一次几百 KB 的索引。

### 6.3 失效规则

| 事件 | 失效范围 |
| --- | --- |
| 复核 / 修正 / 重跑完成 | `extractions` + `evidence-map` + `attempts` |
| 重新解析完成 | 该 version 下**全部** key（锚点已重建） |
| 上传新文件 / 换内容 | `project.files` + 该 version 全部 key |

**「重新解析完成就全清」这条不能省**：锚点重建后，任何还留在缓存里的旧 bbox 都会把用户带到错误位置，且看起来完全正常。宁可多拉一次，也不要展示一个错的定位。

## 7. 测试策略

### 7.1 分层

| 层 | 工具 | 覆盖对象 | 连外部服务 |
| --- | --- | --- | --- |
| `domain` 单测 | pytest | 锚点解析、bbox 换算、旋转、证据匹配、置信度折扣 | 否 |
| `application` 单测 | pytest + 假适配器 | 用例编排、事务边界、失败补偿、幂等重建 | 否 |
| 适配器集成 | pytest（可跳过） | Gotenberg / MinerU / S3 / PG 的真实调用 | 是 |
| API 契约 | pytest + TestClient | 错误码映射、鉴权、分页 | 否 |
| E2E | Playwright | 点击结果 → 翻页 → 高亮；复核与重跑闭环 | 是（compose 起全套） |

### 7.2 必须测的（不可省）

- **锚点生成与解析**：唯一性、越界、格式异常。
- **bbox 换算**：四个旋转角、非等比缩放、裁剪区域、边界值（0 与 1）。
- **证据校验**：锚点不存在 → 丢弃；quote 子串匹配 → 字符区间正确。
- **门禁**：影响清单未确认 → 激活被拒；回归通过率下降 → 激活被拒。
- **404 率**：任何一条自动结果必须能反查成功。
- **定位链路 E2E**：这是最易回归的功能，也是产品承诺本身。

**为什么锚点与 bbox 要放在「必须测」的最高优先级**：它们是唯一一类「错了不报错、只静默给出错误结果」的代码。业务逻辑写错会抛异常，坐标写错只会把高亮画偏——而用户看到高亮偏一次，就再也不会相信这套系统。
