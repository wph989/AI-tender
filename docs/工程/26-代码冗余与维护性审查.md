## 接口契约统一

分析详情、原始模块记录和正式快照使用明确的 Pydantic 响应模型，只序列化已声明字段。前端的报告、运行账、质量问题、业务记录、独立证据和上下文类型均从 OpenAPI 生成类型派生，界面只增加正文加载、错误及展示条目。

- 原始模块记录要求 `content`、`scope` 和非空 `evidence_ids`，通过 `content_evidence` 保存逐条证据绑定；范围保留原文 `lot_refs`。
- 正式快照记录要求解析后的 `lot_ids` 和独立的完整 `citations`，同时声明关系端点、范围效力及人工裁定。
- 来源身份、运行计数、专题输入变化、研究摘要、质量问题及输出格式均进入生成契约。缺少正文、证据身份或快照范围时，响应验证失败。
- 仓储内部配置和状态不通过响应额外字段进入 HTTP；执行预算仍由既有运行账与端口管理。

实现位置：`apps/api/src/tender/api/shared/responses.py`、`apps/web/src/types/knowledge.ts`。生成入口仍为 `scripts/generate-api-types.py`。

## 草稿分页复用

`get_research_context` 在当前 Agent 图内缓存序列化文本。缓存值保留独立内容快照，原地修改草稿、原文、笔记或自查凭据也会触发更新；删除或取消选中的对象释放对应缓存。缓存不写入检查点，工具入口仍逐次核对权限。

每次计算完整分段数量，只为请求窗口创建单元。草稿与关联原文交错、共享原文去重、完整分段以及 `total/next_offset` 保持一致。

离线探针直接执行当前分页函数和真实 `DraftWorkspace`。样本为40条草稿、160块原文，每块11200字符，默认每页6个单元：

| 指标 | 清理前 | 当前 |
| --- | ---: | ---: |
| 首页构造分段数 | 520 | 6 |
| 首页序列化对象数 | 200 | 200 |
| 下一页序列化对象数 | 200 | 0 |
| 下一页序列化字符数 | 1,811,000 | 0 |
| 完整分段总数 | 520 | 520 |

现有完整分页用例继续验证原文重组和去重；新增四项回归分别验证草稿、原文、笔记和自查凭据修改后的缓存刷新。
