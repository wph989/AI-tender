# 17 · 数据库迁移

> 本文只讲**怎么执行和新增迁移**。表结构的权威是 [03-数据模型与溯源设计.md](../设计/03-数据模型与溯源设计.md) 第 5 节,
> 迁移脚本只是它的可执行副本;防漂移由契约测试盯着,机制见 [10-技术选型与工程结构.md](10-技术选型与工程结构.md) 第 4.5 节。
> 部署参数(数据库地址从哪来)见 [07-部署与实施计划.md](07-部署与实施计划.md) 第 1.1 节。
> `0011` 的业务快照 DDL 见 [设计/14-知识库与综合分析实现](../设计/14-知识库与综合分析实现.md)；新增列不回填历史报告。

## 1. 跑在哪里

**必须在 `apps/api` 目录下执行**——alembic 只在当前工作目录找 `alembic.ini`,换目录会直接报找不到脚本目录。

```powershell
Set-Location G:\aicode\AI-tender\apps\api
```

连接串不写进 `alembic.ini`(`sqlalchemy.url` 是空的),由 `alembic/env.py` 调用
`tender.core.settings.database_url()` 现取。取值优先级是固定的三层:

| 优先级 | 来源 | 用途 |
| --- | --- | --- |
| 1 | 真实环境变量 | 容器与 CI |
| 2 | `apps/api/.env` | 本地开发(`.env.example` 是模板,**已被 .gitignore 排除**) |
| 3 | 代码默认值 | 新 clone 后能直接跑通一次 |

**改 `.env` 立即生效,不用重启**:`database_url()` 是函数不是模块级常量,每次调用重新取值。
命令行临时覆盖用环境变量即可:

```powershell
$env:TENDER_DATABASE_URL = "postgresql+psycopg://tender:tender@localhost:5432/tender"
```

两点容易踩:

- 驱动必须是 **psycopg 3**,URL 前缀写 `postgresql+psycopg://`(不是 `postgresql://`,更不是 `postgresql+psycopg2://`)。
  同一个包同时支持同步与异步:alembic 走同步、应用走异步,不必为迁移再引第二个驱动。
- 迁移要 import `sqlalchemy` / `alembic`,**必须用项目虚拟环境的解释器**:

  ```powershell
  .\.venv\Scripts\python.exe -m alembic upgrade head   # 显式用 .venv
  uv run alembic upgrade head                          # 或交给 uv(会自动 sync)
  ```

## 2. 常用命令

| 目的 | 命令 |
| --- | --- |
| 升到最新(建表 / 增量) | `uv run alembic upgrade head` |
| 看当前库停在哪一版 | `uv run alembic current` |
| 看代码里的最新版(可能是多个 head) | `uv run alembic heads` |
| 看完整迁移链与顺序 | `uv run alembic history --verbose` |
| 只渲染 SQL 不连库 | `uv run alembic upgrade head --sql` |

**`current` 与 `heads` 不一致是正常的**,不是错误:`heads` 是版本库里最靠前的那个脚本,`current` 是目标库
实际执行到的位置。两者不同说明**有一笔待应用的迁移**——升级前先 `current` 确认起点,升级后应等于 `heads`。

`upgrade head` 是幂等的:已经在 head 时是空操作,重复执行不会有副作用。

### 离线渲染

`--sql` 走 `run_migrations_offline()`,只把迁移渲染成 SQL 文本、**不建立任何数据库连接**。
用途是「证明迁移能渲染成合法 SQL」,在没有可用数据库的环境(如 CI 前置检查)里也能跑:

```powershell
uv run alembic upgrade head --sql | Out-File .tmp\migration.sql -Encoding utf8
```

不指定起点时会渲染**整条链**，其中包含 `alembic_version` 更新，不能当作增量脚本应用到已有库。
只审阅某次增量时可显式指定范围，例如：

```powershell
uv run alembic upgrade 0010_analysis_guards:0011_analysis_data --sql
```

离线输出用于审阅；现场仍优先使用 `upgrade head`，由 Alembic 读取目标库的实际起点。

### 回滚

```powershell
uv run alembic downgrade -1              # 回退一步
uv run alembic downgrade 0009_provider_cooldown   # 回退到指定 revision
```

**多数迁移刻意不支持回滚**——`0006` / `0007` / `0008` / `0010` / `0011` / `0012` 的 `downgrade()` 直接 `raise RuntimeError`,
提示「请从备份回滚」。这不是没写完,是有意设计:删掉模型测试历史、运行与证据账、已被引用的配置定义,
会破坏审计与可重放性,而这种损失不体现在当次命令的成败上。**这些迁移的回退路径是数据库备份,不是 alembic。**
`0001`–`0005`、`0009` 有可执行的 `downgrade()`,但同样只应用于确知无历史数据的开发库。

## 3. 迁移链现状

链是线性的(每个脚本只有一个 `down_revision`),代码当前 head = **`0017_document_recovery`**；业务库是否已应用以 `alembic current` 为准：

| Revision | 内容 | 可回滚 |
| --- | --- | --- |
| `0001_initial_schema` | 基线表结构(见 03 第 5 节) | 是 |
| `0002_storage_and_jobs` | 对象存储字段、`job` 表 | 是 |
| `0003_llm_management` | 供应商 / 模型 / 功能绑定三层 | 是 |
| `0004_config_center` | 配置中心表、`job` 派发列 + 配置种子 | 是(种子保留) |
| `0005_knowledge_analysis` | 知识库与综合分析表 | 是 |
| `0006_model_capabilities` | 能力证明与调用账本 | 否,要求备份回滚 |
| `0007_model_inputs` | 模型参数与空间身份 | 否,要求备份回滚 |
| `0008_deepagents_runtime` | 分析运行账本 + 隔离 schema `agent_runtime` | 否,要求备份回滚(附加初始化见第 5 节) |
| `0009_provider_cooldown` | `llm_provider.rate_limited_until` | 是 |
| `0010_analysis_guards` | 追加 5 项解析护栏配置定义 | 否,要求备份回滚 |
| `0011_analysis_data` | 模块业务 JSON、派生标段 ID 和不可变分析快照表 | 否，已有快照可能被下游引用，要求备份回滚 |
| `0012_config_limits` | 放宽模型重试/功能请求与时限 CHECK，登记分析证据块预算 | 否，已发布大预算和新键可能被历史运行引用 |
| `0013_retire_extraction` | 下线固定字段抽取、复核和金标回放 | 否，历史表移除后只能从备份恢复 |
| `0014_analysis_retrieval` | 专题检索阈值与结果上限 | 是，仅撤销配置登记，保留历史快照 |
| `0015_finish_corrections` | 收尾纠正轮数 | 是，仅撤销配置登记 |
| `0016_rate_limit_wait` | 模型限流等待参数 | 是，仅撤销配置登记 |
| `0017_document_recovery` | job 下一执行时间、消息租约及恢复索引 | 是，但会删除调度信息，仅用于隔离开发库 |

以 `uv run alembic heads` 的输出为准,上表只说明各脚本的职责与回滚能力。

## 4. 新增一个迁移

本项目**迁移用裸 SQL 表达,不支持 autogenerate**(`env.py` 里 `target_metadata = None`)。原因是 DDL 的权威
是设计文档而不是模型类:需要精确控制部分唯一索引(`ux_release_active`)、部分索引与外键延迟绑定,
这些表达不出「文档里的语义」。手工同步两份清单迟早漂移,所以由契约测试盯着(见第 6 节)。

```powershell
Set-Location G:\aicode\AI-tender\apps\api
uv run alembic revision -m "一句话说明这次改什么"
```

生成的文件落在 `alembic/versions/`,命名是哈希串,需要**手工改成链上下一个序号 + 描述**的形态,
例如 `0012_xxx_feature.py`,并写清 `revision` / `down_revision`。脚本里建议把 SQL 放进模块级
`_STATEMENTS` 元组再在 `upgrade()` 里逐条 `op.execute(sa.text(...))`——契约测试是按这个形态 import 迁移模块、
读 `_STATEMENTS` 比对的,这样比对的是「迁移真正会执行的 SQL」,改写引号或拆行都不会让测试失效。

约定:

- **不改已应用过的迁移**。`0001_initial_schema` 是已发布基线,新增字段一律用新迁移追加。
- 一次迁移只做一件事;`upgrade()` 里的执行顺序按外键依赖排,不按章节顺序(0001 就把两处互相引用的外键
  延后成 `ALTER TABLE ... ADD CONSTRAINT`,原因写在那个文件的 docstring 里)。
- **先写 `downgrade()` 的意图**:能安全回滚就写反操作,不能就在 `downgrade()` 里 `raise RuntimeError`
  说明「为什么必须从备份回滚」,不要留成空实现——空实现会让误回滚静默丢数据。
- 迁移文件的 docstring 用一句话说清这次改动的**原因**,与提交信息同口径。

## 5. 两种部署跑法

**宿主机跑进程**(本项目实际使用的方式,见根目录 `本地启动指南.md` 第 2 节):

```powershell
Set-Location G:\aicode\AI-tender\apps\api
uv run alembic upgrade head
```

**全容器**(仓库根 `docker-compose.yml`):`migrate` 是一次性服务,挂在 `app` profile 上,
`api` / `worker` / `beat` / `web` 全部 `depends_on: migrate: condition: service_completed_successfully`。
迁移失败会**直接中断整组启动**,而不是让 api / worker 跑在半旧半新的表结构上。

```powershell
Set-Location G:\aicode\AI-tender
docker compose --profile app up -d --build
```

容器里读的是**仓库根 `.env`**(`docker compose` 只读那一份),宿主机跑进程读的是 `apps/api/.env`;
两者同名同义、互不影响。

### `0008` 的附加步骤:初始化 checkpoint 表

`0008_deepagents_runtime` **只建业务表和隔离 schema,不建 LangGraph 的 checkpoint 表**。
框架侧 DDL 由部署阶段显式初始化,`uv run alembic upgrade head` 之后还要跑一次:

```powershell
Set-Location G:\aicode\AI-tender\apps\api
uv run python -m tender.adapters.pg.analysis.checkpoints
```

为什么不能塞进迁移:`AsyncPostgresSaver.setup()` 的 DDL 含 `CREATE INDEX CONCURRENTLY`,
必须在 autocommit 连接里执行,**嵌进 alembic 事务会直接失败**。该命令自带
`pg_advisory_lock`,可重复执行;worker 没有任何隐式建表路径,漏跑这步的表现是分析运行时找不到 checkpoint 表。

## 6. 改完迁移必须同步的两件事

迁移不是唯一事实源,改完要跟上两侧,否则测试立刻变红:

- `apps/api/tests/contract/test_ddl_matches_docs.py` 的 `_MIGRATIONS` 映射表:新增迁移在这里加一行,
  指明它对应哪个设计文档的哪个 `sql` 代码块(文件名 + 块序号),比对逻辑本身不用改。
  它从文档和迁移两侧各解析一次表名 / 列名 / 索引名再比对,**任何一侧漏改都会失败**。
- `apps/api/tests/contract/test_config_items_match_migration.py`:有配置种子的迁移(`0004` / `0008` / `0010`)
  要同时改 `tender/config/schema.py` 的 `ITEMS`,测试会逐项比对键、层、类型、默认值、描述与门禁标记。

跑法:

```powershell
Set-Location G:\aicode\AI-tender\apps\api
uv run pytest tests/unit tests/contract -q --tb=short
```

这一层不需要真实数据库,是提交前的最低验证。涉及真实 PostgreSQL 的用例用 `TENDER_RUN_DB_TESTS=1` 显式开启,
且跑在隔离 schema 上,不碰业务数据。

## 7. 常见坑

- **`alembic.ini` 必须保持纯 ASCII**。alembic 用 `encoding="locale"` 读它,中文 Windows 上是 GBK,
  文件里出现任何一个非 ASCII 字节,所有 alembic 命令都会在加载配置阶段就 `UnicodeDecodeError`,
  根本走不到 `env.py`。中文说明写在 `alembic/env.py` 里(那条注释本身就是提醒)。
- **`.env` 用 `utf-8-sig` 读**:Windows 记事本保存会加 BOM,带 BOM 时键名会变成 `\ufeffDATABASE_URL`,
  表现为「明明配了却没生效」。
- **不要在 `apps/api` 之外的目录执行**:找不到 `alembic.ini`,报错信息看起来像脚本目录缺失。
- **不要手工改历史报告或已发布配置来「修好」迁移差异**:`0010` 的 `downgrade()` 抛异常、运行时版本门禁
  拒绝执行旧协议报告,都是有意设计的行为边界。
- **`current` 落后于 `heads` 时不要跳过迁移直接重启服务**:`0010` 之前新增的配置键在页面与审计里读不到,
  会表现为「配置项缺项」而非报错。
- **v3 运行时需要 `0011`**：新代码会读取和写入 `analysis_module.business_data`、
  `analysis_report.derived_lot_ids` 和 `analysis_data_snapshot`，不能只重启而不迁移。

## 8. 现场启用顺序

需要新迁移生效时,按这个顺序,不要只做其中一步:

1. `Set-Location G:\aicode\AI-tender\apps\api`
2. `uv run alembic current` 确认起点,`uv run alembic heads` 确认目标
3. `uv run alembic upgrade head`
4. 若跨过了 `0008`,补跑 `uv run python -m tender.adapters.pg.analysis.checkpoints`
5. **重启 API 与 worker**——进程里缓存的配置注册表与 schema 信息不会随迁移自动刷新
6. 涉及解析协议变更时,重新发起分析生成新报告;已有报告不会自动改写

从 `0010` 升到 `0011` 无需再次初始化已存在的 checkpoint 表。正式启用前先完成备份，
再迁移、重启 API/worker，并用新报告检查多标段、公共条款、补遗及证明材料。
测试可使用 `tests/integration/data_schema.py` 在私有表内安装增量，无需提前迁移业务库；
这不代表真实模型的解析质量已验收。


### 0012 配置限制启用

DDL 见 [12-LLM管理与模型路由](../设计/12-LLM管理与模型路由.md) 第 12 节。先备份并迁移至 0012，再启用 API/worker/beat 与新版页面；否则大预算会被旧数据库 CHECK 拒绝，新增配置登记也会缺失。beat 需要重载才能从固定 5 秒改为每秒唤醒，再按配置派发。

只审阅本次增量：`uv run alembic upgrade 0011_analysis_data:0012_config_limits --sql`。若业务库仍在 0010，现场升级还会先执行 0011。本轮只验证隔离 schema 和离线 SQL，未迁移业务库。


## 6. 文档恢复调度升级（0017）

先应用 `0017_document_recovery`，再加载新版 API、Worker 与 Beat。新版轮询投递到 `poll`，
部署必须同时消费 `tender`、`convert,parse`、`poll`、`analysis`，具体命令见根目录本地启动指南。
未更新消费者时，消息会排队而不会被旧解析 Worker 消费。迁移不回填执行预算、不重置历史解析任务，
旧任务由空租约进入恢复扫描；已获远端任务 ID 的任务继续轮询，提交结果不明的任务按既有失败分支
要求人工核对，不能自动重提。数据库和 broker 之间仍不是原子提交，重复消息依靠任务锁与阶段判断收敛。

本轮验证使用独立 PostgreSQL 测试实例；业务库尚未由本轮迁移或重启。
