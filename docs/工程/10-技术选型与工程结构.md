# 10 · 技术选型与工程结构

> 本文回答两个问题：**用什么技术**、**代码怎么组织**。
> 版本号为 2026-09-26 实测值；未实测到的只给大版本约束，实施时以 `uv.lock` / `pnpm-lock.yaml` 锁定为准。

## 1. 选型原则

所有选型必须服从这五条，冲突时按序取舍：

1. **溯源优先**——任何技术不得削弱"结果可定位到原文"的能力。这条直接否决了所有"只能预览、不能精确定位"的方案（如 kkFileView / Office Online）。
2. **长任务优先**——解析是分钟级任务，异步、可重试、可恢复是第一位的；同步阻塞的设计一律不要。
3. **适配器隔离**——MinerU / Gotenberg / LLM 三者都在快速迭代（MinerU 4.0 相对 2.x 已是不兼容变更），版本差异必须锁死在适配器内部，业务代码只依赖自有领域模型。
4. **可离线**——全部依赖能内网部署，无外部 SaaS。
5. **克制**——不为"先进"支付复杂度。能用单进程解决的不上微服务，能用一张表解决的不上消息中间件。

## 3. 逐项选型论证

### 3.1 前端框架：Next.js vs Vite SPA

| 方案 | 结论 |
| --- | --- |
| **Next.js** | ✅ 采用。内网部署需要 SSR/服务端路由；文件类型路由天然适配"项目 → 文件 → 页面"的层级 |
| Vite + React SPA | 更轻，但需要自己搭路由与构建配置；本项目页面结构简单，收益不明显 |
| Remix / React Router 7 | 能力相当，生态与团队熟悉度不如 Next.js |

> 注意：**不做纯静态导出**。工作台需要服务端注入租户上下文与权限信息。

### 3.2 PDF 渲染：pdfjs-dist（定论）

已在 [06-前端展示与定位.md](../设计/06-前端展示与定位.md) 论证过，此处只记结论：

- **必须能控制 `getViewport()` 与 textLayer**——这否决了 `react-pdf` 等封装层较厚的库。
- 中文 PDF 的 textLayer 字符宽度计算不总是精确，**第一版只做 bbox 矩形高亮**，字符级高亮仅作增强。
- 缩放/旋转必须显式传 `rotation: page.rotate`，与后端"视觉方向 bbox"契约对齐。
- **用 legacy 构建**（`pdfjs-dist/legacy/build/pdf.mjs` + 同目录 `pdf.worker.min.mjs`）：pdfjs 6.x 的现代构建直接用
  `Map.prototype.getOrInsertComputed`，2026-09 实测 Chrome 142 直接抛 `not a function`，一页都渲染不出来；
  legacy 构建自带该方法 polyfill。内网桌面的浏览器版本不可控，这里按最坏情况选。

### 3.3 状态管理：TanStack Query + Zustand

- **服务端状态**（项目、页面、元素、结果、证据）→ TanStack Query。证据索引一次拉取后长期缓存，正好用它的 `staleTime` 模型。
- **客户端状态**（当前高亮、缩放、当前标段筛选）→ Zustand。**不引入 Redux**：本项目没有复杂的跨模块状态机。
- **关键约束**："当前高亮"必须存在状态里而不是画完即忘——缩放/resize 时要靠它重算 overlay（见 06 文档第 6 节）。

### 3.4 后端框架：FastAPI vs Django vs Litestar

| 方案 | 结论 |
| --- | --- |
| **FastAPI** | ✅ 采用。原生 async（解析任务全是 IO 等待）、Pydantic 深度集成（**同一套模型既做 API 校验也做 LLM 输出 Schema**，这是关键复用）、OpenAPI 自动生成 |
| Django + DRF | ORM/Admin 更强，但异步支持与 schema 复用不如 FastAPI；本项目不需要 Admin |
| Litestar | 性能更好，但生态与团队熟悉度不足 |

> 选 FastAPI 的**决定性理由**是 Pydantic：抽取 Agent 的 JSON Schema 约束（`evidence` 必填、锚点正则）和 API 请求校验用的是同一套类型定义，改动只需改一处。

### 3.5 任务队列：Celery vs Arq vs Dramatiq

| 方案 | 结论 |
| --- | --- |
| **Celery** | ✅ 采用。多队列 + 优先级 + 定时任务 + 运行时并发调整（远程控制） |
| Arq | 更轻、原生 async，但缺少成熟的优先级与调度能力 |
| Dramatiq | 介于两者之间，生态不如 Celery |
| 自研 | 不可取——重试、死信、可见性超时这些坑不值得自己踩 |

#### 3.5.1 Celery 的动态并发能力（已核实）

Celery **可以**在运行时调整并发，有两条机制（源码 `celery/worker/control.py`）：

| 机制 | 命令 | 适用池 | 约束 |
| --- | --- | --- | --- |
| `pool_grow` / `pool_shrink` | `app.control.pool_grow(n)` | prefork / gevent / eventlet | **与 autoscale 互斥**；thread / solo 池不支持 |
| `autoscale` | `app.control.autoscale(max, min)` | 需启动时启用 `--autoscale` | 仅修改自动伸缩的上下界 |

**但有四个结构性约束**：

1. **与 autoscale 互斥**——启用 autoscale 后 `pool_grow`/`pool_shrink` 直接返回错误（源码原文：*"pool_grow is not supported with autoscale. Adjust autoscale range instead."*）。
2. **池类型限制**——thread / solo 池不支持。
3. **依赖 broker 远程控制**——Redis / RabbitMQ 支持，SQS 不支持。
4. **语义是"每个 worker 的并发"，不是"集群总并发"**——多副本时总并发 = 副本数 × 单副本并发；改配置要广播给队列内所有 worker，**无法表达"整个集群最多 4 个在途"**，队列里已有 N 个 worker 时实际生效值不确定。

#### 3.5.2 更根本的问题：并发上限绑错了对象

把上限绑在 **worker 进程数**上，限的是"本机同时处理多少个任务"；而我们真正要限的是**同时发往外部服务的在途请求数**。两者没有必然关系：

- 若任务表现为"提交 MinerU job 后轮询 5 分钟"，并发 16 意味着 16 个进程被长时间占住——**但对 GPU 的实际压力可能只有 2**（MinerU 内部自己排队）。
- 若任务改成"提交即返回"的短任务，同样 16 个进程能以极高吞吐提交，**反而需要更严格的闸门**。

同一种"进程数"对应完全不同的外部压力。因此：

> **闸门前移到提交侧，worker 池固定。**

#### 3.5.3 采用的设计

**（1）长短任务拆分**——worker 槽永不被"等待"占住：

```
submit_parse : 提交 MinerU job（202 立即返回）→ 记 job_id → 调度一次 poll → 结束
poll_parse   : 单次查询；非终态则用 countdown 重排自己（指数退避 2s → 30s）
```

**（2）周期调度器读配置**——这就是"动态并发"的实现方式：

```
beat: dispatch_pending（每 5 秒）
  ├─ 读当前配置的 in-flight 上限
  ├─ 统计当前在途数
  └─ 只提交差额个数的任务
```

**每次 tick 都重新读配置** → 改完配置下一个 tick 生效（≤5 秒），**不需要动 worker 池、不需要重启任何进程**。

**（3）三条队列的落地**

| 队列 | 限制的对象 | 实现 |
| --- | --- | --- |
| `parse` | MinerU 侧处于 `queued` + `running` 的 job 数 | **DB 计数即可**（提交即返回，不占槽） |
| `convert` | 同时在途的 Gotenberg 请求数 | **同步 HTTP 调用 + Redis 分布式信号量**；webhook 留到后续阶段（转换 P95 持续 > 2 分钟时评估） |
| `extract` | 同时在途的 LLM 请求数 | Redis 信号量 |

**（4）信号量与动态调整**

调度器在任务交给 worker 前获取转换/抽取许可，只有拿到许可的任务才会派发，避免 worker 占槽等待信号量。worker 完成外部请求后释放许可。

- 配置上调：下一次调度 tick 开始按新上限派发。
- 配置下调：不取消已在途请求，只暂停新派发，直到在途数低于新上限。
- worker 池只需覆盖部署的资源上限；运行时流量由 `max_inflight` 控制，不依赖 `pool_grow` / `pool_shrink` 改变 Celery 并发。
**（5）配置项命名要求**

名称必须表达"在途上限"而非"进程数"，避免语义混淆：

| 易误解的命名 | 采用 |
| --- | --- |
| `worker.convert.concurrency` | `convert.max_inflight` |
| `worker.parse.concurrency` | `parse.max_inflight` |
| `worker.extract.concurrency` | `extract.max_inflight` |

**（6）队列拆分真正解决的问题**

| 队列 | 并发模型 | 瓶颈 |
| --- | --- | --- |
| `convert` | 高并发 | Gotenberg 副本数 |
| `parse` | 低并发 | GPU 显存（`max_inflight` 建议不超过 GPU 数 × 2） |
| `extract` | 中并发 | LLM 网关速率限制 |
| `regression` | 低优先级 + 夜间窗口 | 回归回放，与交互任务隔离 |

三类任务的资源瓶颈完全不同，混在一个队列会互相阻塞——这是拆队列的真正理由。

### 3.6 数据访问：SQLAlchemy 2.0 + Alembic

- 需要**部分唯一索引**（`CREATE UNIQUE INDEX ... WHERE status='active'`）与**部分索引**（`WHERE deleted_at IS NULL`）——从数据库层面保证"同一项目只有一个 active 配置"这类不变量，比应用层加锁可靠。
- 需要 `JSONB`（配置值、报告）与 `GIN`（元素文本检索）。
- 需要 `NUMERIC(7,6)` 存归一化坐标——**绝不能用 float**，坐标比较与序列化都会引入误差。
- 使用 SQLAlchemy 2.0 的 **typed declarative** 风格，让 `Mapped[...]` 与类型检查器协作。

> 不用 SQLModel：它把 Pydantic 与 ORM 揉在一起，而我们的领域模型需要与 ORM 解耦（见 4.2）。

### 3.7 LLM 接入：直接用 SDK，不用编排框架

| 方案 | 结论 |
| --- | --- |
| **官方 `openai` SDK 指向自建网关** | ✅ 采用。我们只需要 chat completions + JSON Schema 结构化输出，这是原生能力 |
| LangChain / LlamaIndex | ❌ 不采用。本项目的编排逻辑（两遍式抽取、双路投票、二次抽取、四道校验）是**业务特有的**，抽象层反而会挡住对请求/响应的精确控制与成本核算 |

**理由**：编排框架的价值在于屏蔽多种数据源与工具调用的差异。而我们的调用形态高度单一（结构化抽取），引入框架只会增加调试难度与不透明的 token 消耗。

### 3.8 结构化输出：Pydantic 生成 JSON Schema，强制 `evidence`

这是全系统最关键的一处工程约束，见 [04](../设计/04-解析流水线与抽取Agent.md) 第 4.2 节。要点：

- `evidence` 用 JSON Schema 的 `pattern: "^p\\d+b\\d+$"` + `minItems: 1` 锁死 → **模型在协议层面返回不了无效引用**。
- 提供 `not_found` 作为合法出口，避免模型为满足必填字段而编造。
- 用 mode=strict 的结构化输出（网关需支持）。

### 3.9 对象存储

MinIO，S3 协议。分层布局见 [03](../设计/03-数据模型与溯源设计.md) 第 6 节。要点：

- 按内容哈希寻址的层（`originals/` / `converted/`）天然去重，永久保留。
- 按版本寻址的层（`render/` / `mineru/`）随版本清理。
- **MinerU 原始产物必须归档**——schema 跨大版本不兼容，没有原始产物就无法回溯历史结果是如何产生的。

### 3.10 可观测性

| 需求 | 方案 |
| --- | --- |
| 全链路串联 | `job_id` / `request_id` 贯穿 API → Worker → Gotenberg（`Gotenberg-Trace`）→ MinerU |
| 结构化日志 | structlog，字段化输出，便于按 job 检索 |
| 指标 | Prometheus + Grafana |
| 追踪 | OpenTelemetry（可选，二期） |

**必须告警的两个指标**（见 [07](07-部署与实施计划.md) 第 4 节）：

1. 证据反查 404 率 > 0 —— 溯源能力已破损，最高级别。
2. 页面尺寸一致性断言失败率 > 0 —— 渲染基座错位，高亮会整体漂移。

### 3.11 服务端 PDF 引擎：pypdfium2（许可驱动）

| 方案 | 许可 | 结论 |
| --- | --- | --- |
| **pypdfium2** + Pillow | Apache-2.0 / BSD-3（PDFium）+ HPND | ✅ 采用 |
| PyMuPDF（`fitz`） | AGPL-3.0 或商业授权 | ❌ 排除 |
| pdf2image（poppler） | 需外部 CLI 进程 | 备选 |

职责：读取每页几何（`width_pt` / `height_pt` / `/Rotate`）与文本层情况；按 block 的归一化 bbox 裁剪局部图（`render.crop_dpi`）供多模态抽取。

**不渲染整页图**——在线预览由前端 `pdfjs-dist` 直接渲染 PDF 基座（Range 流式加载），整页位图既没有消费方，又要付出全量渲染与长期存储的代价（见 [06](../设计/06-前端展示与定位.md) 第 3 节）。

**为什么排除 PyMuPDF**：它是 AGPL-3.0。AGPL 第 13 条对「通过网络提供服务」有传染性要求，而本系统正是内网 Web 服务——用户通过浏览器访问即触发该条款。内部系统未必真会被追责，但没有必要为一份渲染功能承担这个不确定性。

**为什么选 pypdfium2 而不是 poppler**：poppler 要另起 CLI 进程、走临时文件，多一层 IO 与临时文件清理负担；pypdfium2 在进程内直接返回位图缓冲，交给 Pillow 编码即可。

> **前端渲染引擎（pdfjs-dist）与后端 PDF 引擎（pypdfium2）不同，不影响定位精度**：定位依赖的是归一化 bbox 与 PDF 页面几何（宽高、旋转角），二者与渲染引擎无关。两者的一致性由「`width_pt/height_pt` 与 PDF.js 视口尺寸偏差 ≤1%」的断言守卫（见 [05](../设计/05-后端API设计.md) 第 3.2 节），坐标换算由领域层的纯函数负责（见 [11](11-架构设计.md) 第 2.2 节）。

## 4. 工程结构

### 4.1 仓库布局

```
AI-tender/
├── apps/
│   ├── api/                    # Python 后端（API + Worker + Scheduler 同代码库）
│   └── web/                    # Next.js 前端
├── packages/
│   └── contract/               # 跨语言契约的共享事实源（坐标/锚点测试向量）
├── docs/                       # 本设计文档集（索引见 docs/README.md）
├── docker/
│   ├── gotenberg/              # 官方镜像 + 中文字体
│   └── mineru/                 # 预置模型，运行时不联网
├── scripts/                    # 运维与验证脚本（含阶段 0 的坐标验证脚本）
├── pnpm-workspace.yaml
└── docker-compose.yml
```

**为什么 API / Worker / Scheduler 同代码库、不同进程**：三者共享全部领域模型与适配器，拆成两个仓库会立刻产生版本同步问题。同一个镜像、三个启动命令即可（见 [11](11-架构设计.md) 第 1.1 节）。

**为什么有 `packages/contract/`**：`domain/bbox.py` 与 `lib/coords/bbox.ts` 是同一个契约在两种语言里的两份实现——这是全项目唯一必须重复的逻辑。重复必然漂移，所以把测试向量抽出来共享（见 4.5）。

### 4.2 后端目录树

```
apps/api/
├── pyproject.toml
├── alembic.ini
├── alembic/
│   └── versions/                        # 迁移脚本，与 03 的 DDL 一一对应
├── src/tender/
│   ├── domain/                          # ① 纯领域：无框架、无 IO、无 DB
│   │   ├── anchor.py                    #    锚点解析与拼装（p12b5）
│   │   ├── bbox.py                      #    坐标契约与变换（归一化 ↔ 像素）
│   │   ├── page.py                      #    PageGeometry：宽高 + 旋转 + 视口换算
│   │   ├── element.py                   #    块类型、层级、父子关系
│   │   ├── fields.py                    #    字段定义（单值/多值/表格）+ JSON Schema 生成
```

**三个容易走样的地方，提前定规矩**：

1. `adapters/pg/models/` **不是**领域模型。SQLAlchemy 模型带 `Mapped[]` 声明与关系属性，把它当领域对象用，等于让持久化细节渗进业务逻辑——最典型的表现是"改一个字段名要同时改业务代码"。

3. `worker/tasks/` 一个文件对应一条队列，`poll.py` 单独存在——轮询是自重排任务，不与提交任务混在一起（见第 3.5 节）。

### 4.4 依赖方向约束

后端（**只能向内**：`domain` ← `application` ← `adapters`/`api`/`worker`）：

| 目录 | 允许 import |
| --- | --- |
| `domain/` | 仅标准库 + `pydantic` |
| `application/` | `domain` + `ports` |
| `adapters/` | `domain` + `ports` + 第三方库 |
| `api/` / `worker/` | `application` + `adapters` + `config` |

前端补充两条：

| 目录 | 约束 |
| --- | --- |
| `lib/coords/` | 只有纯函数，禁止 import React、fetch、任何组件 |
| `lib/api/generated/` | 只允许被 `lib/api/client.ts` 与 `lib/query/` 引用 |
| `components/ui/` | 禁止引用 `lib/query/`——通用组件不直连数据 |

**用 import-linter 在 CI 中强制后端的约束**。规则一旦靠自觉遵守，三个月后必然破防。

五条契约（分层只能向内、用例不依赖实现、api/worker 互不依赖、domain 与 core 的纯度）写在 `apps/api/pyproject.toml` 的 `[tool.importlinter]` 里，本地随时可验：

```bash
cd apps/api
uv run ruff check      # Lint + import 顺序
uv run lint-imports    # 分层依赖方向
uv run pytest -q       # 测试（含「文档 ↔ 迁移」的 DDL 一致性）
```

后端已改为**可安装包**（`uv sync` 会把 `tender` 以 editable 装进 `.venv`），所以这三条命令都不需要手工设 `PYTHONPATH`——import-linter 必须能真 import 到 root package 才能扫描。

### 4.5 跨语言契约：唯一允许的重复

`domain/bbox.py` 与 `lib/coords/bbox.ts` 是同一套坐标规则的两份实现。后端要算（写库、裁剪、校验），前端也要算（画高亮、缩放重算），这是全项目唯一必须重复的逻辑。

重复必然漂移，所以把**测试向量**抽成共享事实源：

```
packages/contract/
├── coords-vectors.json     # 输入 + 期望输出，两侧共用
└── README.md               # 说明如何新增向量、改契约时的流程
```

- 后端 `tests/contract/test_coords_vectors.py` 消费它；
- 前端 `src/lib/coords/__tests__/vectors.test.ts` 消费同一个文件；
- **任何一侧改动坐标规则，必须同步更新向量**，否则另一侧的测试立刻变红。

**为什么不在前端只做乘法，把换算全交给后端**：高亮要在缩放、resize、旋转时实时重算（见 [06](../设计/06-前端展示与定位.md) 第 6 节），每次往返后端会明显卡顿。而且「只做乘法」这个说法在旋转页上不成立——旋转换算本身就是逻辑，不是乘法。

**为什么不用 WASM 共享同一份实现**：为一组四则运算引入 WASM 工具链，构建复杂度与调试成本远大于收益。共享测试向量能达到同样的防漂移效果。

## 5. 关键接口定义

```python
# ports/converter.py
class OfficeConverter(Protocol):
    async def to_pdf(
        self, src: BinaryIO, *, filename: str, trace_id: str
    ) -> ConvertResult: ...

# ports/parser.py
class DocumentParser(Protocol):
    async def submit(
        self,
        pdf_key: str,
        *,
        pdf_sha256: str,
        ocr_mode: str = "auto",
        tier: str = "standard",
    ) -> ParseSubmission: ...
    async def poll(self, job_id: str) -> ParseJobStatus: ...
    async def fetch_middle_json(self, job_id: str) -> MiddleJson: ...
    async def health(self) -> bool: ...

# ports/llm.py
class LlmClient(Protocol):
    async def extract(
        self, *, chunk: str, schema: dict, field_key: str
    ) -> ExtractionResult: ...

# ports/blob.py
class BlobStore(Protocol):
    async def put(self, key: str, data: bytes | BinaryIO) -> str: ...
    async def get(self, key: str) -> bytes: ...
    def presign(self, key: str, ttl_seconds: int) -> str: ...
```

**注意每个方法的签名都刻意不含 MinerU / Gotenberg 的 HTTP 结构**。`ParseSubmission` 返回 MinerU 版本与有效配置快照，
提交成功后应与 `job_id` 一起持久化。`poll` 映射 MinerU 状态；
`poll` 或 `fetch_middle_json` 遇到进程内索引 404 时，
适配器抛出 `ServiceRestarted`，由用例层从 `document_version` 读取 PDF key 与 SHA-256 后重新调用 `submit`，借 MinerU 秒传恢复。

## 6. 编码约定

| 项 | 约定 |
| --- | --- |
| 包管理 | 前端 **pnpm**（禁止 npm/yarn）；后端 `uv` |
| 文件编码 | **UTF-8（无 BOM）** |
| 唯一例外 | `apps/api/alembic.ini` **必须纯 ASCII**：alembic 用 `encoding="locale"` 读它（中文 Windows 上是 GBK），任何非 ASCII 字节都会让所有 alembic 命令在加载配置时就崩，中文说明放在 `alembic/env.py` 里 |
| 注释语言 | **中文** |
| 注释内容 | **写明"为什么这样写"**，不写"做了什么"。例如"这里必须显式传 rotation，否则扫描件高亮会横过来" |
| 坐标类型 | 后端 `NUMERIC(7,6)`，前端 `number`，**禁止 float32 转换** |
| 错误处理 | 领域错误用 `domain/errors.py` 的类型；适配器把第三方错误码翻译成领域错误（如 MinerU 的 `413`/`400` 都映射为 `UploadSizeMismatch`） |
| 时间 | 一律 UTC 存储，前端本地化展示 |
| 幂等 | 一切对外部系统的提交必须可安全重放（MinerU **没有幂等键**，必须自己持久化状态） |

## 7. 版本策略

- **MinerU 锁定 `>=4.0,<5`**——4.0 相对 2.x 已是不兼容变更，跨大版本必须重跑回归。
- **Gotenberg 锁定具体版本号**并记录在 `document_version.converter_version`——转换参数变更会改变分页，进而影响溯源。
- **pdfjs-dist 锁定次版本**——渲染行为变化会影响高亮对齐。
- 其余依赖由 `uv.lock` / `pnpm-lock.yaml` 锁定，CI 使用 frozen 模式安装。

## 8. 不做的事（与选型同等重要）

| 不做 | 理由 |
| --- | --- |
| 不引入 LangChain 类编排框架 | 编排逻辑是业务特有的，框架会挡住对请求/成本的精确控制（见 3.7） |
| 不引入 Redux | 客户端状态简单，Zustand 足够（见 3.3） |
| 不上微服务 | 三个外部服务已经是黑盒 HTTP，应用侧再拆只会增加运维成本 |
| 不用 float 存坐标 | 归一化坐标必须精确可比（见 3.6） |
| 不做纯静态前端导出 | 工作台需要服务端注入租户上下文与权限 |
| 不自己实现 PDF 渲染 | pdfjs-dist 是唯一合理选择（见 3.2） |
| 不用 Univer 等表格/办公套件做在线预览 | 它们渲染的是自有数据模型，没有「原文档某块落在哪一页哪个坐标」的概念，扫描件无法显示；预览基座一旦与解析基座分叉，定位闭环直接失效（见 3.2）。若将来要做「报价清单在线填报」，才是它的适用场景 |
