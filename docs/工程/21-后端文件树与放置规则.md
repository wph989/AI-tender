# 21 · 后端文件树与放置规则

更新日期：2026-11-14。

本文是后端新增、移动文件时的放置依据。一级目录表达架构职责，业务层内部再按业务模块分类。`service`、`crud`、`agent` 是职责名称，不另建并列架构层。

架构含义、设计取舍、真实执行流程和现有限制见 [11-当前后端架构与设计取舍](11-架构设计.md)。本文侧重文件放置，不将目录完整性等同于实现完全解耦。

## 1. 组织原则

- 已确认的业务模块统一建目录，即使当前只有一个文件。这让新增功能的归属稳定、跨层检索一致；不为尚未出现的业务创建空目录。
- API、用例、仓储端口和仓储实现使用同一组业务名称：`projects`、`documents`、`knowledge`、`analysis`、`llm`、`configuration`、`jobs`。
- `shared/` 只放多个业务实际共用的代码，不接收暂时不知道放哪里的业务逻辑。
- `core/`、现有 `config/`、数据库连接/锁、ORM 表定义按技术职责组织。它们已有明确职责，不再机械嵌套一层业务目录。
- 包的 `__init__.py` 保持轻量，调用者显式导入具体模块。不用兼容转发包掩盖旧路径，也不为目录对称复制实现。

| 职责 | 位置 |
| --- | --- |
| HTTP 入口 | `api/<业务>/` |
| 业务用例、Agent 编排 | `application/<业务>/` |
| 仓储与事务接口 | `ports/repository/<业务>/` |
| SQL、锁、事务实现 | `adapters/pg/repositories/<业务>/` |
| 模型、文档、配置、存储、任务等外部端口 | `ports/<业务>/` |
| 外部服务实现 | `adapters/<业务>/`；PostgreSQL 实现在 `adapters/pg/` 内 |
| 领域规则 | `domain/<业务>/`；跨业务规则在 `domain/shared/` |
| 异步任务 | `worker/<业务>/`；调度和进程入口留在 worker 根目录 |
| 装配依赖 | `core/di.py` |

解析调用的职责沿用上述边界：单专题Agent工具循环放在`application/analysis/skill_agent.py`，草稿版本、自查凭据及最终提交一致性放在`drafts.py`，工作方法在`resources/parse_skills/analysis_workflow/SKILL.md`。生产链路不调用独立审查；旧`review.py`和`topic_flow.py`保留历史兼容测试。模型调用、幂等结算、租约和工具状态联合事务仍经既有端口与`core/di.py`接入PostgreSQL运行仓储，Agent和Worker不直接执行SQL。

知识库与报告有关联，但归属仍然明确：`api/knowledge/routes.py` 负责资料、检索与问答，`api/analysis/routes.py` 负责报告。`application/knowledge/content.py` 是知识处理函数，`service.py` 是管理流程。报告查询归入 `analysis/reports.py`，嵌入与重排模型配置查询归入 `llm/retrieval.py`；`KnowledgeStore` 组合这些查询能力，继续承载知识来源与报告快照的联合事务。业务用例分别依赖 sources、retrieval、management、execution、reports 等窄端口；组合端口仅供装配。`analysis/runtime.py` 管运行账，不为了接口拆分复制 SQL 或共享事务。

原文补读通过 `sources.py` 的 `ChunkWindow` 契约传入 offset/limit。入库前由 `domain/knowledge/text.py` 合并条款大块及各页真实坐标，检索、分析与定位统一使用大块ID；有效索引在数据库中按大块序号取窗口。未建成当前版本索引时复用同一领域流式规则，读到窗口后一块即停止，不为总数额外扫描全文。历史attempt恢复沿用已交付的小块身份，重新解析使用当前大块版本。

## 3. 依赖与事务边界

代码依赖的主要方向为 `api/worker → application → ports → domain`；Worker 也可直接调用端口完成任务生命周期操作。这不是每个请求的执行顺序：用例直接调用注入的具体对象，`ports` 定义契约而不转发请求。`core/di.py` 负责用例、仓储、任务锁与网关装配，Worker 不再直接使用 ORM 或 PostgreSQL 适配器。Worker 仍有非数据库客户端的局部装配；`config/registry.py`、`snapshot.py` 保留配置基础设施实现。详见工程11。

- 用例构造函数接收仓储、网关和配置端口，不接收 Engine，也不自行创建具体仓储。不导入 `api`、`worker`、`adapters` 或 `core.di`。
- 用例可复用配置纯规则 `config/schema.py`、`config/gate.py` 和通用工具；配置读取依赖 `ports/configuration/registry.py`，不直接引用具体 ConfigRegistry。
- API 只解析请求、调用用例、转换响应。`api/shared/errors.py` 保留既有数据库完整性异常到 HTTP 的兜底映射，它不执行 SQL。
- 报告、索引与问答的业务准备、执行、校验和收敛放入 `application/<业务>/execution.py`，模型路由工厂放 `application/llm/factory.py`；Worker 只接入消息、锁、调度与已装配用例。
- Worker 的数据查询、状态更新和事务放入对应 `adapters/pg/repositories/<业务>/`；入口通过端口调用。禁止直接导入 SQLAlchemy、`adapters.pg`、`config.registry` 或 `config.snapshot`，不以“任务内部使用”为由绕过边界。
- 用例通过 `with repository.transaction()` 决定原子操作范围；真实连接、锁、提交与回滚留在仓储。任务配置快照通过事务端口 `snapshot_for_job()` 与任务行同事务写入。
- 新增文档执行参数应同步 `config/schema.py::document_execution_snapshot` 和任务创建入口；读取已冻结参数走文档流水线仓储。派发并发/间隔继续经 `ConfigReader` 读取当前值，详细生效规则见工程11第9节。
- 业务之间可以通过明确的用例或端口协作，不为消除所有跨业务导入而复制代码，也不把相关功能全部挪入 shared。

## 4. 新功能放置示例

新增项目操作时，依次检查：

1. HTTP 参数与响应：`api/projects/routes.py`；文件操作入口在 `api/projects/files.py`。
2. 业务判断与流程：`application/projects/service.py` 或 `files.py`。
3. 所需数据操作协议：`ports/repository/projects/projects.py` 或 `files.py`。
4. SQL 与事务实现：`adapters/pg/repositories/projects/` 下对应文件。
5. 新依赖在 `core/di.py` 注入。优先扩展已有仓储，避免同一数据访问出现多个入口。

同一业务下文件按具体职责命名；模块增长时再拆分职责文件，不先创建 controllers/managers/helpers 等没有明确用途的层级。

## 5. 外部契约与验证

Python 导入路径随目录更新；HTTP 路径、请求/响应结构和 Celery 消息名称保持稳定。特别注意 `tender.worker.tasks.*`、`tender.worker.knowledge.*` 是既有队列任务名称，不能根据新的 Python 路径替换它们，否则历史消息将找不到消费者。

检查点部署命令为 `python -m tender.adapters.pg.analysis.checkpoints`。这会初始化数据库，只在部署流程确实需要时运行；目录调整验证不应启动业务服务或调用真实模型。

在项目根目录运行：

```powershell
& scripts/check-backend.ps1
```

脚本运行 Ruff、import-linter 与全部 unit/contract 测试。首次准备依赖时，在 `apps/api` 执行 `uv sync --group dev`。`test_protocol_types.py` 自动调用 mypy 检查所有 ports、`core/di.py`、Agent 状态、轻量研究及合并审查、应用检索、任务服务、领域分块，以及报告和检索模型查询模块，并用真实仓储的错误签名探针验证门禁有效；这不是全项目 strict 检查，字典内部字段仍需行为测试。

分层由 import-linter 检查；`test_layer_boundaries.py` 检查重复架构层、根目录散落业务文件、跨层业务名称和直接/相对导入，包括 Worker 的数据库边界。当前目录名称检查要求七个已有业务在四处目录中存在，不能据此推导未来每个功能都必须补齐各层；调整检查规则需与实际设计一起评估。`test_task_registration.py` 验证派发消息仍对应已注册任务。目录重组还应对比 OpenAPI，涉及实际数据库路径时运行隔离数据库集成测试。不能为了迁就错误结构放宽规则。
