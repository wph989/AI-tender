# 后端日志基础服务

## 1. 范围

采用 Python 标准 logging + structlog。统一 API、Worker、Beat 的输出、关联上下文、异常脱敏和文件管理。基础模块通过框架入口接入；解析 Agent 的关键诊断通过已有业务日志保留。

基础模块位于 `apps/api/src/tender/core/logging/`：

- `__init__.py`：只导出公共接口，保持调用方的导入路径稳定。
- `setup.py`：幂等初始化、兼容框架 logger、关闭资源及内部配置状态。
- `context.py`：绑定与恢复关联字段，供以后按需使用。
- `formatters.py`：文本/JSON 格式、递归脱敏、字段和记录大小限制。
- `handlers.py`：每日/大小切分、过期清理、文件异常回退。

框架适配位于 `api/shared/logging.py`、`adapters/jobs/celery_logging.py`、`worker/logging.py`。基础模块不依赖 API、Worker 或数据库。

## 2. 配置

环境变量优先于 `apps/api/.env`，变更后重启相应服务生效。配置不放入数据库业务配置中心，数据库不可用时仍可记录运行日志。

| 参数 | 宿主机默认值 | 含义 |
| --- | --- | --- |
| `LOG_LEVEL` | `INFO` | DEBUG / INFO / WARNING / ERROR / CRITICAL |
| `LOG_OUTPUT` | `both` | stdout / file / both |
| `LOG_CONSOLE_FORMAT` | `text` | text / json；普通文件为 JSONL，错误文件为文本 |
| `LOG_DIR` | `logs` | 相对项目根目录；支持绝对路径 |
| `LOG_RETENTION_DAYS` | `30` | 包含当天的自然日数，正整数 |
| `LOG_TIMEZONE` | `Asia/Singapore` | 文件日期采用的 IANA 时区，默认 UTC+8 |
| `LOG_MAX_FILE_BYTES` | `104857600` | 100 MiB；最小 65536 字节 |
| `LOG_CLEANUP_INTERVAL_SECONDS` | `3600` | 后台检查周期，正整数秒 |

例如修改为保留 60 天，在 `apps/api/.env` 设置 `LOG_RETENTION_DAYS=60`，随后重启 API / Worker / Beat。

日志时间戳固定采用北京时间（`Asia/Shanghai`），保留毫秒及 `+08:00`，例如 `2026-10-18T00:00:01.123+08:00`。文件名日期仍采用 `LOG_TIMEZONE`，默认与北京时间同为 UTC+8。Windows 使用 tzdata 提供 IANA 时区数据，不依赖系统是否安装时区数据库。

## 3. 文件生命周期

默认目录：

```text
logs/
  api/2026-10-18.001.jsonl
  worker/2026-10-18.001.jsonl
  worker/2026-10-18.001.error.log
  worker/2026-10-18.002.jsonl
  beat/2026-10-18.001.jsonl
```

文件名格式为 `日期.分片序号.jsonl`，日期采用 `LOG_TIMEZONE`（默认 Asia/Singapore），不再包含启动时分秒、PID 或随机标识。同一服务同一天多次启动、多个进程运行都继续追加当天最新分片；下一条记录会超出 `LOG_MAX_FILE_BYTES`，或发现文件尾部没有换行时，递增序号；跨天从新日期的 001 开始。重启时读取现有分片的实际大小，按数字选择最大序号，不覆盖已有内容，也不填回较早分片。残缺尾行可能来自写入中断，旧分片保留供排查，后续完整记录写入新分片，避免拼接损坏。

错误文件与普通文件处于同一服务目录，使用 `日期.分片序号.error.log`，UTF-8 文本格式。ERROR/CRITICAL 以及任何带堆栈的记录（包括容错分支的 WARNING）写入错误文件；普通 JSONL 与控制台仅保留摘要和简短 `error`，不重复输出堆栈。两个文件各自在首次写入时创建并独立分片，序号不要求一一对应，通过时间、事件及关联 ID 查找详情。`LOG_OUTPUT=stdout` 时不创建文件，因此仍在标准输出保留堆栈，避免容器日志丢失诊断。

服务目录内固定的 `.write.lock` 是进程间协调文件，不是日志分片，不随重启或清理删除。写入、检查实际大小、切换分片与清理在同一把操作系统文件锁内执行，防止多个 Worker 同时判断空间后超写或交错堆栈。每条记录写完关闭文件句柄，进程异常退出由操作系统释放锁；等待锁超过 5 秒按写入失败回退到 stderr。无需新增依赖或环境配置。

旧版带启动时间/PID 或随机标识的文件保持原名，不合并、不追加，仍参与过期清理；服务加载新版后使用新的共享文件。

两类文件分别采用相同的切分和保留规则。跨天后的第一条记录写入当天文件；单文件即将超过大小限制时先开下一分片。JSON 记录及一整段文本堆栈都不会从中间拆开。无对应记录时不创建空文件。

清理规则：

1. 初始化时检查一次，运行期间每小时检查；即使没有新的日志也会执行。
2. 以文件名所属日期判断。2026-10-17 保留 30 天时，保留 2026-09-18 至 2026-10-17，删除更早日期的所有分片。
3. 只处理当前服务目录中符合本模块完整命名规则的普通文件，不递归，不删除符号链接或其他文件。
4. 当天已有多个分片不影响保留天数。删除失败保留文件，下次检查重试；同一目录内多个实例同时清理时也允许另一实例先删除。
5. 全部服务停止期间没有清理线程，下次启动补清。因此保留天数是清理规则，运行时会有至多一个检查周期的延迟；文件被占用等故障会继续延迟清理。

按大小切分只控制单个文件大小，不限制总占用，也不提前删除保留期内的日志。

每条记录立即写入并 flush，不引入应用级日志缓冲队列。flush 不等于 fsync，断电或进程被强制结束时不保证零丢失。文件创建、写入或清理失败时限频报告 `log_file_unavailable`，写入失败的已脱敏记录回退到 stderr，日志故障不主动终止业务。标准流写入失败时以 `log_stream_unavailable` 写入 stderr，记录格式化失败时返回固定的 `log_format_failed` JSON 兜底，两者都不再递归产生日志。

## 4. 输出与上下文

公共字段仅保留：`timestamp`、`level`、`event`、`location`。服务由日志目录区分，项目分析通过项目/报告身份关联业务，不再为每条自动添加 `service`、`process_id` 或 `logger`。

字段顺序固定为 `timestamp` → `level` → `event` → `location` → `request_id` → `job_id` → `project_id` → `report_id` → `module_key`，只输出有值的字段；其余业务字段按名称排序，文本堆栈放最后。顶层的 None 与空字符串省略，保留有业务含义的 0 和 False。

事件使用短名称，例如 `http`、`http.abort`、`task.start/end/fail/retry`、`report.start/end/abort`、`module.start/end/fail/cancel`、`tool.call`、`model.call`。模型和工具调用各自在完成时记录一次；模型事件包含实际模型名、累计输入/输出 token 数和整次调用耗时，重试与切换仍写入调用账本，不再额外输出模型过程事件。工具事件包含工具名、脱敏后的参数、耗时和结果状态。

`agent.round` 的逐轮阶段、预算与进展快照仅记 DEBUG，默认 INFO 不输出。文本、JSONL和错误文件统一省略顶层 `task_id`、`run_id`、`tool_call_id`、`invocation_id`、`thread_id`、`skill_path`、`sha256`；这些身份与元数据仍用于队列、数据库运行账、模型调用账本、工具协议、Skill快照及检查点恢复，不改内部执行机制。项目分析日志使用 `project_id + report_id + module_key` 直接区分项目、报告和专题，补跑次数在 `module.start` 的 `attempt` 查看。

普通日志从堆栈中的实际异常行提取错误摘要并保留多行原因，跳过 Python 的 `During task...` 注记和 SQLAlchemy 帮助链接；这些框架附注不能代替解析失败原因。完整堆栈仍写入对应错误文件，已有显式 `error` 字段优先，脱敏和长度上限不变。

模型路由所有候选失败时，最终业务异常汇总各已尝试模型的脱敏失败原因，同模型同原因重试去重；首候选的渠道错误不再掩盖后备的余额不足或权限限制。实际请求次数、故障转移上限及每次调用账记录不变。

`location` 使用真实代码路径和行号，例如 `tender/api/jobs/routes.py:34`。项目代码省略部署目录前缀，其余来源保留原路径。普通业务及标准 logging 指向日志调用行；接口访问摘要指向匹配接口的定义处（有装饰器时从定义前的装饰器首行开始），支持同步、异步和使用 `functools.wraps` 的包装器。没有匹配端点的请求回退到中间件日志调用处。

关联字段在有来源时提供，缺失时不伪造：`request_id`、`job_id`、`project_id`、`report_id`。任务日志另带任务名、重试次数或执行耗时。只有执行器实际读取报告后才绑定其项目身份；周期任务、无项目的知识库任务不猜测项目，也不为了日志在基础服务查询数据库。

- HTTP 请求校验/生成 `X-Request-ID` 并回传，用于关联同一请求中的业务日志、访问摘要和异常。自动生成的 request_id 和 Celery task_id 共用生成逻辑，均为 12 位 URL 安全字符（72 位随机值），不使用 UUID；合法 ID 指 1–128 位、仅含 `[A-Za-z0-9_.:-]` 的值，非法或缺失时请求改用新生成的短 ID，任务消息头中未通过同一校验的字段不绑定。显式传入的合法 ID 原样保留，不截短，以免破坏已有链路。真实业务 ID 不截短。
- 访问摘要记录路由模板、方法、状态和耗时。不读取请求体、查询字符串或鉴权头。正常完成使用 `http`，中断使用 `http.abort`，删除重复的 `outcome` 字段。成功的健康检查保持仅 DEBUG。
- 普通 HTTP 访问摘要由中间件输出，关闭 Uvicorn 的重复 access 日志。未处理异常沿用 API 唯一错误处理入口，Uvicorn 不再重复打印同一异常堆栈。`httpx`、`httpcore`、`sqlalchemy.engine`、`boto3`、`botocore` 固定为 WARNING，这些库的 INFO 及以下不进入统一日志。
- 只有显式加上 `@throttle_access_log()` 的接口，对正常完成的 2xx/3xx 请求按「方法 + 路由模板 + 状态码」限频。首条立即记录，从该次记录开始计时，窗口内重复请求不输出访问摘要，也不延长窗口；到期后的首条再次记录。默认 60 秒定义在装饰器中，不写入环境配置；可用 `@throttle_access_log(15)` 单独设置 15 秒，传 0 关闭。未加装饰器的接口逐条记录，不对全部 GET 或全部接口默认限频。
- 装饰器仅给原函数添加标记，中间件读取实际匹配端点的标记，在响应结束后决定是否记录；不包装业务调用，不改变 FastAPI 签名解析、依赖注入和同步/异步调度。例如 GET `/api/v1/jobs/1` 与 `/api/v1/jobs/2` 的 200 共用 `/api/v1/jobs/{job_id}` 的窗口，304 独立计时；路径参数和查询参数均不参与分组。不同报告、不同专题的记录查询也合并到同一路由模板的窗口，避免一轮轮询仍输出多条相同模板日志。
- 4xx、5xx、异常、断流和取消不受访问限频影响，也不重置成功分组的窗口。已发出 200 响应头后中断仍保留实际状态码，并以 ERROR 和 `http.abort` 逐次记录。请求执行、响应和 `X-Request-ID` 不受影响。
- 窗口采用单调时钟，每个 API 应用实例独立计时，重启后重新开始；线程间检查与更新互斥。相同窗口长度共用缓存，不同长度独立清理；后续受限接口的成功请求清理对应缓存中的过期分组，不会提前淘汰有效分组。因此内存随窗口内的不同分组数增长；无新请求时不单独启动清理任务。
- 不再统计或输出 `suppressed_count`，限频仅决定当前摘要是否输出；日志不作为请求总量或审计记录。
- Celery 发布信号向消息头传递已有的关联字段，执行前绑定，执行结束后恢复；线程并发和嵌套 eager 调用互不串号。子任务始终使用自己的 `task_id`。
- Celery 用 `task.start`、`task.end`、`task.fail`、`task.retry` 记录生命周期，失败/重试后不再补一条 INFO 结束记录。`task.end` 仅表示函数正常返回，不表示业务分析成功；删除重复的 `execution_state`，异常状态才另记 `task.stop`。短任务名 `task` 仅在开始、失败和重试时提供；首次执行不输出零值重试次数。不采集 Celery 任务 args、kwargs 或结果正文。Agent 工具参数按上文的 `tool.call` 记录，并经过统一敏感字段脱敏和日志长度限制。
- 专题上下文包含项目 ID、报告 ID 和专题键，不再每条输出队列任务 ID、运行 ID、module_id、attempt；运行次数在专题开始时提供。`model.call` 在一次路由调用结束时记录最终模型名、累计输入/输出 token、总耗时和状态；各供应商请求、重试及切换明细仍写入模型调用账本。
- 周期派发任务 `tender.worker.dispatch.dispatch_pending`、`tender.worker.knowledge.dispatch_knowledge` 的开始及成功结束仅记 DEBUG，默认 INFO 不输出这些循环消息。任务内警告、失败与重试仍正常记录，其他业务任务的生命周期仍记 INFO。排查周期派发过程时可临时设置 `LOG_LEVEL=DEBUG` 并重启 worker。
- 访问限频只在 API 中间件生效，不过滤解析 Agent 日志。报告/专题生命周期、Skill 加载、工具调用、研究/综合/核验阶段和记录驳回原因继续输出；每个 Agent 工具仅在完成时输出一条 `tool.call`，包含工具名、脱敏参数、耗时和状态。模型请求正文不写入运行日志。

已按当前前端轮询调用链为以下 11 个 GET 接口加装饰器（均以 `/api/v1` 开头）：

| 接口路径 | 前端轮询来源 |
| --- | --- |
| `/jobs/{job_id}` | `waitForJob` 每秒等待任务结束 |
| `/projects/{project_id}` | `ProjectFiles`、`ProjectWorkspace` 跟进转换/解析进度 |
| `/projects/{project_id}/analysis`、`/analysis/reports/{report_id}`、`/analysis/reports/{report_id}/modules/{module_key}/records` | `ProjectAnalysis` 每三秒刷新状态、报告与专题记录 |
| `/knowledge/collections/{collection_id}` | `KnowledgeCollectionDetail` 每三秒跟进入库进度 |
| `/knowledge/answers/{answer_id}` | `QuestionPanel` 每 2.5 秒等待问答结束 |
| `/llm/settings`、`/llm/providers`、`/llm/models`、`/llm/features` | 模型测试期间 `ModelsPanel` 每两秒调用 `ModelSettings.reload`，一起读取这四项 |

新轮询接口按需在路由函数上标记，路由装饰器放外层：

```python
from tender.api.shared.logging import throttle_access_log

@router.get("/{job_id}")
@throttle_access_log()  # 前端持续查询进度，只压缩重复成功访问摘要。
def get_job(job_id: str, request: Request):
    ...
```

API→数据库→Beat→Worker 的流程尚未持久化最初的请求 ID。这里只传播实际存在的上下文，不能宣称完整分布式追踪。业务 ID 也不从所有任务首参猜测；业务以后需要时可使用：

```python
from tender.core.logging import bind_context, get_logger

logger = get_logger(__name__)
with bind_context(job_id=job_id):
    logger.info("event_name", count=3)
```

访问限频不改变已有业务日志，也不引入日志查询页面、数据库日志表、指标或追踪平台。现有模型调用账本、Agent 事件和配置审计保持各自职责。

## 5. 内容控制

- 字典/列表递归过滤密码、密钥、token、Cookie 等字段；默认屏蔽 prompt、messages、请求/响应正文、任务参数与结果。无法识别的对象只记录类型名，不调用其 `repr`，避免格式化触发业务行为或泄漏正文。
- 未知异常保留类型与堆栈，不采集局部变量。API 兜底、Celery 失败信号以及捕获后收敛为业务失败/回退的入口均记录异常；文件预处理、解析引用持久化、索引、问答、派发及检索回退不会仅更新状态而丢失堆栈。凭证文本规则与上游错误详情共用，额外处理连接串凭证。
- 单字段最多约 16000 字符、嵌套最多 8 层、容器最多 100 项、单条记录按最终 JSON/文本的 UTF-8 字节数（含换行）限制在 64 KiB 内；超限明确标记。长堆栈保留首尾以保留最终异常原因，其他业务字段超限时优先保留事件、位置、关联 ID 及堆栈；保留字段仍超限时继续缩短最大的字段，不能仅靠字符数或删除业务字段判断已满足限制。
- 初始化时注册环境中的已知凭证用于文本替换。不读取数据库解密所有供应商密钥；业务上游错误仍由既有适配器在知道具体密钥时脱敏。任意第三方自由文本中的未知敏感内容无法仅靠字段规则全部识别，因此不应主动记录原文或完整请求对象。
- 索引和问答收口时，`TenderError` 只格式化业务异常自身堆栈，不回放原始 SDK 异常链，以免重新暴露适配器已隐藏的供应商密钥；未知异常仍保留完整异常链，统一经过日志脱敏和限长。

## 6. 本地与容器

本地后台启动脚本复用 Python 的日志配置解析器，并读取模块管理的 JSONL。脚本需要 file 或 both 输出；日志配置、输出模式及目录创建检查在 `-Force` 停止旧实例之前完成，检查失败不会停止旧服务。`-Stop`、`-Status` 不依赖日志配置。不再将标准流重定向到会覆盖历史、无限增长的固定文件。

日志初始化后的 API 装配异常记录为 `api_initialization_failed`，JSONL 保留原因摘要，同目录的文本错误文件保留经过脱敏的堆栈，再重新抛出使进程失败退出。启动脚本读取 JSONL 摘要，详情查看 `.error.log`。Celery 父进程报告的任务失败兼容字符串堆栈，统一脱敏及限长。Celery 的终端横幅及日志初始化前的直接 stderr 输出不作为长期运行日志保存；初始化前失败可按本地指南前台启动查看。

Compose 默认 stdout + JSON，Docker local driver 按 100m / 5 个文件轮转。这是按大小/数量管理，不是按天保留。

如果容器也需要 30 天文件留存，将仓库根 `.env` 中 `LOG_OUTPUT` 改为 `file` 或 `both`，文件保存在 `backendlogs` 命名卷，容器内路径 `/app/logs`。镜像预建该目录并赋予应用用户权限，重建容器保留卷内历史。修改输出配置后需重新创建相应容器。
