# 人员要求解析 Skill

## 适用场景
- 触发：项目控制器启动当前专题人员要求解析任务时调用。
- 输入：授权资料清单与按需检索得到的原文块，不预先灌入全文。
- 输出：完成检索后按专题模板综合的 content JSON，逐条附独立的原文溯源引用。

## 领域知识

人员要求是对投标人拟投入本项目的具体岗位人员提出的可操作要求，主要包括：

1. **项目经理/负责人**：资质等级、从业年限、类似项目经验
2. **技术负责人**：职称、专业背景、资格证书
3. **其他关键岗位**：安全员、质量员、施工员等
4. **人员数量**：各岗位的最低人数要求
5. **社保证明**：是否需提供社保缴纳证明
6. **不得兼任**：哪些岗位不得由同一人兼任

候选条款必须满足：主语是具体人员或岗位，且至少包含人数、个人证书/职称/学历、明确年限或针对个人属性的量化评分之一。仅出现岗位名称、团队配置合理等模糊表述不得提取。

必须排除企业资质/认证、企业业绩、企业持有证书数量、报价与商务条款、投标文件格式、中标后抽测，以及人员行为规范、稳定性、管理制度、服务态度和责任承担等软性要求。要求提供社保、劳动合同等证明材料时可以提取，但一般性的依法缴纳社保不得提取。

## 识别规则

关键词种子（可扩展，不限于）："人员"、"项目经理"、"技术负责人"、"配备"、"团队"、"人员配置"

## 执行流程

1. **主题检索**：使用 `search_document` 搜索"人员""项目经理"等章节
2. **扩展上下文**：根据命中位置使用 `read_document` 读取相邻条款
3. **主语判定**：回答“投标人是否需要为此安排一个具体的人”，否则排除
4. **逐岗位归并**：提取数量、评分、个人证书、经验、专业、技能、证明和兼任限制
5. **输出结果**：按本 Skill 的输出协议调用 submit_analysis；没有依据的条目省略。

## 本项目的检索与输出

- 输入是授权资料清单及检索返回的 id/text 原文块。先核对主文件、澄清、补遗和相关附件，按 coverage.json 的业务主题继续检索；关键词只是线索，不保证完整召回。
- list_documents 返回资料ID与说明；search_document 检索本项目，search_knowledge 检索关联参考库。参考资料不能替代项目依据，参考建议也需要引用本项目相关要求。
- 遇到转引按目标名称、章节或业务主题继续检索，read_document 围绕已读 block_id 补读表头、脚注和条件；不猜测ID、磁盘路径或全文行号。未命中、缺失目标及预算不足如实登记。
- 完成主题核对后调用 complete_research，再综合同一范围内的完整事项。未命中不等于文件未约定；新增原文后重新确认检索和综合，空检索不要求重做已有事项。
- 按 output_format.md 批量调用 submit_analysis，每次最多三条完整事项；相互独立的事项可放在同一批，有父子或端点依赖的事项分步提交。content 承载业务内容，citations 独立提供已读ID及连续原文；不同标段或条件不强行合并。
- 最后一批可携带 records 并设 final=true，通过校验即收尾；仅确认收尾时可用空 records，保留未决 coverage/gaps。遇到工具错误按实际反馈和剩余额度纠正，不自行设定重试次数。
- 权限、调用预算、结构和支持性校验由运行时执行。read_file 只读取当前 Skill 的参考文件或会话历史；不读取招标文件磁盘路径，不递归委派子Agent。

## 参考文件

运行时首次推理前已加载正文、输出说明、核心细则和明确品类的规则；无需重复读取，示例按需通过 read_file 查阅。

- `references/output_schema.json`：本项目机器格式声明，运行时从报告快照读取。
- `references/output_format.md`：事项组织、字段含义和实际 JSON 提交示例。
- `references/coverage.json`：本专题检索覆盖清单，未解决主题保留缺口。
- `references/<type_dir>/extraction_rules.md`：按实际品类加载的专题细则。
- `references/<type_dir>/examples.md`：模拟原文块与逐条提交样例。
type_dir 为 engineering、goods、service；只采用运行时明确的项目/标段品类，混合品类分别核对，不默认服务类。
